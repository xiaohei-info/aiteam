# 契约先行的并行开发拆解方法论

> **一句话**：先把"模块之间怎么对接"用**代码契约**钉死成地基，再让各模块**对着 mock 的对端**并行开发，最后替换 mock 做集成验收；全程用**接口契约 + CI 闸门 + 独立评审**三层防线，让"跑偏"在物理上做不到、或当场被拦下。
>
> 本文是**可复用的项目拆解 playbook**，与具体技术栈/业务无关。文末附一个真实工程（AI Team v1）的套用实例。

---

## 0. 解决什么问题

多人/多 Agent 并行开发大型系统时，两个矛盾反复出现：

1. **并行 vs 一致**：拆得越细越能并行，但模块越多越容易接口对不齐、各自发明 DTO/枚举/错误格式，集成时炸裂。
2. **效率 vs 不跑偏**：任务一多、链路一长，开发者（人或 AI Agent）"写着写着就偏了"——很多实现细节与设计文档、核心约束悄悄冲突，越往后越难纠。

本方法论用一个核心动作同时化解二者：**把"接口"和"约束"从文字变成代码与闸门**。接口是代码，偏不了；约束是测试，偏了就红；剩下的语义偏差，由独立评审兜底。

**适用**：跨模块/跨服务、有清晰模块边界、需要多人或多 Agent 并行、且有设计文档可依的中大型工程。
**不适用**：单人单模块的小改动、探索性原型（此时契约还没稳定，过早冻结是浪费）。

---

## 1. 核心信念

1. **跑偏不能靠"提醒"治，要靠"结构"治**。"记得看文档"不可靠；让错误的写法编译不过/测试不过/合并不了，才可靠。
2. **接口是地基，不是产物**。模块间的契约（数据结构、事件、错误、状态、跨服务调用）必须**先于**业务实现冻结，且以**代码**形式存在。
3. **对端可以是假的**。只要契约冻结，每个模块都能对着对端的 mock/fake 独立开发，无需等对端做完——这是并行度的来源。
4. **单一事实源**。每条口径只有一个权威出处（一段代码或一篇文档），其它地方引用它，禁止平行拷贝（拷贝必然漂移）。
5. **"完成"必须有客观证据**。不是"我觉得没问题"，而是测试/构建/接口调用通过。

---

## 2. 三层防跑偏模型

把"防跑偏"拆成三层，越靠上越硬、越早生效：

| 层 | 防什么偏 | 手段 | 偏了会怎样 |
|---|---|---|---|
| **接口层** | 模块间对接不一致（DTO/事件/枚举/错误/调用形状） | **契约即代码**：共享类型包，下游只 import、禁重定义 | 类型/导入/契约测试不过——**偏不了** |
| **边界层** | 越过职责红线、用了被禁的旧口径、违反硬约束 | **CI 闸门**：边界扫描 + 契约不变量测试 + 质量门禁 | 当场红灯——**偏了立刻知道** |
| **语义层** | 接口对、约束没违反，但实现意图跑偏了设计 | **独立评审**：非实现者对照"设计文档 × 约束"逐条核对 | 合并被打回——**兜底** |

> 经验法则：**CI 抓接口/边界漂移，评审抓语义漂移**。两者互补，缺一不可。

---

## 3. 拆解方法：从设计文档推导出"地基 + 并行 track"

给定一份（或一组）设计文档，按以下 5 步推导出可执行的并行计划。

### 步骤 1 — 找出"地基"（所有并行的硬前提）

地基 = 被所有模块依赖、且模块之间靠它对接的东西。通常包含四类：

- **共享契约（最关键）**：模块间一切对接口径，落成代码——数据结构、事件、枚举、状态机、错误模型、响应包络、跨服务调用的请求/响应、抽象接口（ABC/interface）。
- **共享底座**：认证、配置、日志/trace、统一错误处理、服务间客户端、数据访问基类等"每个模块都要用、不该各造一份"的东西。
- **骨架 + 启动器**：可运行的空壳（每个服务/模块能起来、暴露健康检查与接口文档入口）。
- **闸门 + 假件**：CI（契约测试、边界扫描、质量门禁）+ 对端的 fake/mock（让下游能脱离真对端开发）。

**地基必须串行先行**，由一个精干小组完成、重度评审、**冻结后**才放开并行。这是整个方法的命门。

### 步骤 2 — 找"集成缝"，缝即并行边界

模块之间**唯一**的对接点就是步骤 1 冻结的窄契约。沿着这些"缝"切，缝两侧就是可独立并行的 **track**。判据：两个模块如果只通过契约交互、不共享内部状态，它们就能并行。

### 步骤 3 — 每个 track 内部再找"小地基"

一个 track 内部往往也有先后：某个基础能力（如租户上下文、认证、数据会话）是该 track 其它业务模块的前提。把它标为 track 内的"小地基"，先做，再放开 track 内的业务模块并行。

### 步骤 4 — 给每个并行单元配"对端 mock"

凡是依赖尚未完成的对端，就对着契约写一个 mock/fake。这样所有 track 同时开工，wall-clock 不被最慢的对端拖住。

### 步骤 5 — 末尾留"集成验收"波

把"替换 mock → 真对端"、端到端流程、关键不变量（隔离、隐私、性能、契约 parity）验证集中到最后一波，作为统一的"完成"靶子，避免各模块各自宣称完成却没有共同验收标准。

---

## 4. 三波次执行模型

```
Wave 0  地基（串行，1 小组，冻结后放开）—— 契约 + 底座 + 骨架 + 闸门 + 假件
   │
   ├───────── 多个并行 track（对端用 mock/fake）──────────┐
Wave 1   Track A   Track B   Track C  ...
         (小地基先行 → 业务模块并行)
   │                                                      │
   └──────────────────────────────────────────────────────┘
Wave 2  集成验收（替换 mock → 真对端，跑统一验证矩阵）
```

- **Wave 0**：不产出业务功能，只产出"让并行安全的前提"。宁可在这里多花时间，也不要带着没冻结的接口扇出。
- **Wave 1**：最大并行。每 track「小地基 → 业务模块」，业务模块之间尽量互不依赖。
- **Wave 2**：把分散的"完成"收口为一次可验证的集成验收。

---

## 5. 工单卡（让每个并行单元死守自己的口径）

并行扇出时，给每个单元发一张**自包含工单卡**，而不是一句话任务。卡片把"该看哪份文档、守哪些约束、用哪些契约、不许碰什么、怎么算完成"全部前置，使开发者（尤其是上下文有限的 AI Agent）在长任务里始终被锚定。

```
【模块】<名>            【波次/track】<W1 · Track B>
【唯一口径文档】<指向单一权威：某篇设计文档 + 节号>
【必守约束】<该模块最易违反的 3–5 条硬约束，从全局约束文件 + 口径文档摘出，复述在最前>
【必消费契约（禁止重定义）】<共享契约包里的具体类型清单>
【落点】<目录/文件路径>
【依赖】前置=<本 track 小地基/卡号>；对端=<mock 谁>
【红线（禁止做）】<越界清单：不该写的表、不该调的服务、不该上传的数据……>
【验收（可验证）】<测试/接口调用/parity 证据，而非"应该没问题">
```

要点：**一卡一份唯一口径文档**（不要让一个 Agent 同时背五篇）；红线和必守约束**复述在卡片最前面**（别指望它会去翻），因为"显著性"决定它会不会真的遵守。

---

## 6. 七道防跑偏闸（落地清单）

按"越早越硬"排序，按项目选用、可叠加：

1. **契约即代码** — 共享类型包；下游只 import、禁平行定义。接口漂移→编译/类型/测试不过。
2. **单文档单负责人工单** — 见 §5。一卡一口径，约束前置。
3. **常驻护栏** — 把全局核心约束放进"每次都会被加载"的地方（如 AI 协作的 CLAUDE.md/AGENTS.md，或团队的 PR 模板/lint 规则），而不是埋在长文档里。
4. **小任务粒度** — 任务切到"一两个文件、可短时收口"。跑着跑着才会偏，不给它跑远的机会；配检查点推进。
5. **客观 CI 闸门** — 把硬约束变成测试：
   - **契约不变量测试**：枚举取值、事件类型集合、必填字段等被悄改即红（"漂移守卫"）。
   - **边界扫描**：禁用的旧路径/旧标识/旧 env/越界 import 等，grep/AST 扫描，命中即红（注意排除文档/注释里的"反向说明"，避免误报）。
   - **质量门禁**：接口 schema、唯一 id、错误覆盖、产物隔离等。
   - **关键不变量 e2e**：隔离、隐私、parity 等，先以占位 skip 钉死"要验什么、归哪波、对哪份文档"，对应模块就绪后转正。
6. **独立评审闸** — 非实现者拿"模块 diff × 唯一口径文档 × 全局约束"逐条核对再合并。抓 CI 抓不到的语义漂移。
7. **完成前独立验证** — "完成"必须附证据（测试/构建/接口/parity），"我觉得可以"不算完成。

## 7. 套用到新项目的操作清单（recipe）

```
[ ] 0. 锁定设计文档为单一事实源；散在多处的口径先收敛/去重。
[ ] 1. 按 §3 步骤1 列出"地基四件套"：共享契约 / 共享底座 / 骨架启动器 / 闸门+假件。
[ ] 2. 把模块间所有对接口径写成代码契约（数据结构/事件/枚举/状态/错误/跨服务调用/抽象接口）。
[ ] 3. 为契约写"不变量测试"（取值集合、必填、抽象不可实例化…）——这是漂移守卫。
[ ] 4. 写边界扫描测试（禁用旧口径/越界 import…）+ 质量门禁，接进 CI。
[ ] 5. 搭可运行骨架 + 对端 fake/mock，使下游能脱离真对端开发。
[ ] 6. 用测试验证地基本身可跑、可测、全绿——地基冻结。
[ ] 7. 沿"集成缝"切出并行 track；每 track 标出"小地基先行"。
[ ] 8. 给每个并行单元写工单卡（§5），分发。
[ ] 9. 并行开发：小任务、对端用 mock、每单元自带验收证据、独立评审后合并。
[ ] 10. 末尾集成验收波：替换 mock→真对端，转正 e2e 验证矩阵。
```

**判断地基是否冻结好了的信号**：你能写出每个并行单元的工单卡，且卡里"必消费契约"都已是可 import 的代码、"验收"都已有对应（哪怕 skip 的）测试位。做不到，就说明地基还没好，别扇出。

---

## 8. 常见误区与限制

- **误区：跳过 Wave 0 直接并行**。最常见的失败。没有冻结契约就扇出 = 各自发明接口 = 集成地狱。
- **误区：契约写成文字而非代码**。文字契约挡不住漂移；必须是可 import、可测试的类型。
- **误区：地基追求"实现完整"**。地基要的是"形状对、可对接、可测试"，真实重实现（如真数据库、真加密）可以留占位、标注归属到具体业务工单——**地基定形状，业务填实现**。
- **误区：边界扫描过度，误报淹没真报**。要排除文档/注释里的"反向说明"，否则团队会习惯性忽略红灯。
- **误区：一张工单背多份文档**。Agent/人都会被稀释注意力；一卡一口径。
- **限制**：契约不稳定的探索期不适用——先用原型把契约探明，再进入本方法。契约本身改动属高风险操作，需评审，不能随手改。

## 附录 A：AI Team v1 的套用实例

本方法论提炼自 AI Team v1（三端微服务：运营/企业/用户）的实际落地，对应物：

| 方法论概念 | AI Team v1 实例 |
|---|---|
| 单一事实源（设计） | `docs/v1正式版本/技术设计/概要设计/` 00–11 + 根 `CLAUDE.md`/`AGENTS.md` |
| 并行编排与工单卡 | `docs/v1正式版本/技术设计/概要设计/11-开发实施与并行编排.md` |
| 共享契约（代码） | `server/shared/contracts/`（envelope/枚举/事件/RunSpec/Executor·Driver ABC/跨端契约…） |
| 共享底座 | `server/shared/{config,errors,observability,auth,service_client,db,app_factory}` |
| 骨架 + 启动器 | `server/{operation,manager,agent}_service/app.py` + `server/run.py` |
| 对端假件 | `server/agent_gateway/fake_runtime.py` |
| 契约不变量测试（漂移守卫） | `server/tests/contracts/test_contracts.py` |
| 边界扫描 | `server/tests/boundary/test_constraints.py` |
| e2e 验证矩阵（占位钉靶） | `server/tests/integration/test_verification_matrix.py` |
| CI 闸门 | `.github/workflows/ci.yml` |
| 集成缝 → 并行 track | 三端只经窄 pull 契约对接 → Track Manager / Agent / Gateway / Operation / 前端并行 |
| 小地基先行 | Track Manager 的"租户底座+认证"先于其业务模块；Track Agent 的"本地骨架+登录+网关骨架"先于本地主链 |

> 即：本方法论是"道"，AI Team v1 的 `server/` 地基与 doc 11 是"术"的一次完整实例，可作为新项目套用时的参照模板。
