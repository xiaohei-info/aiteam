# 基于 multica 的多 Agent 并行开发编排 · 设计

## 0. 背景与定位

现有 `parallel-dev-orchestration` skill 把设计/plan 拆成"GitHub issue DAG"，用长轮询的 `orchestrate-tick` 驱动多 Agent 并行。multica 提供了一套**更原生**的能力（squad/leader、issue 状态机、原生 agent 派发、runs 留档、metadata KV），但它要的不是"换个 issue 后端"，而是**另一套执行范式**：

- GitHub 版：`orchestrate-tick` 长轮询；DAG 挂在 issue `blockedBy`；orchestrator 每 tick 当大脑；worker 由 orchestrator 临时 spawn。
- multica 版（本文）：leader（orchestrator）把 DAG + worker 映射固化成一份 **manifest**，由一个**固定引擎**自治地把整张图并行跑完；leader 只在"出错/跑完"才爆发式介入。worker 与 reviewer 都是 **squad 成员 agent**，经 multica 原生派发、在 `issue runs` 留档。

两者是不同控制范式，强行合并 = 一个 skill 背两套范式 + 分支堆叠。**故独立成新 skill**；两者共引同一份「方法论」作为单一来源的"道"，避免理念漂移。

## 1. 核心决策一览（D-列）

| # | 决策 | 取舍理由 |
|---|---|---|
| D1 | 独立新 skill，不与 gh 版合并 | 执行范式不同；共引方法论防漂移 |
| D2 | DAG 依赖 = issue `metadata.blocked_by`（真 DAG，多前置）；`parent` 仍表"卡内 sub-issue" | 父子是树不是 DAG，且与 sub-issue 语义冲突；metadata 忠实表达多前置 |
| D3 | Plan-as-manifest：leader 产**声明式 manifest（数据，非代码）** | 生成数据不生成逻辑，漂移面≈0；保留"动态生成+静态执行"的机制 |
| D4 | 执行引擎 = 固定独立 Python runner，**不套用 harness Workflow 工具** | runtime 错配（见 §6）；但**借其执行语义** |
| D5 | worker 与 reviewer 均经 `multica issue assign` 原生派发，均在 `issue runs` 留档 | 统一留档；reviewer 与 worker 同等可追溯 |
| D6 | roster = **squad 成员**（leader 查 `squad member list`）；成员可互换，仅保证 reviewer≠worker | 贴 multica 原生 squad/leader 模型；零配置文件、零 role 配置 |
| D7 | 防跑偏协议经 **executor skill** 装到成员 agent（`agent skills add`），不复制进 issue body | 单一来源、显著性高、不漂移 |
| D8 | 结构性闸：节点只能经 `in_review→done` 且由 reviewer run 驱动到达 done；worker 永不能自置 done | 把"worker 回报不可全信"用结构落地 |

## 2. 整体架构

```
┌─ squad（如 dev team）────────────────────────────────────────┐
│  leader agent  ◀── 装 orchestration skill（本 skill）          │
│     │  ① 读设计/plan → 拆卡建 issue(todo,无 assignee)          │
│     │  ② 写 manifest(节点/依赖/worker + 评审旋钮)              │
│     │  ③ lint manifest → 单向编译进 issue metadata             │
│     │  ④ 启动固定引擎(run_dag.py)                              │
│     ▼                                                          │
│  固定引擎 ── 读 issue list/metadata → 连续 frontier → 并发派发  │
│     │                                                          │
│     ├─▶ member agent（worker）◀── 装 executor skill            │
│     │      multica issue assign → in_progress → 跑 worker 半    │
│     │      → PR(base=集成分支) → CI                            │
│     └─▶ member agent（reviewer，≠worker）◀── 同 executor skill │
│            in_review → assign → 跑 verifier 半 → 结构化裁决     │
│  全程 runs/run-messages 留档；leader 决策经 squad activity 留档 │
└────────────────────────────────────────────────────────────────┘
```

**两个真源，职责不重叠**：
- **manifest** = leader 的编辑/评审/diff 源（一眼看全整张图、跨失败轮次可 diff）。
- **issue metadata + status** = 引擎运行时源 + status 持久续跑源。
- 两者靠**单向 `apply`（manifest → metadata）**连接，不双向同步、不漂移。

## 3. 核心机制

### 3.1 squad-native roster（D6）

leader（已装本 skill）运行时自行感知可用 agent，无需任何配置文件：

1. 解析自己的队：`multica squad list --output json` → 找 `leader_id == 自己` 的 squad。
2. 枚举成员：`multica squad member list <squad-id> --output json` → 取 `member_type==agent && role!=leader` 为**可用池**。
3. 每个 issue：`worker` 由 leader 从池中按卡选定（写进 manifest）；`reviewer` = 池中任一 ≠ 该 worker 的成员。
4. 项目级配置（集成分支等）放 squad `instructions` 字段。

**换队 = 换 roster**：rd team / dev team 天然隔离。成员可互换（人人能 worker 能 reviewer，由 status 自感知 executor skill 决定行为），reviewer≠worker 由引擎逐 issue 保证。

> 已实测命中（workspace `410ade5e-…`）：`hermes team / dev team / rd team` 均带 `leader_id` + `instructions`；`squad member list` 返回 `member_id/role/member_type`；`squad activity <issue> <action|no_action|failed>` 官方定位为"squad leader agents 记录决策进 issue timeline"。

### 3.2 issue 模型与 metadata-DAG（D2）

- 建卡：`multica issue create --status todo`（**不分配 assignee**），body 放方法论 §6.3 的**锚定结构**（目标/必消费契约/红线/范围边界/验收/测试落点/参考锚点——全是指针，不复制正文）。
- 依赖边：`multica issue metadata set <id> blocked_by '<json id 列表>'`。`ready = 所有 blocked_by 节点 status==done`。
- 卡内分解仍用 `--parent`（原义不变）。

### 3.3 Plan-as-manifest（D3）

manifest 是一份声明式数据（YAML），节点引用 issue key，结构：

```yaml
meta:
  squad: dev team
  integration_branch: feature/v1.0.0   # 亦可取自 squad.instructions
nodes:
  - id: M1                  # issue key
    worker: <member-agent>  # 必填：从 squad 可用池中选
    blocked_by: [M0]        # 编译进 metadata.blocked_by
    # —— 评审旋钮，全可选，缺省=任选异于 worker 的成员 + 单审 ——
    reviewer: <member-agent>             # 指定专审（可选）
    risk: high                           # 升级多 lens 评审（可选）
    gate: { tests: "pytest -m 'not integration'" }   # 该卡测试命令（可选）
```

**生命周期**：leader 生成/编辑 manifest → `lint` → 单向编译进 issue metadata → 固定引擎执行 → 失败则 leader 改 manifest → 再 lint → 再编译 → 重跑（status 持久 = 免费 resume）。这就是"动态生成 + 静态执行"，但生成物是**数据**。

**`lint`（执行前校验，借 Workflow 的 meta/schema 校验思想）**：DAG 无环？每节点 `worker` ∈ squad 可用池？每个 `blocked_by` 引用存在？`reviewer`（若指定）≠ 该节点 `worker`？——**任何 agent 被派发之前**挡住 leader 的拼图错误。

> **评审不进 manifest，评审旋钮才进**：评审是每个工作节点的**固定强制阶段**（worker→评审→done），固化在引擎里，正因如此不可被遗漏/绕过。manifest 只放"评审怎么调"（reviewer/risk/gate），不放"要不要评审"。

### 3.4 固定引擎执行语义（D4，借 Workflow 之魂）

引擎 = 固定独立 Python runner（与 gh 版 `orchestrate.py` 同形态），主循环：

1. `multica issue list --output json`（**一次调用**，带 status+metadata）→ 建图。
2. 算 **frontier**（`blocked_by` 全 done、自身未 done）——**连续 frontier，不设 wave barrier**（某节点 deps 一闭合就派，不等同层其它节点）。
3. **并发（信号量封顶）**对每个 frontier 节点跑 §3.5 的节点循环。
4. **失败按分支隔离**：单节点失败只 block 其下游，健康分支继续跑；frontier 耗尽时把失败集**一次性**汇总。**仅横切/基建失败（契约坏、CI 基建挂）才 fast-fail 立退**。
5. 无 frontier = **ALL_DONE**，退出并出 digest。

**借鉴自 harness Workflow 的执行语义**：连续 frontier（无 barrier）、分支隔离失败（优雅降级）、结构化校验裁决、并发封顶、幂等重入（这里用 **issue status 持久**实现，比 resumeFromRunId 更强：跨会话）。**逃生舱**：引擎拆成"固定原语库 + 薄 driver"，默认 driver 走 manifest；万一某任务需自定义拓扑，可写薄脚本 over 同一组原语——留门不默认。

### 3.5 worker 派发与 reviewer 闸（D5/D7/D8）

单节点固定循环：

```
dispatch worker:
  multica issue assign <id> --to <manifest.worker>   # 触发 multica 跑 worker 半
  引擎置 status=in_progress
  worker（executor skill·worker 半）：
    读 issue + 设计文档全文 → 从集成分支切 → 测试先行 → 只 import 契约
    → PR(base=集成分支) → 过 CI → 写结构化完成报告
gate:
  worker 终态 → 引擎置 status=in_review
  reviewer = manifest.reviewer 或 池中任一 ≠ worker 的成员
  multica issue assign <id> --to <reviewer>          # 触发 multica 跑 verifier 半
  （引擎可 issue comment add 一句 "REVIEW PASS for in_review diff"，留档）
  reviewer（executor skill·verifier 半）：
    只读共享态 → diff×口径×红线 → 验收↔test 强制映射 → 独立复跑测试
    → 写结构化裁决 metadata.review_verdict={approve|changes, evidence}
  引擎读校验过的裁决：
    approve → status=done（解锁下游）
    changes → assign 回 worker / status=in_progress
```

**结构性闸不变量（D8）**：一个节点只能经 `in_review→done`，且这一步**只由 reviewer run 驱动**；worker 永不能把自己置 done。引擎信的是**独立 reviewer 的裁决**（reviewer≠worker、复跑过测试、留档），不是 worker 自述——这把方法论 §6/§7 的"worker 回报不可全信"用结构落地。

> **reviewer skill 必须强制独立复跑测试**，否则闸变摆设。该约束写进 executor skill 的 verifier 半。

## 4. 端到端执行流程

| 阶段 | 谁 | 动作 | 读 | 产出 |
|---|---|---|---|---|
| **0 装备**（每队一次） | 你 | 预建 squad(leader+members)；`agent skills add` 给 leader 装本 skill、给 members 装 executor skill；项目配置写入 squad `instructions` | — | 配置好的 squad |
| **A 打地基**（Wave 0，串行） | leader/worker | 产地基四件套（共享契约代码+底座+骨架+CI 闸/假件），测试冻结（方法论 §3/§4） | 设计文档、CLAUDE.md、方法论 | 提交的契约代码 + CI；可作根节点 M0 |
| **B 拆卡+写 manifest** | leader | 两级拆解到卡级 issue；`issue create --status todo`（无 assignee）+ 锚定 body；写 manifest | 设计文档、契约 | N 个 issue(todo) + manifest |
| **C 校验+编译** | leader/引擎 | `lint` manifest → 单向编译 `metadata set`（blocked_by/旋钮） | manifest | 各 issue metadata |
| **D 引擎自治执行** | 固定引擎 | §3.4 主循环 + §3.5 节点循环，跑到 ALL_DONE 或带失败集退出 | issue list/runs、git diff、CI | status 流转、PR 合并、runs 留档、digest |
| **E 爆发式介入** | leader | 看 digest + 失败 issue 的 runs/run-messages → 改 body/拆 sub-issue/补卡/改 manifest → 回 C/D 重跑（status 持久续跑） | digest、runs | 修订后的 manifest/issues；`squad activity` 决策留档 |

循环 D↔E 直到全 done。

## 6. 为什么不套用 harness Workflow 工具（只借魂）

| 维度 | 独立 Python runner（采用） | harness Workflow 工具（不采用） |
|---|---|---|
| 编排的 agent 群体 | **multica agents**（worker+reviewer） | harness 子 agent |
| 真实工作/留档在哪 | **multica `issue runs`** | harness 会话 jsonl |
| 直调 multica CLI | ✅ subprocess | ❌ JS body 禁 shell-out，须套无用 driver 子 agent |
| resume | issue status 持久 → **跨会话续** | resumeFromRunId，仅本会话 |
| 进度 UI | **multica issue board/runs 本身就是** | /workflows（第二套冗余视图） |

做真实工作的是 multica agent（为留档），而 Workflow 的价值是编排 harness 子 agent——runtime 错配。**但其执行语义值得借**：连续 frontier、分支隔离失败、结构化校验、并发封顶、幂等重入、codegen 逃生舱（§3.3/§3.4）。**不跨的线**：永不生成任意引擎逻辑（即便借鉴 Workflow，它生成的也只是薄 DSL over 固定原语）。

## 7. 防跑偏映射（方法论 §2/§7 → multica 落地）

- **接口层（契约即代码）**：worker 只 import 冻结契约；`lint` 不校验业务但保证图合法；executor skill 强制"只 import 契约"。
- **边界层（CI 闸）**：worker 必过 CI 才进评审。
- **语义层（独立 reviewer）**：§3.5 的结构性闸；reviewer≠worker、复跑测试、APPROVE/REQUEST_CHANGES。
- **生成物防漂移**：manifest 是数据非逻辑（D3）；`lint` 在派发前挡错；引擎是固定代码。
- **共享 infra 集中改**：worker 若被共享契约/CI/边界扫描 bug 卡住，报 leader 统一修，不在本卡分支擅改共享文件（同方法论 §7）。

## 8. 与 gh 版 skill 的差异对照

| 维度 | gh 版 | multica 版（本文） |
|---|---|---|
| 依赖 DAG | issue `blockedBy`（原生） | `metadata.blocked_by`（KV） |
| 驱动 | `orchestrate-tick` 长轮询 | 固定引擎跑 manifest，爆发式介入 |
| plan 形态 | 散在 issue 上 | 显式 manifest（数据） + 编译进 metadata |
| worker 启动 | orchestrator spawn worktree agent | multica 原生 `issue assign` 成员 agent |
| reviewer 启动 | orchestrator spawn 子 agent | multica 原生 `issue assign`，留档 `issue runs` |
| roster | gh assignee | squad 成员（leader 查 member list） |
| resume | 重 tick 读现态 | issue status 持久，重跑续跑 |

## 9. 非目标

- 不改方法论的"道"（三层防跑偏 / 工单卡 / 七闸语义）。
- 不绕 gate 自动关闭（不做无人闭环）。
- 不自建 multica 的 PR/CI（复用 git PR/CI，multica issue 只当跟踪器+派发器）。
- 不改动 gh 版 skill；不在两 skill 间复制"道"正文。
- 不生成任意可执行引擎逻辑（manifest 仅数据）。

## 10. 待验证（实现第一步先做 pilot，写操作）

1. **leader-as-agent 能力**：leader 作为 multica agent 运行时，能否跑 Python 引擎 + 调 multica CLI（自我感知 squad、派发成员、读 runs）。
2. **worker 产可 gate 的 git 产物**：multica 成员 agent 能否从集成分支切、产出 PR、过 CI——§3.5 的整套闸建立在此之上。

> 两项任一不成立都会改变落地方式，故 spec 实施第一步即用一个真 issue 做最小验证（小、快、可丢弃），结论回流再进正式实现。
