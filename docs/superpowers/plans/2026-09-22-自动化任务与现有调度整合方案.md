# 自动化任务与现有调度整合方案

日期：2026-09-22。状态：用户已于本任务批准实施及 PR/CI/服务器部署，实施中；不替代 v1 概要设计裁决。

输入：附件《自动化任务 API 契约》。附件是需求材料，不是架构裁决。本文回答其功能如何在当前项目落地，特别是与既有会话、调度、授权、工作记录、连接器的整合。

## 1. 判断与边界

【核心判断】值得做。新增自动化任务管理体验和日历型调度，复用现有 ScheduleService、SessionHost、Pi Session、执行收据、工作记录与审批链。

【关键洞察】
- 数据结构：任务是配置资源，触发是调度事实，工作记录是执行观察，Pi Session 是内容事实源。
- 复杂度：保留一个调度配置来源、一个调度器、一条执行链；新入口和已有会话入口操作同一份调度。
- 风险点：双份调度、误重放 unknown、删除会话导致审计消失、任务选择扩大员工能力权限。

【技术方案】先补配置与关联，再扩日历规则和本地能力装配，最后接页面。全部执行与任务数据位于用户端；Manager 只负责既有企业资产与授权，不接收任务 prompt、任务执行结果或会话正文。新代码沿用 Node Agent/Fastify/TypeBox，不照搬通用表格中的“三端 FastAPI”。

不触碰冻结 app/、旧库、Hermes 外部仓；不增加云端调度、消息总线、Executor、第二套 Run/Task 状态机；不承诺电脑关闭或未登录后仍能无人值守运行。

## 3. 唯一数据来源与兼容策略

### 3.1 首版选择：独立任务资源，执行仍绑定会话

一个自动化任务当前绑定一个私聊 Conversation；同一配置期间的触发复用该会话及 Pi Session，延续现有行为。页面明确提示会复用历史上下文。每次新建会话模式不在首版暗中引入。

新增 Agent 本地 `automation_task` 配置表，建议字段：

- UUID id，tenant_id，member_id，name，category。
- current_conversation_id，connector_ids（仅引用），revision，created_at，updated_at，deleted_at。
- tenant/member 由 token 确定；数据库引用与 service 都校验同一所有者。

**不在任务表复制 prompt、schedule、enabled、员工快照或执行正文。**

- prompt/schedule/enabled 从当前 conversation.schedule 读取。
- employee_id 从当前私聊 participant/entry_employee_id 读取。
- employee/connectors 展开信息从已有授权投影和本地可用性视图读取，不复制管理面主数据。
- last_run/last_run_at 来自触发关联及工作记录，next_run_at 来自同一个时间计算函数。
- 任务名称是任务配置，会话标题仍是会话元数据；前端明确区分，不互相同步写入。

Conversation 增加可空 automation_task_id 关联，用于识别当前与历史任务会话；历史会话仍指回任务，但不再具有活动 schedule。该字段不改变 Conversation 主状态或员工快照契约。

### 3.2 既有入口的整合

新任务页和旧会话 API 必须调用同一 scheduling service/repository 写入路径：校验所有者、校验配置、更新 schedule、推进 generation、处理 retry、更新相关任务配置版本。

- 现有普通会话调度不强制转成任务，继续运行。
- 新任务列表聚合独立任务和尚未关联任务的旧调度，以 origin/target_kind 区分；历史会话已关联任务时不再作为第二条任务显示。
- 旧会话以其 conversation UUID 作为稳定兼容 task_id，服务端创建新任务 ID 时检查跨来源冲突；只有旧会话首次接受任务专有元数据编辑时才原子创建关联配置，不做全库批量导入。
- 旧调度没有真实分类时展示 other，没有独立名称时以会话标题展示，不补造历史运行结果。
- 旧群聊调度保持原群聊执行，不被强制压成单员工任务。列表增加 target_kind 和 conversation_id，员工筛选匹配固定 participant；新建自动化任务仍为单员工。旧群聊行不能编辑成单员工目标。
- 现有会话编辑器面对日历配置必须正确展示；未接通日历编辑时只能保留配置并引导任务详情，禁止转成间隔后覆盖。
- 旧入口 schedule:null 表示移除后续调度；已关联任务保留为暂停配置，允许在任务详情重新配置。任务资源 schedule 因而允许空并给出 configuration_required；enable 对缺少配置返回 422，不能凭空恢复旧值。

这是当前 v1 新代码之间的整合，不涉及冻结 MVP 的读取、桥接或迁移。

### 3.3 更新员工、暂停与删除

- 运行中修改员工/连接器/执行指令/调度规则返回 409 task_busy；名称、分类允许修改。暂停和删除仍可执行，只阻止后续触发，当前执行继续，可使用既有会话取消入口显式取消。
- 修改员工不能改写原会话固定 participant。先建立同所有者的新私聊会话并验证授权，再以版本校验原子关闭旧 schedule、切换 current_conversation_id、将唯一调度配置转到新会话。中途失败不启用新调度；清理未挂接空会话。
- 切换后旧会话保留历史结果，不允许通过旧 schedule 编辑入口重新启用这条任务的历史绑定；返回明确冲突及当前任务入口。
- 删除任务是软删除配置并禁用/移除后续调度，不调用现有 deleteConversation，保留 Pi 历史和工作记录。
- 已删除任务的详情默认 404；同所有者可通过独立的历史入口或明确 include_deleted 查询运行记录，enable 返回冲突，不能复活。
- 用户若从聊天页明确删除任务关联会话，按现有删除语义清理会话/内容/工作记录，并在同一数据库事务内失效当前任务绑定、保留不含正文的触发墓碑；不可留下仍会执行的悬空任务。界面提前说明历史内容将删除，结果链接显示已删除。

## 4. 调度扩展与可靠性

继续使用 ScheduleService，增加纯函数 normalizeSchedule / nextOccurrence；列表 next_run_at 与 tick 共用它，避免显示时间和实际触发不一致。

| 产品规则 | 内部实现 |
| --- | --- |
| once | 复用 at + one_shot |
| interval | 复用 interval_seconds + at 锚点，新的任务 API 要求 starts_at |
| daily/weekly/monthly | schedule_json 增加有鉴别字段的日历分支，保存 IANA timezone 与当地时间规则 |

保留旧单次/间隔 schema 及校验；新规则作为显式 schema 分支，不把日历字段传给旧 validateSchedule。事件时间统一 UTC；日历规则中的当地时刻和时区不能丢失。旧 interval 无 at 的实际实现以 epoch 为锚点，保留此行为，不按文档注释擅自改为重启时刻。

月不存在日期固定 skip；夏令时不存在时刻 skip，重复时刻只取较早一次。先验证时间计算方案在当前 Node 环境的能力与依赖情况，再选经过验证的时区计算实现，不手写完整时区引擎。新任务 API 最小间隔采用 300 秒；既有会话 API 已支持 1 秒，不能以全局校验收紧破坏旧配置。

触发去重继续复用持久收据；配置改动不能通过换 key 绕过同一计划时刻的去重。每次预占都必须绑定 captured schedule identity + revision + generation；当前一次性预占已有此保护，重复/日历触发也必须补到同一原子校验路径。暂停、删除、修改与预占竞争时以事务顺序为准：先预占的视为当前执行，先暂停的不能再发出 prompt。

现有 misfire=skip 的真实行为需要保留并精确描述：启动初始化时间水位，默认不追补停机期间触发；运行过程中跨过多个间隔只计算最近一个，不逐条补齐。它并不是“晚了任何时间都不执行”。授权阻塞和已持久化的执行前失败 retry 仍按原规则处理。新日历分支使用同类行为，不新增后台补跑队列。

同一会话正在 prompting 时跳过本次机会；等待审批仍属于执行占用。审批复用既有 ApprovalService，不新增自动批准，也不把任务 active 当成工具写权限。前端显示等待审批/授权阻塞等派生信息，不写进 Conversation 主状态。

## 5. 运行记录整合

新增轻量 `schedule_occurrence` 索引，保存 task/legacy target、conversation、计划 UTC 时刻、schedule identity/generation、receipt 引用、配置版本、开始前阻塞/跳过原因和必要的创建时间。此表是触发证据，不驱动 Pi 执行，不复制输出正文。

- 在 reservePrompt 的同一 SQLite 事务内写入触发关联，避免“已执行但没有任务索引”；结果不确定保留证据。
- 调度提交时通过现有 PromptDeliveryOptions 的 idempotencyKey/logicalMessageId 传递稳定身份。
- 给 work_record 补充可空来源关联，使 host.promptParticipant 创建的工作记录与本次 occurrence 显式对应；普通手工 prompt 留空。优先沿现有命令元数据传递，不新增 runtime 协议。
- 单员工触发通常关联一条工作记录；保留旧群聊时允许关联多条，聚合必须依据已有工作记录结果且不能丢失 unknown/部分失败。
- GET runs 是上述索引、执行收据、工作记录、Pi 历史摘要的读视图。使用现有脱敏 safeText 等能力；不按时间邻近猜测归属，也不把整个会话工作记录当成本次执行。
- 既有历史缺少关联时返回“旧记录未建立任务关联”，不伪造 scheduled_at 或成功状态。
- 不把 receipt.completed 等同于业务 succeeded；终局以工作记录/Pi 观察结果为准。

任务调度状态使用 active/paused/completed；删除另由 deleted_at 表达。failed 从任务配置状态中去掉，展示在 last_run。单次预占后立即禁止重复触发，但不能在执行尚未结束时显示“已完成”；终局/不确定由关联证据派生。暂停优先表达用户意图，completed 表达已消费单次；next_run_at 在无未来触发、暂停、删除时为 null。

运行列表必须容纳 queued/blocked/skipped（调度观察）及 running/succeeded/error/aborted/unknown（由既有工作结果映射），并区分未启动和已启动，不能统一映射 failed 后开放重试。

首版不新增通用 retry API。保留已证明未执行的授权重试；unknown 不自动重放。附件提及的手工重试若保留为产品要求，应单独设计新的 attempt 和副作用确认，不复用原 occurrence 再跑。

## 6. 连接器是实际能力缺口

当前 Manager 有连接器目录、员工绑定及 grants；Agent 快照有 connector_refs，但受控 ResourceLoader 当前主要接技能、Hindsight、企业 RAG MCP。没有证据表明仅保存 notion 就能完成通用 Notion MCP 调用。Manager 的 connector test 也主要是本地配置校验，不能等同外部可连通。

GET /api/agent/connectors 应返回当前成员授权、本地安装/连接就绪且所选员工可用的交集；display_name/status 不应只来自静态预设。不得由前端跨端请求 Manager 目录。

完整实现需要补齐一条共享能力链，而不是在任务模块特制 MCP：

1. Manager 继续持目录、绑定、grant 真相；复用 authorized-config pull，并按最小需要增加非敏感描述投影。任何新增配置/凭据领取契约先做评审。
2. Agent 受控能力层解析连接器实例、有效 grant 与本地安装状态；目录预设 ID 和实际授权实例 ID 必须区分，沿用已有引用映射，不把所有 connector_ref 强改成 UUID。
3. 用已安装 MCP SDK 和 approved adapter 提供 custom tools/Extension；禁止 ambient .mcp.json、任意服务器发现和用户传入命令直执行。
4. connector_ids 是任务使用的连接器集合；空列表表示不装配连接器类工具，不影响既有技能/RAG/记忆策略。它只能收窄员工快照授权，不能扩大；运行时重新核对授权及本地可用性。
5. 凭据按执行作用域注入，不写入任务、响应、普通日志或 Pi 提示词；外部副作用经过已有审批/审计链。
6. 变更集合需要重新装配或失效相关 Session runtime 缓存，防止旧工具继续可用，同时保留原 Pi 历史。绑定任务的手工追问沿用同样受限集合，避免绕开限制。

分步实施可以先交付无连接器任务，但这只是阶段成果；附件所需的非空 MCP 任务要在上述链路完成后才算交付。未就绪项不可显示 enabled 或用假成功兜底。连接器具体实例的凭据方案/受控配置来源仍是小规模验证必须回答的输入，不在此虚构现成领取接口。

## 7. API 对齐

可保留附件 automation-tasks CRUD/action/runs 和 Agent connectors 路径，但这是新契约，须提供 OpenAPI diff，不把附件视为已冻结路径。

- 成功 envelope/page 沿用现有格式，错误统一 application/problem+json。
- 新任务 ID 使用 UUID；既有 schedule_id、连接器业务引用保持兼容，不全局改造 ID。
- 列表 prompt_summary 与详情 prompt 分开；schedule schema 覆盖日历规则、旧配置投影和移除配置后的 null。
- 去掉 category=mine，首版所有记录就是当前成员的；分类包含 other，状态筛选覆盖 completed。
- 新旧调度列表去重后再稳定排序/分页；游标绑定 tenant/member/filter，采用已有 opaque cursor 工具，不将两个分页结果简单拼接。
- ETag 基于任务元数据版本和当前调度 generation 生成；GET/写响应都返回。PATCH/enable/pause/delete 条件写入在事务中校验；版本冲突按项目约定 409，缺失必需条件返回可识别校验错误。重复 action 在版本仍匹配时无副作用，过期版本不能绕过并发保护。
- 创建幂等域为 tenant + member + operation + key；记录请求 fingerprint，同 key 不同 body 返回 409；持久化至少 24 小时且处理中不能过期丢收据。不冒用 prompt 收据存储创建流程。
- 创建涉及会话初始化与本地配置写入，使用稳定预分配 task/conversation ID 和持久创建收据；初始化完成前不激活 schedule。重启只依据证据恢复，失败回滚未挂接资源，不能留下幽灵定时任务。
- 员工切换、软删除、旧入口编辑都需要同样的并发控制与 generation 更新；客户端不能提供 tenant/member 覆盖字段。
- enabled 是调度意图，readiness/block_reason 是可运行条件；身份缺失应展示阻塞，不自动改用户意图。

## 8. 实施顺序与文件范围

### 步骤一：收口契约与小规模验证

产出任务资源 schema、兼容映射、状态推导表、OpenAPI diff；验证日历算法及一个真实受控连接器的授权/连接/审批闭环。确认外部桌面工程是否提供页面，不以它代替本仓前端验收。

涉及 `schedule.ts` 的测试样例、`http` schema、Manager 既有 connector/authorized-config 契约的只读核对。未确定凭据通道前不实现假的 connectors enabled 列表。

### 步骤二：任务资源与现有单次/间隔整合

新增建议落点 `storage/automation-tasks.ts`、`services/automation-tasks.ts`、`http/automation-tasks.ts`；`http/server.ts` 只装配注册，不继续堆业务逻辑。`storage/sqlite.ts` 接入事务与本地增量 DDL；保留旧 v1 数据和 API。

实现任务元数据、兼容列表、同一写入入口、创建幂等、条件更新、员工切换、软删除。阶段验收：旧会话和新任务双向操作只改变一份 schedule，执行仍走原 SessionHost。

### 步骤三：运行关联与调度可靠性

新增 occurrence 索引，修改 `schedule.ts`、`storage/sqlite.ts`、`storage/work-records.ts`、`pi/session-host.ts` 的最小关联面，复用现有 PromptDeliveryOptions。补齐重复调度预占竞态保护与失败恢复证据；提供 runs 读视图。

### 步骤四：日历调度

在 `schedule.ts` 或其相邻纯计算模块中扩展规则；旧 schema 和计算行为不变。next_run_at 与真实 tick 一致。月末、时区、夏令时、停机与授权阻塞验证通过后开放所有五种模式。

### 步骤五：连接器共享能力

补 Agent 能力目录读服务、受控 MCP adapter、任务集合约束及 Session 缓存失效；Manager 修改限定在必要投影/授权契约，仍经 TenantContext/RLS。任务选择不能获得超出员工快照的能力。

### 步骤六：前端和全链路验收

## 9. 必须通过的验证

1. 旧单次、无锚点间隔、群聊调度不退化；新旧入口不会各触发一次。
2. 暂停/删除/编辑与 tick 竞争；旧授权回调不能复活被替换或删除的 schedule。
3. 重启后 accepted/unknown 不盲目重放，执行前授权阻塞恢复只执行一次。
4. 任务创建幂等、初始化失败、员工切换失败不遗留活动 schedule。
5. 不同 tenant、同 tenant 不同成员均不能读写对方任务、runs 或重放创建响应。
6. 五种时间模式，月末 skip、夏令时 gap/fold、日历 next_run_at 与实际触发一致。
7. 任务 pause 不取消当前执行；任务软删除保留历史；显式删除会话不会留下悬空调度。
8. 手工 prompt 不混入定时 runs；群聊多工作记录与任务触发关联明确；receipt completed 不伪装业务成功。
9. 被撤销、未就绪或不属于员工的连接器拒绝使用；未选连接器不装配；换集合后缓存不保留旧工具；输出不泄漏凭据。
10. OpenAPI schema/operation_id/错误格式、Agent 类型检查及相关后端/前端测试通过；真实页面创建—触发—结果—暂停—删除闭环通过。
