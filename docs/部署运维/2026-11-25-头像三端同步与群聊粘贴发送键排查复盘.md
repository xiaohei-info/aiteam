## 2. 问题一：群聊粘贴后发送键变灰

### 2.1 现象与复现

群聊输入框（contentEditable）里粘贴带换行/富文本的内容后，输入框肉眼可见有文字，但右侧发送键保持禁用。

真实浏览器复现脚本：
- `clients/desktop/tests/chat-paste-browser-smoke.mjs`：派发合成 `ClipboardEvent('paste')`（带 `text/plain` + `text/html`），只走组件自己的 `onPaste` 处理器；
- `clients/desktop/tests/chat-paste-real-clipboard.mjs`：写入系统剪贴板（同时带 `text/html` 与 `text/plain`）后用 CDP `Input.dispatchKeyEvent({ commands: ['paste'] })` 触发**真实 Cmd+V**，覆盖「浏览器默认插入 HTML → `onInput` → `extract`」这条路径，单聊 / 群聊各跑一次。

### 2.2 根因链路

1. `clients/desktop/src/components/Chat/MentionInput.tsx` 旧实现 `extract(el)` 只遍历 `el.childNodes` 顶层：
   - `Node.TEXT_NODE` → 累加文本；
   - `HTMLElement && node.dataset.mentionId` → 还原 `@名称`；
   - **其他一律忽略**。
2. 浏览器粘贴多行内容时，`contentEditable` 插入的是结构性节点：`<div>第一行</div><div>第二行</div>`、`<p>`、`<span style=...>`、`<br>`。这些节点既不是文本节点也没有 `mentionId` → `extract()` 返回 `''`。
3. `clients/desktop/src/components/Chat/ChatInputBar.tsx:448-451`：

```ts
const hasComposerContent = (isMentionMode ? !!mentionText.trim() : !!input.trim()) || pendingFiles.length > 0
const isSendDisabled = !hasComposerContent || ...
```

   `mentionText` 为空 → `hasComposerContent` 为假 → 发送键 `disabled`。
4. 历史提交 `3b299305`（"粘贴后发送按钮禁用"）只修了 `handleInput` 里「selection 缺失时提前 return」这一层，`extract` 忽略嵌套节点这条路径没被覆盖，所以问题在「复制富文本」场景下复发。既有回归测试 `clients/desktop/tests/mentionInputPaste.test.ts` 是源码字符串断言，也测不到这条路径。

### 2.3 修复

- 新增 `clients/desktop/src/components/Chat/mentionRichText.ts`：
  - `extractMentionText(root: RichTextNodeLike): { text, mentions }` 递归遍历整棵子树；
  - 文本节点累加；`dataset.mentionId` 节点还原 `@name` 并收集 id；
  - `BLOCK_TAGS`（DIV/P/LI/UL/OL/BLOCKQUOTE/PRE/TR/TABLE/SECTION/ARTICLE）与 `<br>` 触发 `appendBreak()`，只在「已有文本且不以 `\n` 结尾」时补换行，空编辑器的占位 `<br>` 不会产出多余换行。
- `MentionInput.tsx`：
  - `const extract = (el: HTMLDivElement) => extractMentionText(el)`（第 35 行）；
  - 新增 `handlePaste`（第 147 行）：只取 `getData('text/plain')`，`preventDefault()` 后自行插入（`execCommand('insertText')`，失败回退 `createTextNode` + range），插入后立即 `onChange(text, mentions)`，不再依赖后续 input 事件；`contentEditable` 上挂 `onPaste={handlePaste}`（第 306 行）。
  - 只取纯文本是为了避免把外部站点的 DOM/样式/图片拖进编辑器，同时保证 mention 之外的内容都能被提取。

### 2.4 验证

- `clients/desktop/tests/mentionRichText.test.ts`：假节点覆盖顶层文本、单行 `<div>`、多行 div、`<br>` + 嵌套 span + `<p>`、深层嵌套 mention chip、空输入 → 全部通过。
- 真浏览器冒烟三用例（多行、单行、中文富文本）：
  - 修复前（`git checkout 6cc2e112^ -- MentionInput.tsx`）：`sendDisabled` 断言 `true !== false` 失败，截图显示输入框仍是占位符「输入消息...」；
  - 修复后：`editableText` 正确、`sendDisabled:false` 全过。
  - 截图：`clients/desktop/output/chat-paste-smoke/{before,after}-fix/`（已 gitignore）。
- 真实剪贴板冒烟 `chat-paste-real-clipboard.mjs`（同一份脚本，单聊 / 群聊各一次）：

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 单聊（受控 `<textarea>`） | 通过 | 通过 |
| 群聊（`MentionInput` contentEditable） | **断言失败**：粘贴后文本进了 DOM，但发送键仍禁用（`sendDisabled true !== false`） | 通过，`text` 含两行、无富文本样式 |

- desktop 全量：`pnpm test` 909 pass / 0 fail；`npx tsc -b` 通过；`pnpm lint` 6 warnings / 0 errors。

### 2.5 为什么单聊没这个问题、上一次为什么只修了一半

单聊和群聊**确实是两个不同的输入组件**（`ChatInputBar.tsx:116`）：

```ts
const isMentionMode = members !== undefined && members.length > 0
```

- `isMentionMode` 为真（群聊，有成员列表）→ 渲染 `<MentionInput>`（contentEditable，支持 `@` 成员 chip）；
- 否则（单聊）→ 渲染受控 `<textarea value={input} onChange={e => setInput(e.target.value)}>`。

`<textarea>` 的粘贴是浏览器原生行为：直接写 `value` → 触发 `input` → React `onChange` → `setInput`，中间**没有「从 DOM 子树提取文本」这一步**，所以不可能因为嵌套节点丢内容。实测也确认：同一份真实剪贴板脚本，单聊在修复前后都通过。

上一次 `3b299305` 其实修的**也是群聊**（`MentionInput.handleInput` 里 selection 缺失时提前 return），并不是单聊。它只修了「粘贴后 selection 不在输入框 → `onChange` 压根没被调用」这条路径；selection 正常时会继续走到 `extract(el)`，而 `extract` 只看顶层节点，文本仍被丢弃。

为什么当时没发现第二条路径：
1. `3b299305` 补的测试 `mentionInputPaste.test.ts` 是对源码做字符串断言（断言 `if (!sel || !sel.rangeCount) return` 已被删掉），只能证明那个 early return 没了，证明不了提取逻辑正确；
2. 当时新增的 `chat-paste-smoke.html` 只是手工页面，没有自动化脚本去真实派发 paste，所以「发送键仍然灰」这种回归只能靠人肉点；
3. 剪贴板只写**纯文本**时 Chrome 会插入顶层文本节点，旧 `extract` 也能过 —— 必须剪贴板里同时有 `text/html`（例如从网页/Word/微信复制）才会生成嵌套 `<div>/<span>`，从而触发该 bug。

这次的测试改成双保险：提取函数用假节点做单元测试（覆盖各种嵌套结构）+ 真实剪贴板 Cmd+V 做端到端 before/after（单聊、群聊都跑），两条路径都锁住。

## 3. 问题二：头像三端不同步

### 3.1 排查到的完整链路（按数据流）

| 环节 | 事实 | 后果 |
|------|------|------|
| 运营端 | `server/operation_service/catalog_avatar.py` 把模板头像规范化为本地 data URL（jpeg/png/webp/gif，限长） | 模板有头像 |
| 企业端招募 | `server/manager_service/recruit_service.py` 的 `_publish_expert()` / `_publish_solution()` 只建 `employee` 行，**从不写 `employee_avatar`**；对照「复制员工」`employee_copy_service.py:77` 有 `self._avatars.copy(...)` | **断点 A：企业侧从来就没有头像**，`avatar_url` 为 None |
| 企业端存储 | `server/manager_service/employee_avatar_service.py:133` 写库时 `url = f"{self._public_base}/api/manager/employees/{id}/avatar/content"`，`_public_base` 来自 `routes_employee.py` 的 `str(request.base_url).rstrip("/")` | 下发的是**绝对 URL** |
| 企业端取图接口 | `routes_employee.py:218-242` `get_employee_avatar_content(..., claims=Depends(require))`，需 Manager Bearer | `<img src>` **带不了 token** |
| 快照/增量 | `snapshot_service.py:138-145`、`authorized_config_service.py:126-145` 输出 `avatar_url / avatar_version / avatar_sync_version` | 原样透传绝对 URL |
| 用户端存储 | `server/agent_service/src/storage/sqlite.ts` `mergeAvatarProjection` 只做本地覆盖判断，`avatar_url` 直接用 Manager 给的 | Agent 侧没有字节，只有 URL |
| 用户端取图 | `server/agent_service/src/http/server.ts` `GET /api/agent/employees/:id/avatar/content` 只读本机 managed 文件，没有就 404；`manager-client.ts` 也**没有**任何二进制下载能力 | **断点 B：Agent 无法提供企业侧头像字节** |
| web 端渲染 | `web/agent/.../TimelineView.tsx:566-576` 只在 `startsWith("/")` 时传 `avatarUrl`，绝对 URL 直接丢弃；`web/shared/.../digital-employee-avatar.tsx` 也只认同源相对路径与受限 data URL | web 端必然回退插画 |
| desktop 渲染 | `clients/desktop/src/lib/avatarUrl.ts` 对绝对 URL 原样返回；`avatarUtils.tsx` 只对 `/api/agent/employees/:id/avatar/content` 同源路径做 Bearer→objectURL | desktop 拿到 Manager 绝对 URL 时也加载失败（无 token，且跨源） |

**结论**：A 导致企业侧根本没有头像；即使手工上传了头像，B 导致三端都拿不到字节 —— 表现就是「三端不同步，各处画插画」。

### 3.2 修复方案（未改任何北向契约）

1. **企业端：招募时布种模板头像**（关闭断点 A）
   - `server/manager_service/employee_avatar_service.py` 新增 `parse_catalog_avatar_url(value)`：
     - 只接受本地 data URL；jpeg/png/webp 原样；
     - gif 用 Pillow 取首帧转 PNG（`_gif_first_frame_as_png`），因为企业头像只收静态栅格图；
     - 旧模板的 `http(s)` / 相对路径一律返回 `None`（拿不到字节，也不把外部 URL 写进企业库），由管理员在员工配置页上传。
   - `recruit_service.py`：`RecruitService.__init__(..., avatars=None)`；`recruit_expert` 成功后、`apply_solution` 事务提交后调用模块级 `_seed_template_avatars(avatars, ctx, seeds)`：
     - 在发布**事务之外**执行，best-effort，失败只 `logger.warning`，不影响已成功的招募/方案应用；
     - 方案应用只给「本次新建」的员工布种，复用员工保留企业既有头像。
   - `routes_recruit.py` 注入与头像路由同一套 `EmployeeAvatarService`（同一存储根与 public base）。

2. **用户端：Manager 头像统一走本机同源代理**（关闭断点 B）
   - `sqlite.ts` `mergeAvatarProjection`：有 Manager 头像时把 `avatar_url` 统一改写为 `/api/agent/employees/:id/avatar/content`（`avatar_source: "manager"`），本地覆盖（`"local"`）仍最优先；新增 `manager_avatar_cache_path/mime_type/version` 三个投影字段（远端投影里的同名字段一律删除，防伪造），版本一致时复用缓存。
   - `sqlite.ts` 新增 `cacheManagerAvatar(tenantId, memberId, employeeId, data, mimeType, avatarVersion)`：校验 mime/魔数/大小，写 managed data root，在 `BEGIN IMMEDIATE` 事务内重读投影（防止并发本地覆盖被夺回）后更新投影与冻结快照；`managerAvatarSource()` 给出应回源的 `avatar_version`；`readEmployeeAvatar` 回退读缓存文件；`cleanupAvatarRoot` 收集缓存路径。
   - `manager-client.ts` 新增 `getEmployeeAvatar(caller, employeeId)`（走 `/api/manager/employees/:id/avatar/content`，用成员自己的会话 token）。
   - `http/server.ts`：`GET /api/agent/employees/:id/avatar/content` 改为 `readEmployeeAvatar(...) ?? await cacheManagerAvatar(...)`；Manager 鉴权失败/不可达/策略拒绝一律返回 404，不把头像失败升级成页面级错误。

3. **前端：同源 + Bearer 取图**
   - `web/agent/src/lib/employee-avatar.tsx`（新增）：`useEmployeeAvatarSrc` 对受保护路径 `/api/agent/employees/:id/avatar/content` 走 `client.stream(src, { headers: { Accept: "image/*" } })` → blob → `URL.createObjectURL`，卸载时 revoke，失败回退插画；`EmployeeAvatar` 包装 `DigitalEmployeeAvatar`。6 个调用点（TimelineView、RosterPicker、OfficePage ×3、GroupExpertRoster、OrgPage、WorkspacePage）切换过去。
   - `web/shared/src/theme/digital-employee-avatar.tsx` 接受 `blob:` objectURL（外部 `http(s)` 仍回退插画，口径不变）。
   - `web/shared/src/api-client/client.ts` 的 `stream()` 允许调用方覆盖 `Accept`（原先硬写 `text/event-stream`）。
   - desktop 侧无需改动：`protectedEmployeeAvatarTarget` 本来就匹配 `/api/agent/employees/:id/avatar/content`，现在这个 URL 终于有真实字节。

## 6. 过程中的工程经验（避免重复踩坑）

1. `@aiteam/shared` 通过 `dist` 暴露：改 `web/shared/src/**` 后必须 `pnpm --dir web/shared build`，否则 `web/agent`、`web/manager`、`web/operation` 的 vitest/构建仍用旧产物，测试会以奇怪的断言失败误导排查。
2. `DigitalEmployeeAvatar` 的 `imageSrc` 只认同源相对路径与受限 data URL；适配层产出 `blob:` 时必须同步放开，否则「取图成功但仍画插画」。
3. 头像测试 mock 必须用 `vi.hoisted` 固定上下文对象引用：每次渲染返回新对象会让 effect 依赖变化、反复重跑、永远停在 `undefined`。
4. 冒烟脚本要派发**真实 paste 事件**才能复现该 bug；`locator.fill()` / 直接设 `innerText` 都不会产生浏览器插入的 DOM 结构。
5. 合成 `ClipboardEvent` 只覆盖组件自己的 `onPaste`；真实 Cmd+V 会走浏览器默认插入 → `onInput` → `extract`。两条路径都要测。
6. 剪贴板里只放纯文本时，Chrome 插入的是顶层文本节点，旧实现也能通过 —— 复现必须同时写 `text/html`（`navigator.clipboard.write([new ClipboardItem({ 'text/html': ..., 'text/plain': ... })])`）。
7. headless Chrome 里 `navigator.clipboard.writeText` 会抛 `NotAllowedError: Document is not focused`，需要先 `Emulation.setFocusEmulationEnabled({ enabled: true })` 并 `Browser.grantPermissions({ permissions: ['clipboardReadWrite', 'clipboardSanitizedWrite'] })`；真实粘贴用 `Input.dispatchKeyEvent({ commands: ['paste'] })`。
8. 修 UI 缺陷必须有 **before/after 双向证据**：先 `git checkout <commit>^ -- <file>` 临时回退生产代码跑同一脚本确认失败，再恢复确认通过（注意：这些文件已提交时 `git stash` 无内容可存，会假装"回退"却在测新代码）。
