# 存量员工头像补种手册（一次性运维）

> 适用版本：包含 `server/manager_service/avatar_backfill.py` 与「一员工一文件」头像存储（迁移 `0057_employee_avatar_file.sql`）的 Manager 部署。
> 目标读者：企业侧 Manager 运维 / 平台方实施。
> 关联复盘：[`2026-11-25-头像三端同步与群聊粘贴发送键排查复盘.md`](./2026-11-25-头像三端同步与群聊粘贴发送键排查复盘.md)

## 1. 上线步骤（顺序不能换）

1. **部署**本轮代码（Operator + Manager）。
2. **立即**跑运营端模板头像转换脚本，确认 `failed` 为空：
   ```bash
   cd server && export PATH="$PWD/.venv/bin:$PATH"
   python -m operation_service.template_avatar_convert
   ```
   在它跑完之前不要编辑专家模板（模板头像还只存在于 `payload.avatar_url` 里）。
3. **再**跑本手册的员工头像补种脚本：先 `--dry-run`，确认计数合理后正式执行。

顺序原因：补种脚本的头像字节来自 Operator 的**模板头像文件**接口；模板还没转换成文件态时，该接口没有内容，补种只会得到 `skipped_template_no_avatar`。

## 2. 什么时候需要跑

员工头像存放在 Manager 的 `employee_avatar` 表 + 固定路径文件 `avatars/{tenant_id}/{employee_id}.webp`，写入方只有三类：

| 写入方 | 触发方式 |
| --- | --- |
| 企业自建员工上传 | `POST /api/manager/employees/{employee_id}/avatar`（仅 `origin='custom'`） |
| 复制员工 | 复制时自动拷贝来源员工的头像文件 |
| 招募 / 行业方案展开 | 本轮起：新建员工后按**当前**模板头像复制一次 |

因此**本轮之前**已经招募的专家没有头像行：Manager 下发 `avatar_url=None`，企业端与用户端（含桌面端）只能回退首字或插画。本工具把这些员工的模板头像补种为员工自己的头像文件。

## 3. 运行前检查

1. Manager 已部署本轮代码，迁移 `0057_employee_avatar_file.sql` 已执行。
2. 运营端模板头像转换脚本已跑完且无失败项（见 §1）。
3. 环境已配 `OPERATOR_URL`（模板头像来自 Operator）、`DB_URL`（业务连接，走 RLS）、`ADMIN_DB_URL`（控制库，用于枚举 tenant；只处理指定企业时可不配，用 `--tenant`）。
4. `manager_data_root`（默认 `MANAGER_DATA_ROOT` / `.data/manager`）所在磁盘可写。每员工一张 WebP（512 像素，通常几十 KB）。

工具只按 `TenantContext(tenant_id=...)` 走 RLS，`tenant_id` 只来自控制库枚举或 `--tenant`，不跨租户查询。

## 4. 先 dry-run

```bash
cd server
export PATH="$PWD/.venv/bin:$PATH"

python -m manager_service.avatar_backfill --dry-run
python -m manager_service.avatar_backfill --tenant <tenant_id> --dry-run   # 只验证某个企业
```

`--dry-run` 会完整走「读员工 → 判断已有头像 → 拉模板头像字节」的链路，只是**不落库**；输出里的 `seeded` 表示「将会写入」的数量。

## 5. 正式运行

```bash
# 全量（按 ADMIN_DB_URL 枚举 tenant，单次上限默认 500，可用 --tenant-limit 调整）
python -m manager_service.avatar_backfill

# 单个 / 多个企业（--tenant 可重复）
python -m manager_service.avatar_backfill --tenant <tenant_a> --tenant <tenant_b>
```

写入的是同源相对路径（`/api/manager/employees/{id}/avatar/content?v={version}`），各端自行拼基址，无需配置对外域名。

## 6. 读输出

命令输出一行 JSON（键名固定，便于接入脚本）：

```json
{"employees": 128, "failed": 0, "seeded": 96, "skipped_archived": 4,
 "skipped_existing": 22, "skipped_no_template": 6, "skipped_template_no_avatar": 0,
 "template_unavailable": 0, "tenants": 3}
```

| 字段 | 含义 |
| --- | --- |
| `tenants` | 本次扫描的租户数 |
| `employees` | 扫描到的员工总数（含归档） |
| `seeded` | 本次写入的头像数（dry-run 时为「将会写入」） |
| `skipped_existing` | 已有头像行，跳过（幂等；管理员手工换过的头像不会被覆盖） |
| `skipped_archived` | 已归档员工，跳过 |
| `skipped_no_template` | 没有 `source_template_id` 的员工（企业自建），跳过 |
| `skipped_template_no_avatar` | 模板本身没有头像（或模板头像还没转换成文件态），跳过 |
| `template_unavailable` | 模板已下架 / 不在本企业发布范围 / Operator 不可达，跳过 |
| `failed` | 写入失败（存储不可写、员工并发消失等） |

退出码：`failed == 0` 返回 `0`，否则返回 `1`。

## 7. 验证

1. Manager 侧：`GET /api/manager/employees` 里该员工带上 `avatar_url`；`GET /api/manager/employees/{id}/avatar/content` 返回 `image/webp` 与 `X-Avatar-Version`。
2. 快照侧：该员工的 `avatar_version` 不再是 `0`。
3. 用户端：Agent 收到新快照后首次打开该员工会话会回源取一次图，之后走本地缓存。
4. 企业端网页：专家卡片与详情弹窗显示图片而不是首字。

## 8. 边界与已知限制

- **只补缺失**：已有头像行的员工一律跳过，不覆盖管理员上传或复制得到的头像。
- **只补模板员工**：`source_template_id` 为空的企业自建员工不在范围内，需要管理员在企业端上传。
- **此前手工换过的员工头像无法恢复**：本轮迁移清掉了旧存储方式（随机文件名）留下的、新代码读不到的头像行；这些员工会被当成「没有头像」重新补种模板头像，原先手工上传的图片不可恢复。
- **按当前模板**：补种的是脚本运行时刻的模板头像；之后模板换头像不会再同步给已有员工（与招募时的口径一致）。
- **模板下架**：`template_unavailable` 计数的员工保持现状，交管理员手工处理。
- **Operator 不可达**：同一模板只重试一次（结果按租户缓存），不会逐员工打 Operator；修好后重跑即可。
- **不做跨租户**：一次运行只处理显式列出的租户或控制库里登记的全部租户。

## 9. 排障

| 现象 | 原因 / 处理 |
| --- | --- |
| `DB_URL is not configured` | 未配业务库连接 |
| `ADMIN_DB_URL is not configured` | 未配控制库连接：补 `ADMIN_DB_URL`，或显式 `--tenant` |
| `OPERATOR_URL is not configured` | 未配 Operator 地址，模板头像无法拉取 |
| `skipped_template_no_avatar` 大量出现 | 运营端模板头像转换脚本还没跑（见 §1），或这些模板本来就没有头像 |
| `template_unavailable` 大量出现 | Operator 不可达、模板被下架、或该企业未发布这些模板 |
| `failed > 0` | 看 Manager 日志里 `avatar backfill failed`（只含 `tenant_id` / `employee_id`，不含头像内容）；多为存储目录权限或员工已被删除 |
