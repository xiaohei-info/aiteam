# 存量员工头像回填手册（一次性运维）

> 适用版本：包含 `server/manager_service/avatar_backfill.py` 的 Manager 部署。
> 目标读者：企业侧 Manager 运维 / 平台方实施。
> 关联复盘：[`2026-11-25-头像三端同步与群聊粘贴发送键排查复盘.md`](./2026-11-25-头像三端同步与群聊粘贴发送键排查复盘.md)

## 1. 什么时候需要跑

员工头像存放在 Manager 的 `employee_avatar` 表，写入方只有三类：

| 写入方 | 触发方式 |
| --- | --- |
| 管理员上传 | `POST /api/manager/employees/{employee_id}/avatar` |
| 复制员工 | 复制时自动拷贝来源头像 |
| 招募 / 行业方案展开 | 本轮起：发布成功后按模板头像布种 |

因此**本轮之前**已经招募的专家没有头像行：Manager 快照继续下发 `avatar_url=None` / `avatar_version=0`，企业端与用户端（含桌面端）都只能回退首字或插画。

本工具把这些存量员工的**模板头像**补写为员工头像。它是幂等的、可重复执行的，不修改任何其它字段，也不触碰已存在的头像。

## 2. 运行前检查

1. Manager 已部署本轮代码（`server/manager_service` 含 `avatar_backfill.py`）。
2. Manager 进程能拉到 Operator 目录，即环境里配了 `OPERATOR_URL`（模板头像来自目录模板）。
3. 数据库连接已配置：`DB_URL`（业务连接，走 RLS）与 `ADMIN_DB_URL`（控制库，用于枚举 tenant）。
4. `manager_data_root`（默认 `MANAGER_DATA_ROOT` / `.data/manager`）所在磁盘可写，剩余空间足够存放头像对象（单张 ≤ 5 MB，通常几十 KB）。

工具只读写本租户数据：每次运行按 `TenantContext(tenant_id=...)` 走 RLS，`tenant_id` 只来自数据库枚举或 `--tenant`。

## 3. 先 dry-run

```bash
cd server
export PATH="$PWD/.venv/bin:$PATH"

python -m manager_service.avatar_backfill --dry-run
```

只想验证某个企业：

```bash
python -m manager_service.avatar_backfill --tenant <tenant_id> --dry-run
```

`--dry-run` 会完整走「读员工 → 拉模板 → 解析头像」的链路，只是**不落库**，输出里的 `seeded` 表示「将会写入」的数量。

## 4. 正式运行

````bash
# 全量（按 ADMIN_DB_URL 枚举 tenant，单次上限默认 500，可用 --tenant-limit 调整）
python -m manager_service.avatar_backfill

# 单个企业
python -m manager_service.avatar_backfill --tenant <tenant_id>

# 多个企业（--tenant 可重复）
python -m manager_service.avatar_backfill --tenant <tenant_a> --tenant <tenant_b>

# Manager 对外基址与请求域名不同时（例如经过反代），显式指定，供 avatar_url 使用
python -m manager_service.avatar_backfill --public-base-url https://manager.example.com
````

不指定 `--public-base-url` 时写入同源相对路径（`/api/manager/employees/{id}/avatar/content`），桌面端/企业端都会自行拼基址，通常无需指定。

## 5. 读输出

命令输出一行 JSON（键名固定，便于接入脚本）：

```json
{"employees": 128, "failed": 0, "seeded": 96, "skipped_archived": 4, "skipped_avatar": 0,
 "skipped_existing": 22, "skipped_no_template": 6, "template_unavailable": 0, "tenants": 3}
```

| 字段 | 含义 |
| --- | --- |
| `tenants` | 本次扫描的租户数 |
| `employees` | 扫描到的员工总数（含归档） |
| `seeded` | 本次写入的头像数（dry-run 时为「将会写入」） |
| `skipped_existing` | 已有头像行，跳过（幂等） |
| `skipped_archived` | 已归档员工，跳过 |
| `skipped_no_template` | 自定义/复制员工（无 `source_template_id`），跳过 |
| `skipped_avatar` | 模板头像不是可用的栅格 data URL（旧 HTTP 地址、相对路径、无法解码），跳过 |
| `template_unavailable` | 模板已下架或不在本企业发布范围（Operator 返回 NotFound / 不可达），跳过 |
| `failed` | 写入失败（存储不可写、员工并发消失等） |

退出码：`failed == 0` 返回 `0`，否则返回 `1`，便于在运维流水线里判断。

## 6. 验证

1. Manager 侧：`GET /api/manager/employees/{employee_id}/avatar` 返回 `version >= 1` 与 `avatar_url`。
2. 快照侧：`GET /api/manager/.../snapshots` 中该员工的 `avatar_version` 不再是 `0`，`avatar_sync_version` 变为 `{version}:avatar-{n}`。
3. 用户端：Agent 收到新快照后，首次打开该员工对话会触发一次 `GET /api/agent/employees/{id}/avatar/content`（本机代理缓存），之后直接走本地文件。
4. 桌面端：企业侧头像显示为图片；企业端人才市场本来就是模板头像，不受影响。

## 7. 边界与已知限制

- **只补缺失**：已有头像行的员工一律跳过，不会覆盖管理员上传或企业自定义头像。
- **只补模板员工**：`source_template_id` 为空的员工（自定义、手工创建）不做任何事。
- **旧模板不留外链**：模板若仍是 `http(s)://` 或相对路径，工具不会把它写进企业库（企业头像接口只服务本企业对象存储），这类员工需要管理员上传，或让运营端把模板改成 data URL 后重跑。
- **模板已下架**：`template_unavailable` 计数的员工保持现状。
- **不回滚字节**：重复执行安全；如需撤销某员工的头像，走管理员接口更新或删除 `employee_avatar` 行的既有流程。
- **不做跨租户**：一次运行只处理显式列出的租户或控制库里登记的全部租户。

## 8. 排障

| 现象 | 原因 / 处理 |
| --- | --- |
| `ADMIN_DB_URL is not configured` | 未配控制库连接：补 `ADMIN_DB_URL`，或显式 `--tenant` 指定企业 |
| `OPERATOR_URL is not configured` | 未配 Operator 地址：模板头像无法拉取，先补配置 |
| `template_unavailable` 大量出现 | Operator 不可达、模板被下架、或该企业未发布这些模板；先查 Operator 目录 |
| `skipped_avatar` 大量出现 | 运营端模板还是旧式 HTTP 头像；在运营端改为上传图片（data URL）后重跑 |
| `failed > 0` | 看 Manager 日志里 `avatar backfill failed`（只含 `tenant_id` / `employee_id`，不含头像内容）；多为存储目录权限或员工已被删除 |
