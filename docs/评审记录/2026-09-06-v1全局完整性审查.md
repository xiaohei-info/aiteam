# AI Team v1 三端全局功能完整性审查

## 审查结论

基线：main `5483218edecc35eb3e199d3985c4b0b4dda587a0`。本轮为只读审查，未修改源码、项目文档、配置、提交或部署。覆盖 Operator、Manager 控制面、知识/记忆/技能/连接器、Agent 与仓内 Web、跨端治理及交付。已对照实际路由、服务、持久化/外部适配器和前端调用，不以 API 数量或单元测试通过作为功能完成证据。

三端已经有真实可用的主链，不是空壳。但按 v1 正式规划，仍有权限控制、业务动作、能力执行、失败恢复和治理传递方面的缺口，不能认定完整 v1 已交付。下面将五份分组报告归并为业务整改项；安全/行为缺陷和纯粹“缺接口”明确区分。

裁决口径：`docs/v1正式版本/技术设计/概要设计/00-架构总纲与裁决索引.md` D1–D24，08-25 Pi-native 的 06/07 修订、08-26 单企业 Manager 修订优先。10/11 内仍有旧多 runtime、Run/Task/Loop、Wave0 状态，不据此要求重建废弃机制。08-21 完整产品交付路线图仅补充未冲突的验收要求。macOS 是已确认的三端复合客户端，可按身份/职责直连相应端；本仓 Web 和仓外 macOS 实现不混为一谈。

下文“概要设计”统一指上述目录。P1 是应先修的权限/关键业务问题；P2 是应补齐的体验、管理或交付问题。不是每项都需要新接口，很多应修既有调用、校验和数据消费。

## 一、优先处理：权限与失效控制

### 1. P1 停用成员仍可新登录及拉取授权配置

页面将 app_user.status 改为 disabled，但密码身份查询不取/不检查状态，授权配置和快照授权也未检查成员状态。新在线登录仍可签发 token；这不是已签发离线 JWT 在有效期内仍有效的问题。

应补统一 active-principal 校验并用于登录、配置/快照和运行凭据签发。依据：概要设计03§9、05 F05/F09/F10。代码：`server/manager_service/repository.py:57–75`、`auth_service.py:147–162`、`authorized_config_service.py:225–259`、`snapshot_service.py:221–241`。

### 2. P1 普通成员能改企业设置、读取未授权员工完整配置

真实路由只验有效 JWT，没有在企业设置写入处验管理角色；同一普通成员可 GET 全量员工配置/persona，而专用 snapshot 接口却返回403。RLS 隔离企业不等于成员授权。

应限定管理写权限，并将完整配置读取限制在管理角色或按员工授权裁剪。依据：概要设计03§9.1/9.6/9.7、05 F16。代码：`server/manager_service/routes_settings.py:42–75`、`settings_service.py:31–63`、`routes_employee.py:99–125`、`employee_config_service.py:57–59`。

### 3. P1 显式关闭知识能力后，默认企业知识仍可被访问

disabled 绑定变成空 knowledge_refs 后，Manager RAG 又回退到默认企业空间；Manager MCP 不校验实际工具限制。因此已明确禁用与从未设置被当成同一状态。合成探针以 tools=[read] 和 disabled 绑定仍能 search/get 文本。

应区分默认许可与显式拒绝，并在 Manager 每个知识操作重新检查能力/工具权限。保持单一企业知识空间，不恢复多知识库产品。依据：概要设计04§6.1.2/6.6、06§7.5。代码：`server/manager_service/rag_mcp.py:331–353,425–435,594–617`。

### 4. P1 只读记忆 lease 没有限制写入、删除权限

Hindsight facade 只检查 bank 和 lease 范围，随后以 Manager 服务凭据转发任意允许的 HTTP method/subpath。只读 recall lease 的合成探针也能转发写入及 bank 删除；没有对真实 bank 执行删除。

应把可执行操作绑定到 lease，在 facade 校验精确操作，并明确策略收紧后的失效机制；破坏性管理操作要单独授权。依据：概要设计04§6.6、06§7.5。代码：`server/manager_service/hindsight_credentials.py:284–308`、`hindsight_facade.py:52–107`、`routes_hindsight.py:125–133`。

### 5. P1 服务身份未绑定到具体企业

服务间认证目前是一个共享 token 的匹配，不返回经过验证的 Manager principal/enterprise scope；Operator 汇总入口直接信任 body 中企业/tenant ID。合成的合法服务 token 可以向另一企业写汇总。

应为每个 Manager 部署建立可验证身份及企业绑定，由身份限定或校验 body 归属。用户 JWT 的非对称验签已有，不是这项缺失。依据：概要设计03§9.1/9.6、05§5。代码：`server/shared/service_token.py:53–88`、`server/operation_service/routes_rollup.py:56–62`、`rollup_service.py:108–111`。

### 6. P1 模型授权收紧后旧 Relay token 不会被撤销

替换 token 时旧 token ID 被覆盖，却没有上游撤销动作；deny-all 也不联系 NewAPI。匹配的 active 缓存行即使已过期仍被复用。

应补 NewAPI token 更新/撤销/续期及可重试的生命周期记录，保留失败撤销的追踪，不只改本地模型可见性。依据：概要设计04§6.7 D18。代码：`server/operation_service/platform_provider_service.py:299–334`、`platform_provider_repository.py:279–298`、`newapi_client.py:99–150`。

## 二、Operator 业务闭环

### 7. P1 企业开通缺少企业到独立 Manager 的映射

开通、重置、通知都使用进程级唯一 manager_url；企业数据和开通返回没有具体 Manager 部署引用。无法从这条业务链按企业找到不同 Manager。

应保存企业与已部署 Manager 地址/服务身份引用的关联，并用于后续开通、重置、通知和用户入户。不是要求自动容器编排。依据：概要设计09§14.3、00 D1/D20。代码：`server/operation_service/dependencies.py:68–78`、`schemas.py:20–51`、`repository.py:20–33`、`catalog_dependencies.py:33–42`。

### 8. P2 运营端四个可见企业操作请求错误

真实前端的 recharge(payment_method)、adjust_quota(quota)、suspend(reason)、close(reason) 全部发向不接受这些字段的 actions 接口，四种请求实测422。导出动作也没有消费返回行生成文件。

应改接已有正确 quota/lifecycle 接口及充值 schema，补实际 route-level 浏览器请求测试和文件下载，不需为错误前端另造同义接口。依据：概要设计00§2.4 的企业治理职责。代码：`web/operation/src/features/accounts/EnterpriseActions.tsx:32–100`、`useAccountsApi.ts:99–102`、`server/operation_service/routes_admin.py:59–64,456–468`。

### 9. P1 配额与企业停用只停留在状态和建议

正确的 Operator quota/lifecycle 请求虽然200，却没有向 Manager 传递策略。Manager 配额只在手动 Evaluate 时计算整个企业，未按 scope/target_ref 评估，只返回通知/节流文字；没有自动通知或限制新招募/新快照的消费者。

应补策略同步、按范围自动评估、通知及新招募/新快照治理；保留软配额，不把它改为每次执行强制联网领配额。依据：概要设计04§6.5.1 D24。代码：`server/operation_service/admin_service.py:129–160,250–271`、`server/manager_service/usage_audit_quota_service.py:163–227`。

### 10. P1 模板隐藏及企业可见范围未在拉取端执行

设置 hidden 后，Manager 服务身份仍能读列表和详情。可见范围只是存储/通知字段，实际 pull 没有按企业过滤；下架已有拦截，不能混同。

应在列表、详情及方案内嵌专家包统一校验企业可见性。依据：概要设计05 F03。代码：`server/operation_service/catalog_service.py:328–339,465–519,575–613`、`routes_catalog.py:179–252`。

### 11. P1 模板固定版本、团队编辑和实例升级没有闭环

已发布模板可直接改内容但仍为version1，按version1再次拉取会得到新内容；方案编辑的 expert_template_ids 与实际优先消费的 expert_bindings 不一致。Manager 的目录通知不形成持久的可升级状态，已有实例只显示已招募。

应建立不可变发布版本和方案专家版本清单，统一团队编辑来源，并提供已安装版本与可用版本的比较/升级提示；不自动覆盖企业个性配置或历史会话。依据：概要设计05 F03/F07/F15、04§6.2.1。代码：`server/operation_service/catalog_service.py:363–406,525–541`、`server/manager_service/routes_catalog_notify.py:35–61`、`recruit_service.py:124–127`。

### 12. P2 平台系统账号管理仍是单管理员种子

生产账号仓储仍由环境变量创建一个内存 system_admin，没有平台用户创建、禁用、角色管理路径。签名密钥持久化已经有，不能误报成密钥也只是内存。

应持久化平台账号/身份并提供受限管理动作，让 system_operator 真正可分配。依据：概要设计03§9.2/9.3、04§6.1。代码：`server/operation_service/auth_service.py:105–119`、`system_repository.py:32–74`。

## 三、Manager 配置与能力闭环

### 13. P2 员工激活、暂停、归档不进入增量同步版本

状态变化不涨配置version，known_versions相同就不返回变化。缓存draft的Agent可能激活后仍显示不可用，缓存active的可能暂停后仍显示ready。新运行凭据另有active检查，因此不是证明暂停后模型还能照常执行。

应增加生命周期/投影版本或等价的增量失效机制。依据：概要设计04§6.2、05 F10/F14。代码：`server/manager_service/migrations/0034_employee_role_title.sql:6–27`、`authorized_config_service.py:83–136`。

### 14. P2 应用新方案会覆盖已有员工授权

方案复用已招募员工时，把新方案选择的成员列表替换原有grant。A已能用的员工，被应用给B后A会失去访问；失败回滚也不恢复复用员工旧授权。

应保存/合并已有授权，或明确要求管理员确认替换；失败时恢复原状态。依据：概要设计05 F06/F07/F14。代码：`server/manager_service/recruit_service.py:264–309,381–448,482–525`、`repository_member.py:196–224`。

### 15. P1 连接器能配置和显示连接成功，但不能作为员工工具执行

连接测试只做本地schema校验，无凭据和外部请求也会写connected；connector_refs进入snapshot后没有Agent执行适配器/凭据消费者。

应先选一个受支持连接器打通授权、凭据、实际连接检查和Agent受控调用，区分配置有效与真正可执行。依据：概要设计04§6.6、06§7.5。代码：`server/manager_service/connector_ops_service.py:34–67`、`connector_probe.py:123–157`、`server/agent_service/src/pi/session-host.ts:708–732`。

### 16. P2 员工记忆设置和保留期没有作用于执行策略

memory-setting保存禁用/retention_days成功，但snapshot读取另一份employee.memory_policy，仍可能默认开启recall/retain；保留期没有进入Hindsight执行/清理路径。

应统一员工记忆策略的事实来源，接到snapshot/lease和实际保留清理。依据：概要设计04§6.6。代码：`server/manager_service/employee_bindings_services.py:274–290`、`snapshot_service.py:128–149,255–261`。

### 17. P2 自定义技能元数据编辑可能清空可执行内容

浏览器PUT不带files/content_hash，服务默认空值覆盖旧包；Agent分发会跳过坏包，readiness却不报告缺少技能。Operator安装的不可变技能包有保护，不受此PUT影响。

应保留包内容或明确分开元数据与包编辑，并让readiness反映实际技能缓存状态。依据：概要设计04§6.6、06§7.3/7.5。代码：`web/manager/src/features/capability/CapabilityPage.tsx:239–252`、`server/manager_service/capability_catalog_service.py:65–80`、`server/agent_service/src/http/server.ts:1502–1510`。

### 18. P2 知识导入中断后可能永久卡住

上传持久化后只交给进程内BackgroundTasks，没有重启后的作业恢复；遗留uploaded/parsing/indexing无法重试或删除。正常异常能标failed，进程中断则不能保证。

应补持久作业恢复/启动对账，识别失联任务、安全重试或标失败，不取消真正运行任务的保护。依据：概要设计05 F08及兼容RAG详设的恢复验收。代码：`server/manager_service/routes_knowledge_intake.py:145–161`、`knowledge_intake_service.py:519–535,577–581,904–914`。

### 19. P2 已暴露的扩展登录和账号界面未完成

find_user查5列却读第6列，OAuth/Passkey成功认证后的正式身份查询会IndexError；WebAuthn RP ID用tenant UUID而非可信域名。Manager Web也未接已有signOut和因子管理。密码登录/首登重置主链已有。

若保留这些扩展能力，应修SQL映射与RP配置并接界面；否则明确不开放，不因这项强推首版必须新增SSO/refresh服务。依据：概要设计03§9.3–9.5。代码：`server/manager_service/repository.py:78–93`、`passkey_service.py:44–58`、`web/manager/src/AppProviders.tsx:103–118`。可选密码有效期策略还需在创建/重置时维护时间戳，避免重置后仍过期。

## 四、Agent 执行与前端

### 20. P1 人工审批只有展示，没有实际审批流程

没有ApprovalRecord、tool_call审批gate、批准/拒绝/继续接口。sandbox和permission_mode确实存在，但不等于逐动作审批。

应接通有副作用工具的审批记录、决定与继续/拒绝流程，绑定参数、快照及幂等；不另造执行内核。依据：概要设计06§7.5/7.8、07§8。代码：`server/agent_service/src/pi/session-host.ts:708–733`、`pi/resources.ts:93–109`、`pi/event-sse.ts:128–134`。

### 21. P1 正常定时任务缺少调用Manager所需的用户凭据

scheduler只构造用户/企业ID，没有accessToken；实际runtime-config请求无Authorization，401后任务变unknown，一次性任务已关闭。普通HTTP prompt不会缺这个token。

应为调度器提供明确授权、可过期的本地执行身份解析，不把密码/service token塞进schedule。依据：概要设计00 D19。代码：`server/agent_service/src/schedule.ts:99–111`、`manager-client.ts:204–213`。

### 22. P1 已装载会话仍无法在Manager短暂离线时继续工作

每次prompt重新创建Session并向Manager拉runtime-config，默认记忆还要取新lease。已有快照和JSONL无法避免这个阻断。

应设计受控、有有效期的已装载运行材料复用，保持凭据最小化和权限边界；不任意换模型或绕过认证。依据：概要设计00 D14、04§6.2/6.3。代码：`server/agent_service/src/pi/session-host.ts:940–991,1142–1183`。

### 23. P1 已接受请求的失败和流式终态不能可靠呈现

202之后若Pi初始化前失败，只有日志/unknown，没有客户端可见的失败终态；serializer丢assistant错误原因，前端可能一直忙或空回复。断流没有完整重连对账，多成员群首个结束事件会提前清空统一busy状态。

应补安全失败反馈、必要错误字段、群整体执行状态及entries恢复机制。依据：概要设计07§8/8.3/8.5。代码：`server/agent_service/src/http/server.ts:1625–1654`、`pi/event-sse.ts:152–172`、`web/agent/src/features/chat/TimelineView.tsx:134–194`。

### 24. P2 普通文档附件上传成功，但模型读不到正文

Markdown等非图片只发送文件名并标记已引用，字节未注入prompt，也无授权附件读取工具；受限workspace读不到附件仓。已有安全下载/图片输入不能替代文档理解。

应提供本地受控附件读取/材料化，或暂时明确存储-only/不支持作为输入，不把上传成功显示成已被模型使用。依据：概要设计07/08附件交互及产品交付Attachment链。代码：`server/agent_service/src/http/server.ts:1619–1647`、`storage/sqlite.ts:251–256`、`pi/session-host.ts:708–733`。

### 25. P2 仓内Agent Web没有接上已经补好的读取能力

消息搜索、真实participants、preview/unread、工作记录及统计后端已有，但web/agent没有消费者，群成员仍根据当前授权/方案估算。这不是再缺一批后端接口，也不能据此判断仓外mac客户端没实现。

应改接现有API，补已读写回、搜索定位/分页、固定roster和工作/统计界面，不再造接口或mock数值。依据：概要设计07/08及当前客户端接入契约。代码：`web/agent/src/features/chat/useChatApi.ts:248–303`、`features/group/GroupPage.tsx:130–143`、`features/workspace/useWorkspaceApi.ts:6–9`。

## 五、治理与交付

### 26. P1 用量正常上报已有，断网后没有自主补传闭环

Agent只在一次执行结束或手工flush时发送，恢复联网/启动无自动排空；Manager接收成功后向Operator失败仅记日志，没有自己的持久投递重试。Node Manager fetch也无明确超时，可能卡在sending。

应补有界重试/恢复触发、Manager持久投递记录和请求超时，不阻塞本地执行。依据：概要设计04§6.5、05 F13/§5.3。代码：`server/agent_service/src/main.ts:57–60`、`usage-flush.ts:10–36`、`server/manager_service/routes_usage_audit_quota.py:127–136`。

### 27. P1 企业统计丢失成员维度

Agent上报member_id，Manager落库映射丢弃，表只保留员工/企业/时间等维度，不能回答哪个成员产生费用。不要把本机已有按成员统计当成企业汇总也具备。

应按已认证身份落成员维度并提供对应统计/预算范围。依据：概要设计04§6.5、10 Phase4。代码：`server/manager_service/usage_audit_quota_service.py:239–254`、`migrations/0007_usage_audit_quota.sql:19–34`、`billing_repository.py:132–237`。

### 28. P2 审计写入、页面和平台汇总没有接通

登录/拒绝访问确实写日志表，但审计页面读另一些表；Agent始终上报audits=[]，Manager→Operator也只有usage汇总。

应统一安全事件的查询投影与脱敏逐级上报，让实际登录/授权拒绝能在管理页面和平台汇总看见，不上传聊天/工具正文。依据：概要设计04§6.5、05 F16。代码：`server/agent_service/src/manager-client.ts:171–174`、`server/manager_service/login_audit.py:48–62`、`audit_repository.py:41–60`、`rollup_reporter.py:53–72`。
