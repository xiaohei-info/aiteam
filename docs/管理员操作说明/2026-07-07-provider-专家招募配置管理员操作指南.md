# Provider 配置与专家招募管理员操作指南

> 面向 Manager 端管理员。本文按照「配置 Provider → 招募专家 → 修改专家 LLM 配置 → Agent 私聊使用」的真实闭环描述，管理员可照文档完成全链路 onboarding。
>
> 所有文案/入口与当前 Manager UI 一致；token/secret 一律使用占位符，不泄露任何真实凭据。

> **关于侧栏入口**：Manager 当前侧栏导航包含「人才市场」「方案目录」等，但 **「Provider 凭据」「已招募专家实例」「成员级授权」尚未注册到侧栏**。请直接通过路径 `/providers`、`/experts`、`/grants` 访问（后续补侧栏 nav 后无需回改本文档）。

---

## 1. 背景：三端分工（必读）

| 端 | 角色 | 负责本操作 |
|----|------|------------|
| **运营端 Operator** | 平台方 | 注册/发布专家模板（含 `default_model`）、行业方案目录 |
| **企业端 Manager** | 企业管理员 | **配置 Provider 凭据与 `supported_models`、招募/应用方案、授权成员、修改专家 LLM 配置** |
| **用户端 Agent** | 用户本机 | pull 已授权专家 → 私聊/群聊使用 |

关键边界：

- 专家模板的「真相」只在 Operator 侧。Manager 从人才市场单向拉取模板，**不改模板真相**。
- `provider_ref` / `supported_models` 是 Manager 租户本地概念，**不具备跨租户可移植性**——Operator 模板只能声明 `default_model`，不能替 Manager 写死 provider。
- Agent 只消费 Manager 下发的已授权专家列表，**不在本地猜测或补齐 provider**。

因此，要让 Agent 私聊能用某一个专家，Manager 必须完成三步：**有 Provider → 招募落地 → 配置完整（model + provider_ref）→ 授权同步**。任一环节缺失，Agent 端都不会展示该专家。

---

## 2. 第一步：配置 Provider 凭据与 supported_models

入口：Manager 左侧导航 **「Provider 凭据」**（路径 `/providers`）。仅 `owner` / `enterprise_admin` 可写。

### 2.1 新增凭据

1. 点击 **「新增凭据」**，进入创建表单。
2. 填写：
   - **Provider Ref**：租户内唯一引用（如 `openai-main`），创建后不可改。RunSpec 与招募匹配均通过此引用关联。
   - **显示名称（可选）**：面向管理员的可读名（如 `OpenAI 主账号`），便于在区分。
   - **Secret（明文，仅本次）**：AI Relay 令牌或直连 provider API key。**⚠️ 服务端加密存储后不再回显**，请妥善保管明文；本界面任何时候都不会再次展示它（红线 D18）。
3. **能力目录（supported_models）**：声明本 Provider 支持的模型列表——这是后续「按 default_model 自动匹配 provider」的基础，**强烈建议创建时一并填写**：
   - 点击 **「＋ 添加模型」**。
   - 每行填写：
     - **模型标识**（必填）：如 `gpt-4o`、`claude-3-5-sonnet`，需与 Operator 发布模板用的 `default_model` **完全一致**（大小写敏感）。
     - **显示名（可选）**：如 `GPT-4o`，UI 缺省时回退到模型标识。
     - **启用**：默认勾选；未启用的模型**不参与自动匹配**，也不会出现在专家配置页的模型下拉中。
   - 可重复「＋ 添加模型」添加多行；逐行 **「移除」** 可删除。
4. 点击 **「创建」**。创建成功后表单收起，列表刷新。

> 完整创建流程对应的 API：`POST /api/manager/provider-credentials`。示例 token 请使用占位符（如 `sk-****`），不要在文档、issue、截图中泄露真实 secret。

### 2.2 查看 / 删除

- 列表展示：Provider Ref、名称、模式、可见性、版本。**不展示、不缓存任何形态的 secret**（D18）。
- 仅写角色可见 **「删除」** 操作列。删除前请确认无专家/运行仍依赖该 provider_ref。

### 2.3 关于端点与模式（mode）

- **relay**（默认）：走 AI Relay 企业级令牌。
- **direct**：直连 provider API key。
- **endpoint**：对应接入端点（非敏感，允许回显）。可在创建表单对应字段填写。

### 2.4 可见性（visibility）

- **tenant**：租户内全员可用（默认）。
- **members**：仅 `allowed_member_ids` 列出的成员可用；选择此项时必须填写成员列表。

## 3. 第二步：从人才市场招募专家

前提：Operator 已注册并**发布**了专家模板（状态 `published`）；Manager 已在 `/providers` 配置好至少一个 Provider。

入口：左侧导航 **「人才市场」**（路径 `/marketplace`）。

1. 人才市场展示本租户**可招募专家模板**列表（由 Manager 单向拉取 Operator 目录）。
2. 点击模板行的 **「招募」**，即可一键落地为租户内的专家实例：
   - 无需手填实例标识（slug）——后端自动生成租户内唯一 slug。
   - 入参仅 `template_id`。
3. 招募成功后顶部出现提示 **「招募成功」**，并提供 **「编辑配置」** 链接，可直接跳转到专家实例配置页。

同样可通过左侧导航 **「方案目录」**（路径 `/solutions`）**「应用方案」**：一次性展开方案内所有专家实例 + 叠加方案级知识/技能引用。

---

## 4. 核心机制：Operator 的 default_model 如何匹配 Manager 的 provider

招募时，后端 `RecruitService` 的 `ProviderResolver` 按如下优先级把专家模板的 `recommended_config` 解析为本租户的 `provider_ref`，结果通过 `provider_match_status` 返回：

| status | 含义 | 发生条件 | manager 需做什么 |
|--------|------|----------|------------------|
| **explicit** | 显式引用，校验通过 | 模板直接带了 `provider_ref`，且本租户存在该 ref | 无需额外动作（请核对引用是否为本租户真实 provider） |
| **matched** | 自动唯一匹配 | 模板仅带 `default_model`，本租户**恰好 1 个 provider** 在 `supported_models` 中启用该 model | 无需额外动作，employee 已自动带 `model` + `provider_ref` |
| **ambiguous** | 多匹配 | 模板仅带 `default_model`，本租户**多个 provider** 都启用该 model | 招募仍会创建 employee（`provider_ref` 为空），**需管理员到专家实例手动选一个 provider** |
| **none** | 无匹配 | 模板无 `provider_ref` 且无 `default_model`，或有 model 但本租户**无 provider 启用它** | 招募仍会创建 employee（`provider_ref` 为空），**需管理员到专家实例配置 provider + model** |

> 两条路径（「招募专家」与「应用方案」）共用同一个 resolver，匹配口径一致，不会出现同模板不同结果。

## 5. 第三步：招募后查看 / 修改专家的 provider / model / LLM 配置

入口：左侧导航进入 **「已招募专家实例」**（路径 `/experts`），展示本租户全部已招募专家。

### 5.1 专家实例列表

列含义：名称、slug、状态、Provider 引用、模型、配置状态。

- **配置状态**徽章：
  - **「已配置」**：`model` 与 `provider_ref` 齐全。
  - **「待配置」**：任一缺失（此时 Agent 私聊不会展示该专家，见第 7 节）。

### 5.2 编辑配置（EmployeeConfigDrawer）

点击行末 **「编辑配置」**，打开详情/配置抽屉。可修改：

- **提示词 / 人设**：`display_name`、`persona`。
- **模型配置**（核心）：
  1. 先在下拉 **「Provider 引用」** 中选择本租户 provider（来源即第 2 步配置的 Provider 凭据列表）。
  2. **模型**下拉随之联动：仅展示所选 provider 的 `supported_models` 中**启用**的模型。V1 **不支持手输入模型**，必须从目录中选择（避免落到未验证的 provider/model 组合）。
     - 未选 Provider 前，模型下拉禁用，提示 **「请先选择 Provider」**。
     - 切换 Provider 时，若当前 model 不在新 provider 目录内，自动清空。
     - 若 provider 已选但目录无启用模型，提示 **「该 Provider 未配置可用模型」**（请回第 2 步补充 `supported_models`）。
  - **思考深度**：`none` / `basic` / `deep`。
- **运行时**：`runtime_binding`、`timeout_seconds`（正数）。

保存调用 `PUT /api/manager/employees/{employee_id}`，仅覆盖被编辑字段，**保全** `tools` / `skills` / `knowledge_refs` 等未触达配置；服务端托管字段（employee_id / version / status 等）不会被回写。

> 提示：`Provider 引用`与`模型`两栏全部有值，是将专家从「待配置」翻转为「已配置」、进而被 Agent 私聊可见的**唯一**方式。

---

## 6. 第四步：授权成员使用专家（并触发 Agent sync）

招募/应用方案时可选择「招募即绑定授权」（部门级 / 成员级）；也可后续在左侧导航 **「成员级授权」**（路径 `/grants`）单独创建 `member_grant`（`resource_type=expert`，`resource_id=<employee_id>`）。

Agent 用户登录本机后，会执行 `POST /api/agent/grants/sync` 主动 pull 增量授权：

- `ok === true` 且 `upserted >= 1`：授权已同步到本地 roster。
- 同步失败不阻断本地离线工作（保留旧本地投影），但 roster 顶部会出现 Manager 端指向的错误提示。

---

## 7. Agent 私聊为什么只展示「已授权且配置完整的专家」

Agent 私聊点击 **「＋ 新建对话」** 会弹出专家选择弹层（RosterPicker），其过滤规则：

1. **已授权**：只展示 Manager 下发且经 `grants/sync` 同步到本地的专家（未授权的不会出现）。
2. **配置完整**（防呆）：`model_policy.model` 与 `model_policy.provider_ref` 齐全才可选；缺失则显示 **「待 Manager 配置」** 并禁用按钮。Agent 端**不会**在本地推断 provider。
3. **未 revoke**：已撤销授权的专家被过滤。

因此，若某专家在 Agent 私聊中**看不到**或**显示「待 Manager 配置」**，请按顺序排查：
- 管理员是否已在 Manager 完成「已配置」？（第 5 步）
- 是否已创建 `member_grant` 授权该成员/部门？（第 6 步）
- Agent sync 是否成功？

## 8. 常见错误排查

| 现象 | 大概率原因 | 处理 |
|------|-----------|------|
| 招募后专家实例「待配置」，Agent 私聊看不到 | 无 Provider，或 Provider 没配 `supported_models` | 到 `/providers` 补配能力目录，再到 `/experts` 手动选 provider/model |
| 模型下拉为空，「该 Provider 未配置可用模型」 | Provider 的 `supported_models` 为空，或对应 model 未启用 | 回 `/providers` 编辑该 Provider，添加并启用模型（可咨询运营端模板用的 `default_model` 标识） |
| 想选的 model 不在下拉里 | model 标识与模板 `default_model` 不一致（大小写/拼写），或未勾选「启用」 | 核对 Operator 发布模板用的 `default_model`，修正 Provider 能力目录 |
| 切换 provider 后 model 被清空 | 新 provider 目录不含当前 model（正常联动行为） | 重新从下拉选择属于新 provider 的 model |
| Agent 私聊专家显示「待 Manager 配置」 | employee 缺 `model` 或 `provider_ref` | 到 `/experts` → 「编辑配置」补齐 |
| Agent roster 顶部提示「授权同步失败」 | Manager 端不可达，或 `grants/sync` 失败（如 `/api/manager/grants/authorized-config` 返回 403：`member_id` 与认证主体不一致） | 检查 Manager 服务可达性；确认 sync 请求的 `member_id` 为当前认证主体本人（F10 门禁：主体不一致即 403，不会被误判为通过） |
| 授权创建了但 roster 还没出现 | sync 尚未执行或 `upserted=0` | 触发一次 Agent 端同步；确认 grant 的 `member_ids`/`department_ids` 覆盖该用户 |
| 保存专家配置时报「选择模型前请先选择 Provider」 | 未选 Provider 就试图带 model | 先选 Provider，再选 model（模型目录归属不明的 model 不会被保存） |

## 9. 推荐 onboarding  Checklist

管理员可按下列顺序走通完整闭环：

- [ ] `/providers` 创建 Provider 凭据，**一并填好 `supported_models`**（模型标识与运营端模板 `default_model` 一致，并启用）。
- [ ] `/marketplace` 招募专家模板，确认返回 `provider_match_status` 为 `matched`/`explicit`；若为 `ambiguous`/`none`，进入下一步手动配置。
- [ ] `/experts` 查看实例；对「待配置」专家点「编辑配置」，选 Provider → 选启用模型 → 保存，使其变为「已配置」。
- [ ] `/grants` 创建成员/部门级授权（`resource_type=expert`）。
- [ ] Agent 端 sync → 私聊 roster 出现该专家 → 选择专家创建私聊会话。
