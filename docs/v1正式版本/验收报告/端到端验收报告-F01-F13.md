### 问题1：运营端数据库配置错误 ✅ 已修复

**问题描述**:  
`server/operation_service/dependencies.py` 使用了不存在的 `settings.raw.get("oper_db_url")`

**根本原因**:  
代码使用了不存在的 `settings.raw` 属性，应该直接使用 `settings.admin_db_url`

**修复方案**:  
- 修改 `get_repository()` 函数使用 `settings.admin_db_url`
- 同时修正注释和变量命名

**验证结果**:  
代码修复后，运营端服务可正常启动并连接数据库

**提交**: `19c8c01 fix(operation,shared): 修复数据库配置和迁移脚本问题`

---

### 问题2：迁移脚本硬编码数据库名 ✅ 已修复

**问题描述**:  
`server/operation_service/migrations/0001_enterprise_account.sql` 中硬编码了 `GRANT CONNECT ON DATABASE oper`，但 dev 环境使用 `aiteam_v1` 数据库名

**根本原因**:  
SQL 迁移脚本无法动态获取当前数据库名，导致在不同环境下 GRANT 语句失败

**修复方案**:  
1. 注释掉迁移脚本中硬编码的 `GRANT CONNECT ON DATABASE oper`
2. 在 `apply_migrations` 函数中添加动态 GRANT CONNECT 逻辑：
   - 执行 `SELECT current_database()` 获取当前数据库名
   - 使用 `psycopg.sql.Identifier` 安全拼接 GRANT 语句
   - 幂等授权（GRANT 可重复执行）
3. 同时修复 `operation_service/repository.py` 和 `shared/db/__init__.py` 中的 `apply_migrations`

**验证结果**:  
迁移执行器可以正确授予 `app_rw` 角色对当前数据库的 CONNECT 权限

**提交**: `19c8c01 fix(operation,shared): 修复数据库配置和迁移脚本问题`

### 问题3：tenant_signing_keys 表缺少 version 字段 ✅ 已验证

**问题描述**:  
企业端 `tenant_signing_keys` 表缺少 `version` 字段，导致 `keys.py` 访问该字段时失败

**根本原因分析**:  
- `0001_tenant_base.sql` 创建表时未包含 `version` 字段
- `0009_key_rotation.sql` 通过 `ALTER TABLE ADD COLUMN` 幂等添加该字段
- 如果迁移未正确执行，或数据库是在 0009 添加前创建的，则表中缺少该字段

**迁移逻辑验证**:  
检查 `0009_key_rotation.sql`，确认其逻辑正确且幂等：
```sql
-- version: 密钥版本（用于生成 kid，单调递增）
IF NOT EXISTS (SELECT 1 FROM information_schema.columns
               WHERE table_name='tenant_signing_key' AND column_name='version') THEN
    ALTER TABLE tenant_signing_key ADD COLUMN version integer NOT NULL DEFAULT 1;
END IF;
```

**使用场景**:  
`server/manager_service/keys.py` 在以下场景访问 `version` 字段：
- L37: `_current_row()` 查询当前签发密钥
- L66: `ensure()` 插入新密钥
- L88: `rotate()` 解析当前版本号
- L97: `rotate()` 插入新版本密钥

**修复建议**:  
确保在企业端服务启动时正确执行迁移。当前 `manager_service` 的迁移通过测试中的 `shared.db.apply_migrations` 执行，生产环境需要明确的迁移执行机制。

**后续跟进**: 需要在 Phase 1 中明确 manager_service 的迁移执行时机（建议在服务启动时自动执行，类似 operation_service）

## 四、发现的问题与建议

### 4.1 系统账号初始化机制缺失 🔴 阻塞

**严重性**: 高（阻塞端到端验收）

**问题描述**:
- 运营端的企业开通接口需要平台角色认证
- 但系统没有提供初始化第一个系统管理员的机制
- 导致"鸡生蛋"问题：需要管理员才能创建企业，但没有管理员无法开始

**建议方案**:
1. **迁移脚本 seed 默认账号**（推荐）:
   - 在 `operation_service/migrations/` 中添加 seed 脚本
   - 创建默认 `system_admin` 账号（用户名: `admin`, 初始密码: 强制首次登录重置）
   - 仅在表为空时插入（幂等）

2. **CLI 初始化工具**:
   - 提供 `server/run.py --tier=operation init-admin` 命令
   - 交互式输入用户名/密码创建第一个管理员

3. **环境变量配置**:
   - 支持 `OPERATION_INIT_ADMIN_USER` 和 `OPERATION_INIT_ADMIN_PASSWORD`
   - 服务启动时检查并创建（仅首次）

**影响范围**: F01-F13 全部阻塞

### 4.2 Manager 服务迁移执行机制不明确 🟡 中等

**严重性**: 中（影响生产部署）

**问题描述**:
- `operation_service` 在 `dependencies.py` 的 `get_repository()` 中自动调用 `apply_migrations`
- `manager_service` 的迁移只在测试中执行，服务启动时不会自动执行
- 生产环境部署时，如果忘记手动执行迁移，会导致表结构不完整

**建议方案**:
在 `manager_service` 中添加类似 `operation_service` 的迁移自动执行机制，或明确文档说明迁移执行流程

## 附录B：修复代码示例

### B.1 问题1修复

```python
# server/operation_service/dependencies.py (修复后)
@lru_cache(maxsize=1)
def get_repository() -> EnterpriseRepository:
    """单例企业账号仓储。有 admin_db_url → PostgreSQL；否则内存（dev/测试）。"""
    settings = load_settings("operation")
    # 运营端使用 admin_db_url 作为数据库连接（运营端表是控制面表，直连管理库）
    db_url = settings.admin_db_url

    if db_url:
        # PostgreSQL 实现：自动应用迁移，连管理 DSN。
        admin_url = settings.admin_db_url
        app_rw_password = settings.app_rw_password
        apply_migrations(admin_url, app_rw_password)
        return PgEnterpriseRepository(db_url)

    # 内存实现（dev/测试）。
    return InMemoryEnterpriseRepository()
```

### B.2 问题2修复

```python
# server/operation_service/repository.py 和 server/shared/db/__init__.py (新增逻辑)
def apply_migrations(db_url: str | None, app_rw_password: str | None = None) -> None:
    # ... 执行迁移脚本 ...
    
    # 动态授予 CONNECT 权限（问题2修复：迁移脚本无法硬编码数据库名）
    with conn.cursor() as cur:
        # 获取当前数据库名
        cur.execute("SELECT current_database()")
        db_name = cur.fetchone()[0]
        # 幂等授权：GRANT 可重复执行
        from psycopg import sql as _sql
        
        cur.execute(
            _sql.SQL("GRANT CONNECT ON DATABASE {} TO {}").format(
                _sql.Identifier(db_name), _sql.Identifier(_APP_ROLE)
            )
        )
```
