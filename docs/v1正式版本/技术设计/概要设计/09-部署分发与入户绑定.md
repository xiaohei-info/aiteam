## 14. 部署与运行形态

系统是**云侧两个控制面交付物 + 用户端本地交付物**：

- **运营端 Operator（平台方部署）**：Operation Service + 运营端前端 + oper 库，公网可达。一套，平台方运维。
- **企业端 Manager（会话级 tenant 数据空间）**：Manager Service + 企业端前端 + 当前 TenantContext 数据空间 + 企业共享 Manager RAG/员工个人记忆。一个进程可服务多个企业会话，但每个 JWT/request 只服务一个 tenant，由 Operator 提供受控 Manager 地址与服务身份。
- **用户端 Agent（每用户本机自部署）**：Node Agent Service + 用户端前端 + 进程内 Pi Session/SDK runtime + 本机库；默认仅 localhost。每用户一套。

部署细节：
- **开发（单机模拟三端）**：docker-compose 起 Operator、支持会话级 tenant 的 Manager、Agent 三服务 + oper_db + manager_db + tenant 数据空间 + 用户端本地库 + 用户端 Local Runtime Worker；可用独立 tenant fixtures 验证 RLS/工作区隔离。**不再需要中心 Edge 与中心消息总线**。
- **生产**：Operator 与 Manager 由平台方部署与运维；Agent 提供安装包/镜像由用户本机部署；Operator↔Manager 走云侧服务间调用，Agent→Manager 走用户端主动访问（TLS）。
- **运行时接入配置**：runtime（含 Hermes）由 Node Agent 的进程内 Pi Session/SDK 管理；**不再使用旧 `HERMES_WEBUI_*` 环境变量与 `app/.env`**（旧 WebUI loopback 链已废弃），也不恢复独立 Gateway/Executor/Driver 多 runtime 翻译链。

### 14.1 工程落点裁决：单仓「层优先（`server/` 后端 + `web/` 前端）→ 端」，`app/` 降级为只读参考

> 工程结构的精简口径（目录树 + D15 交付物按端精简）同时收录在常驻指令文件 CLAUDE.md / AGENTS.md §9；本节给出完整裁决与理由，是工程落点的单一事实源。

**裁决**：**单仓库**，顶层按层分——`server/`（后端 Python）+ `web/`（前端 JS/TS），各自再按端分子目录；**不拆前端仓/后端仓双仓**。旧 `app/` 整体冻结为旧架构（单体基座）只读参考实现——**只读不写**，v1 全新重建稳定后再删除。

**理由**：
1. **不拆双仓**：一次端内改动常同时动该端前端 + 同端后端 + 跨端契约（认证/摘要 schema）；双仓会逼出两个 PR、版本对不齐、契约漂移。本团队 trunk-based（master 直推），多仓协调税远大于收益。前后端"各自独立构建/部署"靠目录分层 + 独立流水线即可拿到，**仓库边界 ≠ 部署边界**。
2. **层优先（`server/`+`web/`）而非端优先**：因构建期已按端组装产物（见 §14.2），源码布局不必 1:1 镜像部署单元；层优先让前后端各用各的工具链（`server/` 一套 Python、`web/` 一套 JS），共享代码各归各层（`server/shared`、`web/shared`），更顺手。
3. **不复用 `app/` 作新后端根**：`app/` 是冻结的旧单体契约对照基线（状态机/角色/cursor/timeline 以它为事实参照），v1 重建期作为**只读契约参照**保留（新旧不并跑、不互调，[10](10-重建验证与阶段实施.md)）；新后端用 `server/`，待旧 `app/` 删除后若需要可再改名回 `app/`，届时无冲突、成本极低。

> 工程目录目标态（单仓，层优先）：
> ```text
> <repo-root>/
> ├── server/                # 后端（Python）
> │   ├── operation_service/ # 运营端：企业开通 / 目录治理 / 跨企业汇总（含运营端认证面）
> │   ├── manager_service/   # 企业端：配置 / 授权 / 成员认证（含企业端认证面）
> │   ├── agent_service/     # 用户端 Node：本地会话、Pi Session 与执行（含用户端本地登录）
> │   ├── shared/            # 共享后端包：service_client / auth(验签·鉴权·签发) / 错误模型 / db / schema base
> │   └── run.py             # 控制面启动器：--tier=operation|manager（Agent 使用 Node 入口）
> ├── web/                   # 前端（JS/TS）
> │   ├── operation/         # 运营端前端
> │   ├── manager/           # 企业端前端
> │   ├── agent/             # 用户端前端
> │   └── shared/            # 共享前端包：page-shell / api-client 基类 / timeline-client / role-state / i18n / 设计系统
> ├── deploy/                # 三端 docker-compose / 各端 Dockerfile / 安装包 / ctl.sh
> └── app/                   # 🔒 旧架构单体基座——只读契约参考，v1 重建完成后删除
> ```
>
> **无 `edge_gateway/`**：早期目标态中的 `edge_gateway/` 随"取消中心 Edge"裁决删除；其认证职责下沉为 `server/shared/auth` + 各端服务自带入口中间件。
>
> **命名口径**：后端 Python 包名统一用下划线（`agent_service`），维持"后端模块 ↔ 前端目录 ↔ 接口前缀"三处对齐：`server/agent_service` ↔ `web/agent` ↔ `/api/agent`；口语里的 `agent-service` 即指此目录。
>
> **`app/` 无任何运行期例外**：新服务**不读取 `app/.env`、不调用、不反代、不桥接** `app/` 的任何端点，**不与旧系统并跑或双写**。`app/` 仅作**只读契约对照基线**（状态机/角色/cursor/timeline 口径参照，见 [10](10-重建验证与阶段实施.md)），不参与 v1 运行链。runtime 启动配置由用户端 Node Agent 的 Pi Session/SDK runtime 管理，与旧 `HERMES_WEBUI_*` 口径无关；旧 WebUI loopback 执行链已废弃。多 runtime/Executor/Driver 旧方案不作为当前 v1 实施路径。

### 14.2 统一启动器 + 构建期分端产物

源码单仓共享，但**交付物按端精简**——既要 dev 便利，又要守住"用户端不含控制面代码"的隐私底线：

- **控制面启动器（dev 便利）**：Python 入口 `server/run.py --tier=operation|manager`（或 `APP_TIER` 环境变量）只挂载对应控制面 router/DB/migrations；用户端 Agent 由 Node 入口独立启动。前端各端独立 dev server。
- **构建期分端（生产/分发）**：CI 按端产出**三个精简产物**，各产物只含本端代码 + 对应 `shared`，互不含对方后端/前端。
- **用户端是硬隔离线**：用户端交付物**绝不打包**运营端/企业端的后端代码与前端界面（隐私 + 最小攻击面）。
- **禁止运行时胖产物**：不做"一个含三端全部代码的产物在运行时 `APP_TIER` 切端"——尤其前端不做"一个 bundle 运行时切端"（那会把控制面 UI 下发到用户浏览器）。`--tier` 只用于 dev 与按端构建入口选择，不等于把三端代码塞进同一交付物。

### 14.3 部署分配与入户引导（端之间如何互相找到）

Manager 是按 tenant 请求隔离的企业服务，同一实例可承载多个企业会话。入户链改为：Operator 注册/分配企业 → Manager 按显式 tenant 初始化 → 负责人按企业标识登录 → 用户端 Agent 绑定该 Manager 会话。

1. **运营端开通企业**：Operator 创建企业记录，生成 `enterprise_id` / 兼容 `tenant_id` + 负责人 bootstrap 凭据。
2. **Manager 服务**：Operator/部署系统提供受控 Manager 地址；Manager 的账号、业务数据和 workspace mapping 由 JWT/TenantContext + RLS 按 tenant 隔离，不依赖进程级企业 pin。
3. **Manager 初始化**：Manager 在显式 tenant 请求下创建该 tenant 数据空间、默认角色、默认部门和唯一企业共享知识库 workspace/mapping。
4. **负责人首次登录**：负责人提供企业名称/代码访问 Manager，使用该 tenant 的 bootstrap 登录并强制重置密码；此后凭据仍按 tenant 归属。
5. **用户端首次绑定**：Agent 配置 `MANAGER_URL`；成员登录后完成 Agent↔当前 tenant Manager 绑定（领取 token + 验签材料），同一 JWT 不切换 tenant。
6. **地址变更**：Manager 地址变更通过安装包参数/二维码/配置串/企业通知渠道下发；Agent 持久化 Manager 地址，访问失败按 [05 通信](05-通信架构与跨端契约.md) 降级（已登录/已装载本地继续可用）。

> `tenant_id` 生成规则、企业邀请码/配置串格式、Operator↔Manager 服务身份建立、Agent 验签材料下发留详设；本节定死的是**"Operator 注册企业 → Manager 按 tenant 初始化 → 负责人企业标识登录 → Agent 绑定当前 tenant"**。
