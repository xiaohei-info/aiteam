# AI Team v1 概要设计 · 11 开发实施与并行编排

> **本篇定位**：v1 正式开发的**并行编排计划 + 防跑偏治理 + 每模块工单卡**。回答"如何在最大化并行效率的同时，让每个开发 Agent 死守自己模块的设计口径、不跑偏"。
>
> **架构形态修订（2026-09-07，覆盖 2026-08-26 单企业进程说明）**：Track M 的 Manager 进程可承载多个企业会话；每个 request/JWT/TenantContext 只落一个 tenant，企业 RAG workspace 与 endpoint `instance_id` 持久化并按 tenant 隔离。跨企业目录/治理仍属于 Operator；账号、RLS 与租户授权是 Manager 的业务边界。
> **对应落点**：全仓推进；地基代码已落 `server/shared/contracts/`、`server/tests/`、`.github/workflows/ci.yml`。
> **配套阅读**：[00 总纲](00-架构总纲与裁决索引.md)、[10 重建验证与阶段实施](10-重建验证与阶段实施.md)（Phase 0–4 验收）、仓库根 `CLAUDE.md`/`AGENTS.md`（通用约束）。

## 1. 核心思路

**契约即代码，先冻地基；三端各建 mock 对端并行开发；最后替换 mock 做集成验收。**

防跑偏不靠"提醒看文档"（人/Agent 都会跑偏），而靠三层让跑偏**做不到或当场被拦**：
- **接口层**用代码契约钉死（`server/shared/contracts/`）——偏不了；
- **边界层**用 CI 闸门扫死（`server/tests/boundary/` + `.github/workflows/ci.yml`）——偏了就红；
- **语义层**用独立评审兜底——偏了被打回。

## 2. 三波次编排与依赖

```
Wave 0  地基（串行，1 小组，冻结后放开扇出）—— 所有并行的硬前提
   │
   ├──────────────┬───────────────┬──────────────┬─────────────┐
Wave 1（并行，各 track 对"其它端"用 mock/fake）
 Track M        Track A                         Track O      web/*
 (Manager)      (Agent本地 Pi Session)          (Operation)  (各端对本端OpenAPI)
 M0→M1..M8      A0→A1..A5                       O1..O3       W-shared→W-O/M/A
   │              │               │              │             │
   └──────────────┴───────────────┴──────────────┴─────────────┘
Wave 2  集成验收（替换 mock → 真对端，跑验证矩阵）
```

**并行原理**：三端只经 Wave 0 冻结的窄契约集成 → 每端"对端"先用 mock → M/A/O/前端并行；用户端 runtime 直接复用进程内 Pi SDK，不另设 Gateway/Executor/Driver 线。

**Track 内仍"小地基先行"**：`M0`（租户底座+认证面）先于 M 业务模块；`A0`（本地骨架+本地登录+Pi Session/fake test runtime）先于 A 业务模块。

> 与 [10 §18](10-重建验证与阶段实施.md) Phase 对应：Wave 0 = Phase 1 的 shared 底座+Manager tenant 会话底座+契约冻结；Wave 1 Track M/A = Phase 2；Track O = Phase 4；Wave 2 = 各 Phase 验收口径汇总；原 Track G/Phase 3 多 runtime 计划已取消。

## 3. 防跑偏机制（七道闸，越早越硬）

| # | 闸门 | 落地物（已建/待建） |
|---|---|---|
| 1 | **契约即代码** | `server/shared/contracts/`（已建）：envelope/错误模型、枚举、token claims、TenantContext、运行事件/时间线、快照、授权/投影、脱敏摘要、跨系统 pull。Agent runtime 直接消费 Pi SDK；下游**只 import、禁重定义**。 |
| 2 | **单文档单负责人工单** | 本篇 §4 工单卡：每 Agent 只认一份口径 + D# + 必消费契约 + 红线 + 验收。 |
| 3 | **常驻护栏** | `CLAUDE.md`/`AGENTS.md` 每会话自动加载（设计原则/风险边界/§3.8 不沿用旧代码风格）。 |
| 4 | **小任务粒度** | CLAUDE.md §10.1：任务切到一两文件/半天收口；用 subagent-driven/executing-plans 带检查点。跑着跑着才会偏，不给它跑远的机会。 |
| 5 | **客观 CI 闸门** | `server/tests/boundary/`（已建：旧路径/`HERMES_WEBUI_*`/旧角色/`import app`/`app/.env`）+ `server/tests/contracts/`（已建：枚举/事件集合漂移守卫）+ `.github/workflows/ci.yml`（已建）；待建：OpenAPI 门禁、RLS、parity、隐私（`server/tests/integration/test_verification_matrix.py` 占位）。 |
| 6 | **独立评审闸** | CLAUDE.md §10.4：非实现者 reviewer agent 拿"模块 diff × 负责文档 × CLAUDE.md"逐条核对再合并。CI 抓接口漂移，评审抓语义漂移。 |
| 7 | **完成前独立验证** | CLAUDE.md §10.4 + §7 检查点：必须给测试/接口/parity 证据，"我觉得没问题"不算完成。 |

## 4. 工单卡

```
【模块】<名> 【Wave·Track】<W1·M3> 【唯一负责文档】<NN 篇>

```
