# AI Team v1 概要设计 · 11 开发实施与并行编排

> **本篇定位**：v1 正式开发的**并行编排计划 + 防跑偏治理 + 每模块工单卡**。回答"如何在最大化并行效率的同时，让每个开发 Agent 死守自己模块的设计口径、不跑偏"。
>
> **架构形态修订（2026-08-26）**：Track M 的 Manager 按一企业一部署实施；企业 RAG 只有一个共享 workspace，员工个人记忆按 employee scope 隔离。跨企业并行与汇总属于 Operator/多套 Manager 部署，不是同一 Manager 内的 workspace/租户池；账号密码与独立数据库即为 Manager 企业边界，不需要额外的运行时绑定配置。
> **对应落点**：全仓推进；地基代码已落 `server/shared/contracts/`、`server/tests/`、`.github/workflows/ci.yml`。
> **配套阅读**：[00 总纲](00-架构总纲与裁决索引.md)、[10 重建验证与阶段实施](10-重建验证与阶段实施.md)（Phase 0–4 验收）、仓库根 `CLAUDE.md`/`AGENTS.md`（通用约束）。
> 本篇为 v1 地基级裁决口径，与其它篇冲突时以 [00 §20 裁决表](00-架构总纲与裁决索引.md) 为最终仲裁。

## 1. 核心思路

**契约即代码，先冻地基；三端各建 mock 对端并行开发；最后替换 mock 做集成验收。**

防跑偏不靠"提醒看文档"（人/Agent 都会跑偏），而靠三层让跑偏**做不到或当场被拦**：
- **接口层**用代码契约钉死（`server/shared/contracts/`）——偏不了；
- **边界层**用 CI 闸门扫死（`server/tests/boundary/` + `.github/workflows/ci.yml`）——偏了就红；
- **语义层**用独立评审兜底——偏了被打回。

## 2. 三波次编排与依赖

```
Wave 0  地基（串行，1 小组，冻结后放开扇出）—— 所有并行的硬前提
   │
   ├──────────────┬───────────────┬──────────────┬─────────────┐
Wave 1（并行，各 track 对"其它端"用 mock/fake）
 Track M        Track A         Track G        Track O      web/*
 (Manager)      (Agent本地)     (Gateway)      (Operation)  (各端对本端OpenAPI)
 M0→M1..M8      A0→A1..A5       G1,G2          O1..O3       W-shared→W-O/M/A
   │              │               │              │             │
   └──────────────┴───────────────┴──────────────┴─────────────┘
Wave 2  集成验收（替换 mock → 真对端，跑验证矩阵）
```

**并行原理**：三端只经 Wave 0 冻结的窄契约集成 → 每端"对端"先用 mock → M/A/G/O/前端 五线同时开工。Gateway（06）因 Executor/Driver contract 已冻，可与 Agent 本地主链并行（A 先吃 fake runtime，后期换真 Driver）。

**Track 内仍"小地基先行"**：`M0`（租户底座+认证面）先于 M 业务模块；`A0`（本地骨架+本地登录+Gateway 骨架+fake runtime）先于 A 业务模块。

> 与 [10 §18](10-重建验证与阶段实施.md) Phase 对应：Wave 0 = Phase 1 的 shared 底座+Manager 单企业部署+契约冻结；Wave 1 Track M/A = Phase 2；Track G = Phase 3；Track O = Phase 4；Wave 2 = 各 Phase 验收口径汇总。

```

```
