## 6. 数据架构（系统所有权 + Manager 单企业数据空间 + 配置投影 + 治理摘要上报）

### 6.1 数据所有权原则

每张核心表只能有一个写端。系统所有权分三类：Operator 持多企业平台运营真相；Manager 持当前企业管理真相；Agent 持用户本地会话与执行真相。每个 Manager 部署只服务一个企业；跨企业编排与汇总由 Operator 及多套 Manager 部署承担。

| 数据域 | 写端 | 库（部署位置） |
|---|---|---|
| system_user / system_role / **enterprise_registration** / **owner_credential**（初始/重置，不存可逆密码）/ platform_template / industry_solution / **platform_provider / platform_model / platform_model_rate / platform_provider_tenant_access** / platform_finance / platform_audit / **cross_enterprise_usage_rollup** | 运营端 Operation | oper（中心） |
| manager_deployment / enterprise_binding / service_identity | 企业端 Manager / 部署系统 | 当前企业 Manager 控制库 |
| enterprise / member（成员账号 + 凭据）/ **owner_local_credential**（重置后）/ role / department / employee（专家/员工实例，引用平台 Provider/模型）/ solution_instance / prompt / enterprise knowledge（管理面+源文档，见 §6.6）/ employee_private_memory_policy / skill_binding / connector / **platform_provider_projection / tenant_provider_access_projection**（只读/加密派生投影，见 §6.7）/ **member_grant**（成员级授权）/ billing_setting / enterprise_audit / **enterprise_usage_rollup** | 企业端 Manager | 当前企业 Manager 数据空间（现有 PostgreSQL/RLS 兼容层） |
| conversation / **Pi Session index** / **conversation_participant_session** / **conversation_entry_source** / approval / attachment / artifact / schedule / **loaded_expert_projection** / **loaded_solution_projection** / **frozen_snapshot** / usage_summary_outbox / **local_session_token** | 用户端 Agent | agent（用户本机）；会话正文与工具记录在受控 Pi Session JSONL |

跨端读取走 pull API 或本地投影，**禁止跨端/跨库直写**。

### 6.2.1 行业方案实例与 Participant Session

Operator 只持 `solution_template` 真相；Manager 应用固定版本方案包，在 tenant 内展开 `employee`、`solution_instance`、`member_grant` 和 coordinator 映射。方案模板不携带租户知识 ID、普通专家 Skill 或 member/department ID；企业知识通过 tenant-scoped employee knowledge binding 管理。

Agent 的 `solution_instance` 是只读授权投影。创建一个 group Conversation 时，Agent 为当前投影的 coordinator 和有序 roster 建立一组 `conversation_participant_session`，每个 participant 对应一个持久 Pi Session JSONL。新建另一 Conversation 才创建另一组文件；同一 Conversation 内后续 prompt 始终复用相同 participant Session。

> **认证存储归属**：系统账号在 Operator；企业负责人 bootstrap 来源在 Operator；企业负责人重置后凭据与成员凭据按 tenant 存在 Manager；Agent 只持本会话 token 和本地投影。详见 [03 认证](03-认证与身份设计.md)。

### 6.1.1 Manager PostgreSQL 企业数据边界（可实现裁决）

Manager 仍采用 **PostgreSQL `tenant_id` + Row Level Security (RLS)** 作为当前企业部署的纵深防御和兼容层。Manager 业务数据库不承载多个企业作为目标拓扑；所有企业业务表强制满足：

1. 表必须有 `tenant_id`；内部主键统一使用 UUID，企业可读账号/slug 另设 `enterprise_code` / `enterprise_slug`，禁止把可读账号当 RLS 主键。
2. 主键/唯一键凡涉及业务唯一性必须带 `tenant_id`，例如 `unique(tenant_id, phone)`、`unique(tenant_id, employee_slug)`。
3. 表必须 `ENABLE ROW LEVEL SECURITY`，关键表必须 `FORCE ROW LEVEL SECURITY`。
4. 应用每个请求进入事务前必须 `SET LOCAL app.tenant_id = '<tenant_id>'`。
5. 应用 DB 用户禁止 superuser 与 `BYPASSRLS`。
6. 连接池必须在事务边界设置 `tenant_id`，禁止跨请求复用残留上下文。

示例：

```sql
ALTER TABLE employee ENABLE ROW LEVEL SECURITY;
ALTER TABLE employee FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_employee_isolation ON employee
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

应用侧统一入口：

```text
HTTP request
  -> shared/auth 解析 token
  -> TenantContext(tenant_id, user_id, roles)
  -> TenantDataSession.begin()
  -> SET LOCAL app.tenant_id = TenantContext.tenant_id
  -> 业务 repository 查询
```

演进路径：

| 隔离档位 | 方式 | 适用场景 | 代价 |
|---|---|---|---|
| L1 | 共享库共享表 + `tenant_id` + RLS | 默认 SaaS、多数中小企业 | 成本低，必须严控 RLS/连接池 |
| L2 | 共享库 + schema-per-tenant | 中大客户、需按租户备份/迁移 | migration 与连接路由更复杂 |
| L3 | db-per-tenant | 金融/私有化/超大客户 | 运维成本最高 |

业务代码不感知 L1/L2/L3 差异，只通过 `TenantRouter` 与 `TenantDataSession` 访问租户数据。这样后续把某个 tenant 从 L1 升级到 L2/L3，不需要重写业务模块。

### 6.1.2 Manager 企业共享 RAG（单企业部署裁决）

一个 Manager 部署只服务一个企业。企业共享知识库在 Manager 内只有一个逻辑 workspace，由部署配置固定；`knowledge_space_id` 仅作为既有文档、binding、citation 和数据库迁移的内部兼容键，普通管理员不创建或选择多个知识空间。

```text
Manager deployment = one enterprise
enterprise_knowledge_space_id = enterprise_shared  # 可由既有部署兼容配置覆盖
LightRAG workspace = LIGHTRAG_WORKSPACE             # Manager 启动时固定
```

强制规则：

1. 前端、Agent、业务 API 都不得直接传 LightRAG `workspace`。
2. 只能通过 Manager-owned `ManagerRagService` 访问 LightRAG。
3. Manager 启动时使用该部署配置的固定企业 LightRAG workspace；企业账号库和独立数据库是企业边界，不接受请求切换 workspace。
4. 企业共享文档只索引一次；员工、方案和成员授权是访问控制，不复制文档或建立第二套企业索引。
5. 已存在的旧 `knowledge_space_id` 仅可通过 Manager 的受控兼容映射访问同一企业 workspace；未知键不能创建新 workspace。
6. LightRAG 的 PostgreSQL KV/Vector/DocStatus 等存储仍使用独立数据库/namespace；凭据只存在 Manager，不暴露给 Agent/浏览器。

```text
HTTP/MCP request
  -> Manager enterprise identity + member/employee authorization
  -> ManagerRagService.get(enterprise/shared or known legacy key)
  -> fixed LIGHTRAG_WORKSPACE
  -> LightRAG(workspace, storage=PGKV/PGVector/PGDocStatus/...)
```

员工个人级长期记忆由 Hindsight employee-private bank 承担，与企业共享 LightRAG 文档索引分离。Manager 不把个人记忆写入企业知识库，也不把企业文档复制到每个员工的个人 bank。

### 6.1.3 Manager 非 DB 资源企业边界

企业数据边界不能只停在 PostgreSQL 与 RAG。凡是 Manager 持有或派生的当前企业资源，都必须绑定 `tenant_id` 并经 TenantContext 访问：

| 资源 | 强制隔离口径 |
|---|---|
| 对象存储 | object key 前缀必须为 `tenant_id/knowledge_space_id/...`；下载/删除必须先验 TenantContext 与资源归属 |
| 缓存 | cache key 必须包含 `tenant_id`，禁止用手机号、employee_slug、solution_slug 等非全局唯一字段裸做 key |
| 队列 / outbox | 消息 payload、幂等键、重试记录必须包含 `tenant_id`；consumer 处理前恢复 TenantContext |
| 审计日志 | enterprise_audit 必须带 `tenant_id`、actor、resource_type、resource_id，不记录会话内容 |
| trace / log | 结构化日志必须带 `tenant_id`；跨租户聚合只允许运营级汇总视图读取 |

强约束：任何 Manager repository、cache client、object client、queue producer/consumer 都不得接受调用方手写 tenant 字符串；只能从 TenantContext 读取。详设必须提供跨租户串线回归测试，不只测 DB RLS。

### 6.2 跨端读取策略（pull + 本地投影）

- **新鲜读**：Agent 按需访问 Manager API（如成员登录认证、执行快照生成）；Manager 按需访问 Operator API（如招募专家模板详情、方案包详情）。
- **配置投影（本地优先）**：用户端**周期/触发式 sync** Manager 中"已授权给本账号的专家/方案"，落 `loaded_expert_projection`、`loaded_solution_projection` 本地只读投影；方案投影至少包含有序 employee roster、`coordinator_employee_id`、solution version/config version 和协作说明。对话路径只读本地投影，不每次跨端取配置。Manager 离线时已冻结的 participant sessions 与投影继续工作。
- **执行固化读**：见 §6.3 快照。
- **变更感知**：Manager 可接收 Operator 云侧目录发布通知，也可定期校验目录版本；Agent sync 时带本地投影版本号/etag，Manager 只回增量，未授权条目自动从投影中失效移除。

### 6.3 员工/专家执行快照（EmployeeExecutionSnapshot）

用户端 Agent Service 发起 run 时，不直接读可变配置，而是固化执行快照：

```text
EmployeeExecutionSnapshot
  employee_id / version / snapshot_version / display_name / persona
  model_policy / execution_policy
  tools / signed skill refs / employee knowledge bindings / connector_refs / memory_policy
```

**所有权裁决（D5）**：快照由**用户端 Agent Service 在装载专家/participant Session 前从 Manager 拉取并冻结**，连同 `snapshot_version` 落用户端本地库；每个 Pi Session 全程只引用该快照。方案群聊额外冻结 `solution_instance_id/config_version`、coordinator 和 participant roster，避免长对话期间授权或团队配置漂移。Manager 只需提供按 employee/version 生成快照的接口；已登录且已装载的本地 Pi Sessions 在 Manager 离线期继续工作。

### 6.4 全新建库（不迁移旧数据）

系统所有权分库是**全新重建**：Operator、Manager、Agent 各自从零建库，Manager 租户数据从零建 tenant data space，**不迁移 MVP 单库（macmini 测试库）中的任何存量数据**。旧库只在需要时作为字段/口径的只读参照，不作数据源。
- 详设产出"各系统表 → 写端 → 目标库（部署位置）"的 **schema 设计**（按系统定义，非"现有表→新库"的搬迁映射）。
- 各系统 schema migration（DDL 脚本）按系统独立编写，落在该系统的 migrations 目录；沿用"schema migration 在首次 DB 连接时自动应用"的现有机制（这是建表脚本，非数据迁移）。
- 会话/run 等表本就归用户端**本机库**，全新建库后随用户本地使用自然落地；MVP 演示库中的此类数据不导入、不迁移。
- 如需演示数据，由各系统通过正常业务流程（企业开通、招募专家、发起会话）重新产生，不从旧库拷贝。

### 6.5 治理摘要上报（替代跨端 usage 事件）

**形态变更**：会话内容、执行明细、usage 原始事件与逐 token 明细不上传，治理闭环靠**脱敏聚合摘要逐级上报**：
- **上报内容**：计量（token/成本、run 次数/时长、错误率，按员工/专家/时间聚合）、关键审计事件（专家招募装载、登录、授权变更、越权尝试）。**不含**会话文本、文件、工具输入输出明细。
- **上报路径**：Agent → Manager（成员级聚合，落 `enterprise_usage_rollup`）→ Operator（企业级聚合，落 `cross_enterprise_usage_rollup`）。
- **可靠性**：上报失败本地缓冲后补传，按 `summary_id` 幂等去重；上报是尽力而为，不阻塞本地执行。
- **隐私边界**：脱敏在用户端**上报前**完成；详设产出摘要 schema 与脱敏字段清单。

### 6.5.1 配额与账单控制（本地优先下的取舍）

本地优先意味着 Agent 离线期间不能依赖 Manager/Operator 做逐次执行前强校验。v1 默认采用**软配额 + 事后治理**：

- Manager 从 Operator 同步企业配额/账单策略，并在租户内展示预算、告警和停用策略。
- Agent 在线 sync 时拉取本成员/本设备可用策略与本地提示阈值；离线时已装载专家可继续执行。
- Agent 上报脱敏 usage summary 后，Manager 聚合并执行告警、冻结新增招募、禁止新快照下发等治理动作，再上报 Operator。
- 默认不做"每次 run 前向 Manager 领取 quota lease"，否则 Manager 离线会阻断本地执行，破坏 D14。

企业如选择强成本控制，可在详设中增加**可选硬配额模式**：run 前领取短期 quota lease，Manager 不可达时拒绝新 run。该模式必须在产品上显式标记为"牺牲离线可用性换成本控制"，不能作为默认。

> **三端交互流程清单（原 §6.5.2 F01–F16）已并入 [05 通信架构与跨端契约](05-通信架构与跨端契约.md)**，因其本质是跨端契约面。

### 6.6 外部能力的归属与本地化（消除"企业端 vs 本地"歧义）

知识/记忆/技能/连接器/MCP 既是**企业资产**（在 Manager 管理）又可能在**用户端执行**，二者按"管理面 / 执行面"分开，避免歧义：

| 能力 | 管理面（当前企业 Manager 数据空间持有） | 执行面（用户端 Agent 本地） |
|---|---|---|
| 企业知识库（**LightRAG**） | 一个 Manager 企业部署的共享文档源、索引和访问授权；使用一个固定 workspace，内部兼容键不作为多知识库产品对象 | Agent 通过受控 Manager RAG MCP 使用授权检索/引用；普通会话与检索命中不上传控制面 |
| 员工个人记忆（**Hindsight**） | 员工级记忆策略、保留期和管理/删除授权；每个 employee 独立 bank | Agent 通过 Manager lease/facade 使用 employee-private memory；个人记忆不进入企业共享知识库 |
| 技能（ClawHub/SkillHub/Hermes skills） | Operator 持外部市场只读投影与已校验、固定版本的平台分发包；Manager tenant 持企业已安装目录、版本与绑定策略真相 | pull 已授权技能并**本地安装/执行**；无原生技能机制的 runtime 降级为 MCP 工具暴露 |
| 连接器（Connectors） | 连接器定义、可见性、凭据授权（grant，谁能用） | 运行时**最小权限注入**凭据，本地发起对外部 SaaS 的调用 |
| MCP | MCP server 定义与授权 | 本地启动/连接 MCP，本地调用 |

> **复用裁决**：知识库复用 **LightRAG**、记忆复用 Manager 托管的 **Hindsight Pi Extension/facade**——二者职责互补：LightRAG 管文档语料检索，Hindsight 管经明确策略授权的跨会话记忆。Agent 通过受控 custom tool/Extension 调用，不把能力实现细节暴露为第二套业务状态机。

**裁决与隐私口径**：
- **企业管理面真相在当前企业 Manager 数据空间**，用户端只持 pull 下来的授权配置/只读投影。企业文档由 Manager 保留并经受控 RAG MCP 提供检索/引用；Agent 不复制整套企业知识库。平台技能分发包由 Operator 管理；Manager 只主动拉取 Operator 已开放的固定版本并复制为当前企业的已安装技能，Manager 不直连外部技能市场。
- **流向单一**：企业资产（知识索引、技能包、连接器凭据）**自上而下流到本机**（企业把自己的资产发给自己员工的机器，不违反隐私承诺）；用户的会话/查询内容**绝不上行**。
- **连接器的对外调用是其本职**：连接器按定义调用外部 SaaS（数据出本机到该 SaaS），这是连接器语义本身，**不属于**"会话内容上传企业端/运营端"的禁止项；凭据按 `CLAUDE.md`/`AGENTS.md` §13（横切·安全与隔离）最小注入、用后不留痕。
- **大语料权衡**：企业知识索引保留在 Manager/LightRAG，Agent 只接收受查询结果上限约束的引用；个人记忆由 employee-private Hindsight scope 管理，不与企业知识混存。

### 6.7 平台 Provider、内部 AI Relay 与价格（统一 Provider 真相）

runtime CLI 跑起来必须能访问模型 provider。平台采用内部 NewAPI 作为默认 AI Relay，Operator 统一维护 Provider、发布模型、版本化价格及 tenant access；Manager 不再建立第二套 Provider/模型真相。

| 面 | 归属 | 内容 |
|---|---|---|
| 平台管理面 | Operator oper 库 + 内部 NewAPI | `platform_provider/platform_model/platform_model_rate` 真相；NewAPI 上游 channel；加密管理凭据；为每企业 Manager 部署签发可撤销、限模型/限额的 Relay Token |
| 企业管理面 | 当前企业 Manager 数据空间 | Operator 目录的只读投影；employee 对平台模型的选择；加密企业 access 投影。Manager 只能从 Operator 为当前企业发布的模型中选择，不创建 Provider、不编辑价格 |
| 执行面 | 用户端 Agent（本地） | pull 已授权的 provider/model/pricing 快照；Pi SessionHost 在 Session 作用域最小注入 tenant 受限 Relay Token，用后清理，不写共享 profile |

**裁决（D18，2026-08-24 修订）**：
- **Operator 是 Provider/模型/价格唯一真相端**；专家模板固定平台 Provider/模型。Manager 招募时继承并校验，不能自由输入或另建 Provider。
- **默认且 v1 唯一执行路径为内部 AI Relay（NewAPI）**。真实上游 key/Relay 管理密钥不得离开 Operator/NewAPI 管理面；严禁把全平台共享 key 下发 Manager/Agent。
- 每企业 Manager 部署使用独立、可撤销、可轮换、可限模型/限额的 Relay Token。Manager 仅持加密派生投影，Agent 仅在授权 runtime-config 中取得当前企业 Token。
- 价格由 Operator 自动发现 + 人工覆盖并版本化；模板固定模型、不固定金额。招募与每次 Run 分别解析/冻结当时有效 `pricing_version`，历史成本不得被调价改写。
- Manager 修改员工模型时只能选择 Operator 当前发布且对当前企业可见的模型；变更递增 employee version，新 Run 使用新快照，已开始 Run 不变。
- Agent 本地按冻结价格和 runtime token usage 以 Decimal/micro-USD 计算 cost，只上报脱敏汇总与 pricing version。未知价格必须标为 unknown，不伪装为 0。
- **LLM/Relay 调用不属于会话内容上传控制面的禁止项**；Agent 仍不直连 Operator，只经 Manager 主动拉执行投影。
- Pi Session/EmployeeSnapshot 只引用平台 Provider，不内联任何明文凭据；Relay Token 只在受控 Session 作用域注入。
