# AI Team v1 概要设计 · Pi 事件流与对话页

> **本篇正式修订**：Pi Session entry/event 是 Agent 对话与执行事实源。历史 `AgentRuntimeEvent -> BusinessTimelineEvent` 双层模型不再是生产契约；演进 provenance 见 [`docs/superpowers/specs/2026-08-25-pi-solution-group-chat-addendum.md`](../../../superpowers/specs/2026-08-25-pi-solution-group-chat-addendum.md)。
>
> **对应落点**：`server/agent_service`（Pi SessionHost、SSE、entries、source/index metadata）、`web/agent`（Pi event/session view）。

## 8. 事件流与对话页展示

对话页展示：用户与 Agent 消息、thinking、工具调用/结果、审批、错误、重试、compaction、usage/cost、附件/制品引用和最终结果。

### 8.1 Pi 原生事件链

```text
Pi AgentSessionEvent
  -> Agent Service 脱敏/限长 serializer
  -> Conversation SSE
  -> web/agent TimelineView
```

固定版本的 Pi 事件是实时 wire contract，Agent 只做边界安全处理，不把事件重命名为 Run/Task/Timeline 状态：

```text
agent_start / agent_end / agent_settled
message_start / message_update / message_end
tool_execution_start / tool_execution_update / tool_execution_end
compaction_start / compaction_end
auto_retry_start / auto_retry_end
approval_required
```

serializer 只允许 UI 所需字段，去除 provider secret、路径、Session 文件、workspace、原始请求和 runtime 对象；事件带 `conversation_id`，并在群聊带 `source_employee_id/source_employee_display_name/source_role`。

### 8.2 单聊与群聊的 SSE

```text
private Conversation
  1 participant Pi Session -> 1 subscription -> Conversation SSE

group Conversation
  N participant Pi Sessions -> SSE multiplexer -> 1 Conversation SSE
```

浏览器不直接订阅各员工 Session。群聊每个事件标记实际产生事件的 participant；用户 `@` 的 user message 通过来源索引标记为 human，Agent `mention_employee` 的 user message 标记为 employee，避免把目标 Agent 错当成消息发送者。

### 8.3 持久历史与刷新恢复

Pi Session JSONL 是正文事实源：

- user/assistant/thinking/tool/compaction/message entry 从 Pi Session 读取；
- Conversation SQLite 只保存 Session 索引、participant 映射、授权 snapshot、附件、幂等收据和来源索引；
- `/entries` 使用 Pi entry id，断线后从 entries 恢复持久消息/工具结果；
- transient delta 不承诺断线后逐 token 回放。

群聊 entries 从同一 Conversation 的 participant Sessions 合并，并按稳定 timestamp + entry id 排序。多目标用户消息在各 participant Session 中可能各有一个 user entry，通过 `logical_message_id` 去重；各 Agent 的 assistant/tool entries 保留来源，不互相覆盖。

来源索引最小字段：

```text
conversation_entry_source
  conversation_id / employee_id / pi_entry_id
  logical_message_id
  source_type: human | employee
  source_id / source_display_name
```

该索引不保存消息正文，不构成第二套 Message/Timeline 事实源。

### 8.4 群聊业务时间线

普通用户体验应呈现为：

```text
用户
  @财务专家 请检查毛利率

财务专家
  毛利率下降……
```

协调者调用 `mention_employee` 的底层 tool call/result 可以在 Timeline 中折叠为“协作活动”，避免把同一段回复展示两次；展开调试时仍可查看 tool call、target、tool result 和 source。

### 8.5 状态与幂等

Conversation 持久化主状态仍为：

```text
draft | active | paused | muted | archived
```

展示态（streaming、busy、waiting、reconnecting 等）不写入主状态。Pi 的 `agent_settled`、abort、error 和 provider error 是本次 prompt 的真实终态信号，不转换为独立 Run 枚举。

一个用户 prompt 的 Idempotency-Key 绑定 Conversation、caller、request fingerprint 和目标 participant 集合：

- 无 `@` 目标是 coordinator；
- 单个/多个 `@` 目标是被提及 participant；
- 多目标全部完成才可标记 completed；
- 任一目标崩溃后状态不确定时标记 unknown，不自动重放。

### 8.6 隐私边界

Raw Pi event 只在用户端按脱敏/保留期受控归档（若实现需要），不跨端上传。Manager/Operator 只接收脱敏 usage/audit summary，不接收普通 Conversation、Pi JSONL、群聊正文、Agent 工具输入输出或 child/peer Session 明细。企业知识查询和长期记忆仅按明确授权的 Manager facade/lease 例外传输。
