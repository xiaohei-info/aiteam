# 行业方案「单人 / 组群」类型、群聊编排与运营端 UI 重构 — 需求与设计（草案）

> 状态：**草案，待确认**。本文只做现状核对与方案设计，未开始编码。
> 可视化版本：`2026-11-17-方案单人组群与群聊编排-可视化.html`（UI 示意与数据流图）。
> 口径依据：v1 概要设计 00（D 裁决）、02（API / 错误模型）、04（所有权 / 租户隔离）、05（跨端 pull）、06（Pi Session）；AGENTS.md §2、§3、§8、§10。
> 2026-11-17 已确认（用户拍板）：
> ① 「单人」= 仅 1 位专家、**不建群**；「组群」= ≥2 位专家，必须有群主与编排规则。
> ② 群聊编排规则**复用 `collaboration-markdown-v1`**（与用户端自定义群同格式，成员用 `@{…}` 引用）。
> ③ Skill / MCP：专家级**声明 + 展示 + 可编辑**；运营端草稿、企业端应用前、桌面端人才市场都能看到清单。

## 1. 目标与边界

### 1.1 目标

1. 方案有明确类型：单人方案应用后得到 1 位可直接私聊的专家；组群方案应用后得到一组专家，桌面端可一键建群，群自带编排规则。
2. 运营端发布前，群主、编排规则、成员、所需 skill/MCP 都被**看见并确认**，不是黑盒生成。
3. 企业管理员应用方案前就能看到该方案需要哪些 skill / MCP，缺什么一目了然。
4. 运营端相关页面做到「一眼知道当前状态、下一步是什么、卡在哪、谁该处理」。

### 1.2 非目标

- 不新增执行内核：编排规则只是 `GroupOrchestration` 的 prompt，执行仍由 Agent 的既有编排完成（`server/agent_service/src/groups/orchestration.ts:1-4`）。
- MCP 只做**声明**，不下发连接地址、令牌或任何凭据；连接器由用户本机安装（`server/agent_service/src/connectors.ts:12-13` 明确「Explicit local installation」）。
- 不让桌面端「应用方案」：应用方案是企业管理员在 Manager 的动作，桌面只消费已授权的方案。
- 不做新的状态机或审批流：沿用 `draft → generating → ready_for_review → in_review → approved → published`。
- 不迁移旧数据：已发布方案保持原样，缺省视为 `group` 且无编排规则（见 §6、§3.4 兼容）。

**核对结论**：
1. 「应用方案自动招募群聊成员」企业端**已具备**，缺的是类型、编排规则的落库与下发。

3. MCP 在契约里没有独立字段，但 `required_connectors / optional_connectors` 已能表达「需要哪些外部系统」，Agent 侧的连接器本质就是 MCP（`connectors.ts:1-6` 使用 MCP SDK 的 `StreamableHTTPClientTransport`）。**这是对上面「新增 MCP 声明字段」的收敛：复用现有 connectors 字段，不新增专家模板契约字段**（见 §8 #3）。

## 3. 方案设计

### 3.1 方案类型与草稿内容（Operator）

`GeneratedSolution` 新增（均有默认，旧草稿可读）：

| 字段 | 类型 | 规则 |
|---|---|---|
| `mode`（新） | `"solo" \| "group"` | 缺省时按专家数推断：1 → solo，≥2 → group |
| `orchestration_rules`（新） | `str`，≤8000 | 仅 group 使用；`collaboration-markdown-v1`；成员用 `@{expert_key}` 引用；solo 必须为空 |
| `experts[].skills`（新） | `[{skill_id, version, content_hash, reason}]` | 只能引用 Operator 平台 skill 目录中已发布的固定版本；`reason` 说明为什么需要 |
| `experts[].mcps`（新） | `[{key, display_name, purpose, required}]` | `key` 符合连接器标识（`^[a-z][a-z0-9_-]{0,63}$`，与 `connectors.ts:20` 一致）；仅声明 |

模型校验（`GeneratedSolution._consistent_team`）：
- solo：`len(experts) == 1`，`coordinator_key` 自动为该专家，`orchestration_rules == ""`。
- group：`2 ≤ len(experts) ≤ 12`，`coordinator_key` 必填。
- `orchestration_rules` 里每个 `@{x}` 的 `x` 必须在 `experts[].key` 中；`@{` 不成对则拒绝（与 `validateMemberReferences` 同规则，`orchestration.ts:27-33`）。
- **「必须有规则」不放在模型校验里**，放在 `submit_review` / `approve` / `publish` 闸门（`solution_authoring_service.py:305`）：旧的多专家草稿没有规则也要能读、能编辑，只是不能提交审核。

### 3.2 生成（worker）

- 新建草稿时选择类型（单人 / 组群）并随草稿保存；生成提示词按类型分支：solo 要求只产出 1 位专家；group 要求产出群主建议、编排规则（Markdown，含「谁先发言 / 何时交接 / 何时结束 / 交付物」四段骨架）。
- 生成前把「可选的平台 skill 目录摘要」（id / 版本 / 名称 / 一句话）注入任务提示，模型只能从中选；返回后**宿主**校验每个 skill 引用存在且已发布，不存在的剔除并写一条「系统提示」类 finding，不静默吞掉。
- MCP 由模型按资料推断给出声明（名称、用途、是否必需）；宿主只做格式校验。
- 群主与规则是**建议值**：详情页以「待你确认」状态展示，未确认不能提交审核（§3.5）。

### 3.3 发布到目录（Operator → catalog）

1. 专家：`skills` → 专家模板 `platform_skill_refs`；`mcps` → `required_connectors`（`required=true`）/`optional_connectors`（`required=false`）。不新增专家模板字段。
2. 方案模板 `payload` 新增 `mode`、`orchestration_rules`。**规则里的 `@{expert_key}` 在这一步换成 `@{template_id}`**（`publish_plan` 已确定性产出 `expert_template_ids`，`solution_authoring_service.py:106`），所以 Manager 不需要知道草稿 key。
3. `SolutionPackage` 增加 `mode`、`orchestration_rules`（两个都有默认，`extra="forbid"` 要求下游先升级，见 §6 发布顺序）。

### 3.4 企业端应用方案（Manager）

- `solution_instance` 新增 `mode`、`orchestration_rules`（迁移）。
- `apply_solution`（`recruit_service.py:257`）：
  - solo：只允许 1 位专家，不要求协调员，`coordinator_employee_id` 置空。
  - group：沿用协调员校验；把 `@{template_id}` 换成 `@{employee_id}`（用本次招募 / 已招募员工的映射），再落库。已招募的专家复用其现有 `employee_id`。换算后若仍有无法解析的引用，整单 422 回滚，不留半成品。
- `authorized_config_service.py:156` 的方案投影新增 `mode`、`orchestration_rules`，并附每位专家的 `skills / mcps` 摘要，供 Agent 与桌面显示。
- 应用前预览（企业端人才市场方案详情 / 应用弹窗）：列出专家、群主、**所需 skill 与 MCP**，并标注「企业已具备 / 缺失」。skill 的「已具备」以租户已安装平台 skill 判断；MCP 是用户本机安装的，企业端**无法判断**，只显示「用户需在本机安装」，不做虚假的「已就绪」。
- 「自动招募」：沿用现状，应用即招募全部启用专家；不新增「招募后再确认」状态。

### 3.5 运营端：生成与确认流程

```text
新建草稿(选类型/模型/图片识别/补充说明) → 上传资料 → 开始生成
  → 生成完成（AI 给出：成员、群主建议、编排规则建议、skill/MCP 清单）
  → 运营确认三件事：群主 ✔ / 编排规则 ✔ / skill-MCP 清单 ✔（solo 无前两项）
  → 处理敏感项 → 提交审核 → 管理员审核 → 发布
```

提交审核闸门（后端强制，前端同步展示）：
1. 敏感项全部处理（现状）。
2. group：群主已确认、`orchestration_rules` 非空且引用合法、成员 ≥2。
3. skill 引用全部可解析（目录中已被下架的会阻塞并说明）。

「确认」不另建状态：用草稿上的 `confirmed` 记录（群主 / 规则 / 能力清单各一个时间戳与操作人，写进现有事件表 `solution_review_event`），正文再被编辑则对应确认作废（防止「确认后又被改」）。

### 3.6 桌面端

- 人才市场加页签「专家 | 方案」。方案卡展示：名称、类型徽标（单人 / 组群）、成员头像、标签、所需 skill/MCP 数。
- 方案详情：成员与群主、编排规则（只读渲染）、skill 与 MCP 清单（MCP 标注「需在本机安装」，已安装的显示「已就绪」——Agent 本地可知）、交付要求。
- 「用此方案建群」：仅组群方案显示；单人方案显示「开始私聊」。调用既有 `createConversation`，`solution_instance_id` 带上；**Agent 侧**在 `server.ts:1821-1862` 路径把方案的 `orchestration_rules` 校验后作为 `orchestration` 传给 `createResolvedGroup`（`orchestration.ts` 的 `validateMemberReferences` 复用）。方案没有规则（旧方案）则回退到当前行为，不报错。
- 数据来源：本机已装载的授权方案投影（`GET /api/agent/grants/solutions`）。**不新增 Agent→Manager 目录浏览接口**（待决策 #4）。

### 3.7 UI 重构（专业 UX 视角）

问题诊断（读现有页面得出）：
1. 列表：只有标题可点；状态徽标与「下一步」割裂；一行里「继续生成 / 取消 / 删除」混在一个 ⋯ 菜单，**主操作与危险操作同级**。
2. 详情：从上到下堆 资料 / 敏感项 / 正文 / 操作记录 四张卡，用 6+ 条 Banner 说明状态；用户要自己拼出「现在该做什么」。提交审核按钮禁用原因只在 tooltip 里（触屏不可见）。
3. 正文编辑是整页「编辑 / 保存 / 取消」模式，编辑时锁住其它所有操作（`isLocked`），长文档体验差；新增的群主 / 编排 / skill-MCP 若继续堆在同一页会更糟。
4. 错误直接显示后端英文 detail。

重构原则：
- **一个状态一个主操作**：页头只有一个主按钮，文案随状态变化（上传资料 / 开始生成 / 处理敏感项 / 提交审核 / 审核 / 发布）；其余收进「更多」，危险操作单独分组并二次确认。
- **步骤条**：资料 → 生成 → 确认 → 审核 → 发布，当前步骤高亮，阻塞项直接写在步骤下（「还差 2 项敏感项」「群主未确认」），用文字而不是 tooltip。
- **详情改为工作台**：左侧主区分节（概览 / 团队与群聊编排 / 专家 / 能力清单 / 敏感项），每节**就地编辑**，不再整页编辑模式；右侧固定侧栏：发布清单（逐条 ✔/✖）、资料、操作记录（可折叠）。
- **列表**：状态分段筛选带计数；整行可点；行内显示「状态 + 下一步 + 阻塞原因」；类型徽标（单人 / 组群）；空态 / 加载 / 错误三态齐全。
- **编排规则编辑器**：带「插入成员」按钮（@ 引用）、引用即时校验、预览把 `@{key}` 渲染成成员头像与名字。
- **一致性与可访问性**：沿用 `@astryxdesign/core` 组件与主题，不新增 UI 依赖；键盘可达；状态不只靠颜色；错误信息中文化（映射表集中在 `labels.ts`）。
- 企业端：应用方案弹窗按同样的信息结构（成员 / 群主 / 规则 / skill-MCP 清单 / 模型选择）重排；桌面端人才市场遵循桌面现有设计规范（`clients/desktop/docs`），不照搬运营端样式。

**发布顺序**（因 `SolutionPackage.extra="forbid"`）：
1. Manager 先升级（能接受并忽略/落库新字段）；
2. 再升级 Operator（开始产出新字段）；
3. 最后发布 Agent 与桌面。
旧 Operator → 新 Manager、新 Manager → 旧 Agent 都要保持可用（新字段全部可缺省）。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 模型生成的编排规则引用了不存在的成员 | 宿主校验 `@{key}`；不合法则任务 `schema_invalid`，与现有生成失败通道一致；人工编辑时即时校验 |
| 模型「编造」skill | 只允许从注入的目录摘要中选；宿主校验存在与已发布；剔除项记 finding |
| 规则里 key→模板 ID→员工 ID 两次换算出错 | 换算是纯函数，Operator 发布期与 Manager 应用期各一份单测；Manager 换算失败整单回滚 |
| 已发布旧方案没有类型 / 规则 | 缺省视为 group、无规则；Agent 回退旧行为；运营端可重新生成发布新版本，不改历史 |
| 「确认」后又被编辑 | 编辑相关字段即作废对应确认并提示 |
| MCP「已就绪」误导 | 企业端不显示就绪状态；桌面仅根据本机连接器安装情况显示 |
| UI 重构范围过大 | 严格限定在列表 / 新建 / 详情工作台 / 企业端应用弹窗；沿用组件库；分批合入，每批保留并更新现有 44 条前端用例 |

## 10. 修订（2026-11-17）：skill / MCP 改为 Agent 能力，不再强绑定

**用户决定**：skill 与 MCP 属于 Agent 能力，不在专家和方案上强绑定；使用方案时若需要，在对话中提示用户，询问是否安装，同意后由 Agent 执行安装并加载。

### 10.1 已决定
| 项 | 结论 |
|---|---|
| 方案上是否保留 | 保留**非强制的推荐能力**（`SolutionPackage.recommended_capabilities`，kind=skill/mcp，ref，显示名，用途）。只是线索：不进闸门、不绑定专家、不参与授权 |
| 安装来源 | 平台目录 + 用户手动指定来源 |
| 授权粒度 | 可选「以后自动安装同类能力」 |

### 10.2 运营端（已实现）
- 去掉「能力清单」确认闸门；`confirm` 只剩 `coordinator`、`rules`。
- 发布不再写专家模板的 `platform_skill_refs` / `required_connectors` / `optional_connectors`；各专家声明合并去重成方案级 `recommended_capabilities`。
- 草稿里 `GeneratedExpert.skills/mcps` 保留，仅作生成时的推荐来源。
- Manager 不需要翻译 skill/MCP；只需透传 `recommended_capabilities`（`SolutionPackage` 为 `extra=forbid`，发布顺序仍是 Manager → Operator → Agent）。

### 10.3 Agent 端（待实现，开工前需确认的防护）
安装 skill / MCP 等于执行第三方代码，下面是对所选「手动指定来源」与「自动安装」的建议防护：
1. **手动指定来源每次都要明确确认**，并展示来源地址与将获得的权限；「以后自动安装」只对**平台目录来源**生效，不对手动来源生效。
2. 自动安装的记忆项存本机，可在设置中查看与撤销；方案推荐清单不能自行触发安装，必须由对话中的实际需求触发。
3. 安装、加载走现有 Pi Session 审批链路与审计，不绕过 sandbox；MCP 凭据不由方案下发。
4. 该流程属 Pi Session / Approval 共享口径（AGENTS.md §8 高风险），契约变更需先确认。
