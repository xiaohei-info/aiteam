行业方案：单人 / 组群、群聊编排、能力清单与运营端 UI 重构 2026-11-17 · 设计草案，未写代码

一句话：方案没有类型、群主与编排规则靠 AI 黑盒、所需 skill / MCP 看不见，运营端页面又难操作 → 方案带类型与编排规则并由运营确认，应用后自动招募，桌面端可一键建群 → 每一端发布前后都看得见、管得住。

方案分「单人 / 组群」

单人 = 1 位专家、不建群；组群 = 2–12 位专家，必须有群主与编排规则（复用 collaboration-markdown-v1）。

三端各管一段

运营端生成并确认 → 企业端应用即招募并换算成员 ID → 桌面端人才市场展示方案、一键建群。

看得见的清单与重构后的页面

专家所需 skill / MCP 提前显示；运营端列表与详情改为「状态 + 唯一主操作 + 文字阻塞说明」。

阅读提示：工作量用 S / M / L 粗估，只表示相对大小，不是排期承诺；UI 为示意图，不是最终视觉稿；表格里标「新」的是仓库里目前没有的东西。配套设计文档：2026-11-17-方案单人组群与群聊编排-需求与设计.md。

1 解决什么问题

现在的问题本方案怎么解决谁受益
方案没有类型，一个专家的方案也被当作团队新增 mode: solo | group；solo 恰 1 位专家、无群主与规则；group 2–12 位运营、企业管理员
只有 ≤4000 字的自然语言「协作说明」，不参与建群新增 orchestration_rules（collaboration-markdown-v1，@{成员} 引用），随方案下发，建群时直接作为群编排桌面用户
群主由 AI 给出，运营没有明确确认的入口AI 给建议，运营显式「确认群主 / 规则 / 能力清单」后才能提交审核运营、审核人
需要哪些 skill / MCP 到用了才发现生成产物按专家带 skills（只能引用平台目录）与 mcps（仅声明）；草稿页、企业端应用前、桌面详情都显示运营、企业管理员、用户
桌面人才市场只有专家，无法按方案建群加「方案」页签，详情展示成员 / 编排 / 清单；组群方案「用此方案建群」，单人方案「开始私聊」桌面用户
运营端页面：只有标题可点、详情堆 5 个卡片和 6 条 Banner、禁用原因藏在 tooltip重构为步骤条 + 唯一主操作 + 发布清单 + 分区就地编辑，状态和阻塞原因直接写成文字运营、审核人
不能保证的事：不保证 AI 生成的编排规则质量（只保证格式与引用合法，是否合理由运营确认）；不保证 MCP 在用户机器上可用（声明不等于已安装，企业端无法得知本机连接器状态）；已发布的旧方案没有类型与规则，按「组群、无规则」兼容；UI 的主观观感需要你看截图验收。

3 数据流

边界：不向用户机器入站；会话内容不上传；平台模型状态单写者；Manager 租户数据经 TenantContext / RLS；MCP 只声明不下发凭据。

3.1 总图：谁在哪一端做什么

实线 = 同端流程；虚线 = 跨端调用。方向只有：Manager 拉 Operator、Agent 主动访问 Manager、Agent 本机内部；没有入站到用户机器。

7 阶段与依赖

阶段内容依赖验收
P0 验证小规模验证：worker 稳定产出规则与 skills；生成前能取平台 skill 摘要；key → 模板 ID → 员工 ID 换算样例样例资料 3 份各生成 5 次，引用合法率 ≥95%、skill 命中率 ≥90%；换算单测通过
P1 契约与运营端后端共享契约、草稿 / 生成 / 闸门 / 确认 / 发布换算；最小前端接入P0、高风险确认单人只能 1 专家；组群缺群主或规则无法提交审核；发布后目录含 mode 与规则；旧草稿可读
P2 运营端 UI 重构列表、新建、详情工作台、规则编辑器、能力清单、错误中文化P1每个状态唯一主操作 + 文字阻塞说明；用例全绿；你验收前后对比截图
P3 企业端应用迁移、应用换算与落库、投影下发、应用前预览、弹窗重排P1（Manager 先发布）solo 只招 1 人；group 实例带员工 ID 规则；失败整单回滚；跨租户回归通过
P4 桌面端Agent 建群带编排；人才市场方案页签与详情；私聊 / 建群入口P3建群后群详情有编排卡；单人无建群入口；旧方案行为不变；e2e 通过

P2 与 P3 可并行；P4 依赖 P3 与 Agent 改动。
