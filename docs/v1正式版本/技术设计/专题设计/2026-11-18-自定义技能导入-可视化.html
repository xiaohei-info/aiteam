自定义技能：像 MCP 一样，能自己导入，也能从企业拿 2026-11-18 · 设计草案，未写代码

一句话：技能现在只能装企业签过名的；本方案让成员用「选文件夹 / 选 zip / 粘贴 / 网址」四种方式导入自己的技能，只存在本机，同时保留「从企业拿」这条链路。

四种导入方式

本机文件夹、本机 zip、粘贴 SKILL.md、https 网址（支持 GitHub 仓库子目录 / 单个 md / zip）。

只在本机

技能文件只存在用户机器，不上传企业端；企业端与运营端一行不改；企业也不能禁用。

不等同于放行脚本

导入时不执行任何内容；员工照技能说明跑命令，仍走现有 bash + 审批 + 沙箱。

阅读提示：工作量用 S / M / L 粗估，只表示相对大小，不是排期承诺；UI 为示意图，不是最终视觉稿；表格里标「新」的是仓库里目前没有的东西。配套设计文档：2026-11-18-自定义技能导入-需求与设计.md。

1 解决什么问题

现在的问题本方案怎么解决谁受益
「添加技能」只能装企业开放的技能；企业没开放就用不了新增四种导入方式，成员把自己手上的技能装进本机，只对自己的会话生效企业成员（你）
技能没有来源标记，分不清哪些是企业给的、哪些是自己装的能力页每项显示来源「企业 / 自定义」；自定义显示来源（网址可复制）企业成员
自定义技能塞不进现有签名缓存（SkillCache 只认签名包）并列一个本机存储 + 清单（每文件 sha256），加载时校验；被改动就标出来并停用用户与 Agent 维护者
员工用技能靠 read 工具；有的专家没有沿用 5a4bbdaa：没有 read 的专家拿到只读技能目录的 read成员的所有员工
从网址导入的可靠性未知（GitHub 子目录、zip 炸弹、跳转）先做一次小规模验证（P0），把上限和解析路径定下来再实现全体
不能保证的事（对外口径一致）：① 不保证服务方（GitHub 等）永远可用，导入失败就是失败，不会自动重试到底；② 不保证自定义技能一定正确——它没经企业审核，写错的技能员工会照错做；③ 不保证导入时能挡住所有恶意内容，只挡路径穿越、软链接、超大包；真正跑命令那一步仍要靠审批；④ 不保证「从网址导入」对私有仓库有效，只支持公开地址。

3 数据流

边界：不向用户机器入站；技能内容不上传企业端/运营端；企业端与运营端零改动；专家快照与审批口径不变。

3.1 总图：谁在哪一端做什么

实线 = 同端流程；虚线 = 跨端调用。方向只有：Agent 主动访问 Manager、Agent 主动访问公网；没有入站到用户机器，自定义技能内容不出本机。

3.2 主流程

成员选来源文件夹 / zip / 粘贴 / 网址
→
先检查路径安全、规模、SKILL.md、Pi 能否加载、同名
→
预览确认名称 / 说明 / 文件数 / 来源
→
写本机临时目录 → 校验通过 → 原子替换
→
下一轮生效所有员工可用，仍受专家工具清单外的能力口径约束

3.3 状态与处置矩阵

状态含义员工侧表现成员可做的
已安装清单与文件一致所有员工可用撤销；换成新版本
文件被改动sha256 与清单不符不加载，员工看不到重新导入；撤销
同名冲突与企业技能同名 / 与已装自定义同名不会装改 name；或确认替换自定义那份
下载失败网址 404 / 超时 / 跳转出 https不会装检查网址；或改用 zip / 文件夹
校验不通过无 SKILL.md / name 不合规 / 超限 / zip 炸弹不会装按提示改包

#事项建议卡住谁
1对话里员工能否发起「网址导入技能」不做。模型自己从网上找技能装不可控；成员想装就在「能力」页导入。以后需要再做成审批式P1
2规模上限与二进制文件允许任意文件；≤256 个、总 ≤10 MiB、单个 ≤5 MiB，由 P0 用真实仓库校准P1
3网址来源要不要「检查更新」P1 不做；重新导入即覆盖，能力页显示来源网址便于重新导入P2
4引入 fflate 解 zip同意（MIT、零依赖）；不引入就要放弃 zip 与 GitHub 仓库网址P1
5与企业技能同名拒绝并提示改 name，避免同名谁生效说不清P1
建议你最先拍板：#1（决定 P1 范围与聊天工具边界）、#4（决定 P1 依赖与 GitHub 仓库网址是否可行）。
