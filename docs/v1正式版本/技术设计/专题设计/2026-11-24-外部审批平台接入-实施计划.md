**单向依赖约束**（C1 加 import 守卫测试）：

- `routes → hub → {storage, plugins/registry, contract}`；`plugins → contract`；`storage → contract`。
- **`agent-tools/**` 不得 import `plugins/**` 与 `hub/executor.ts`**，这是「自然语言不能触发外部写操作」（方案 §15）的编译期保证。
- `storage/**` 不得 import `hub/**`；`hub/**` 与 `plugins/**` 不得 import 任何模型客户端（分析只走员工 Pi Session，§1.3 (7)）。
- 核心目录（`contract/`、`hub/`、`storage/`、`agent-tools/`、`routes/`）不得出现插件 id 字面量或按插件分支（C31 守卫，方案 §2.1「核心零改动」）。

### 1.3 关键技术选择（方案未展开的部分）

**(1) 凭据与确认通道**

用户级凭据复用 `server/agent_service/src/mcp-auth.ts` 的 `McpCredentialStore`，OAuth 回调复用 `McpAuthService.login/callback` 与 `GET /api/agent/mcp-auth/callback`；不用 WebView 可读的 `secure_session.rs` 存储，不新建凭据 Broker。限制：挡不住同一操作系统账户下的其他进程。企业应用 Secret 托管与换票**待定**（方案 §13 #12）。

执行确认经桌面宿主私有通道下达（方案 §3.4 第 3 条、§10 第 3 条），沿用 `clients/desktop/src-tauri/src/local_directory_host.rs` 的形态（Unix `0600` UDS 位于 `0700` 目录 + 每启动随机 72 字符 token）；该实现当前仅 Unix，C13 须同时提供 Windows 命名管道（当前用户 DACL）。

**(2) 宿主进程能力：单实例在 P1，常驻只对长连接插件**

方案 §13 #5 要求「同机单实例由桌面宿主负责」，这与平台无关，放 P1（C15，`tauri-plugin-single-instance`）。后台常驻、开机自启、托盘角标、唤醒重连（方案 §7.5）只在首个真实插件采用本机长连接时才做（C34）；轮询类插件不需要。Agent 是桌面端 sidecar，存活期等于桌面进程；「唤醒后增量对账」归端 B（`hub/reconcile.ts`），由端 C 在系统唤醒 / 网络变化时调一次 `POST /api/agent/approvals/sync`。通知复用已有 `tauri-plugin-notification` 与 `src/lib/systemNotifications.ts`。

**(3) 同步：复用 `ScheduleService` 的调度机制，但不复用其 misfire 语义**

`hub/sync.ts` 复用 `server/agent_service/src/schedule.ts` 的定时器与重试落库形态，但**不能用 `misfire: skip`**：跳过一次同步等于漏单。错过的周期合并成一次带游标的增量同步，游标（`ext_approval_binding.cursor`，`connection` 行）只在成功后推进（方案 §7.1 第 6 条）。`describe().push = true` 的插件只缩短间隔，不取消定时对账（方案 §3.1 约束 2）。

**(4) 审批群聊：复用现有群聊，不新建第二套会话**

会话 id 记在 `ext_approval_task.conversation_id`；创建走 `src/services/group-creation.ts` 的 `GroupCreationService.create()`，投递走 `src/services/group-message-delivery.ts`。「只有负责员工能提交正式建议」由 `approval_submit_proposal` 按 `flow` 行的 `employee_id` 判定；其他参与者只发表意见，不落建议字段（方案 §3.5）。

**(5) HTTP 路由：不再往 `http/server.ts` 里堆**

`src/http/server.ts` 已 3700+ 行。11 个接口集中在 `ext-approval/routes/index.ts` 导出 `registerExtApprovalRoutes(server)`，`server.ts` 只加一行调用（AGENTS.md §3.8）。

**(6) 多设备单活：靠「凭据不跨设备」实现，不引入分布式锁**

2026-11-24 已拍板「只允许一台设备活跃处理事务」（方案 §13 #5）。以用户级凭据不跨设备为前提；若 P0 裁决引入企业侧服务承接写操作，须重新设计单活与跨设备去重（方案 §13 #12）。

- 凭据只存在完成授权的那台设备的 `McpCredentialStore`，绝不跨设备同步；其他设备本地没有 `connection` 行 → 连接页显示「未在本设备授权」，不展示任务。
- 接管：新设备重走授权；旧设备自检失败后任务置 `blocked`（`reason_code = credential_expired`），提示「授权已在其他设备接管」（各平台新授权后旧 Token 是否立即失效列入 P0）。
- 执行幂等键由跨设备外部字段组成（方案 §7.3），同机单实例由 C15 负责。

对提交的影响：C7 加「凭据存储无同步 / 导出路径」用例；C12 加接管后置 `blocked` 用例；C28 向导显式告知「在此设备授权后，其他设备不再接收与处理」。**不新增表、不新增跨端接口。**

**(7) 用量：审批分析必须走员工 Pi Session 回合**

现有链路：`pi/session-host.ts` 在回合结束时构造 `UsageCapture` → `aggregateUsage()`（`src/usage.ts`）→ 本地 usage outbox → `UsageFlushService`（`src/usage-flush.ts`）上报 Manager `/api/manager/usage/upload`。**这条链路只覆盖走 SessionHost 的回合**，所以分析由 `hub/dispatch.ts` 投递为负责员工 Pi Session 的一个回合，`hub/` 与 `plugins/` 不得另开模型调用通道（C1 守卫 + C18 用例）。`useFauxModel` 分支会跳过用量记录，验用量要用「fake 插件 + 真模型」。

**(8) 上下文裁剪：表单字段必进，附件按次授权（方案 §13 #3）**

| 层 | 内容 | 默认 | 落点 |
|---|---|---|---|
| L1 表单字段 | `flow` 行 `field_whitelist_json` 勾选的字段 | **必进** | `agent-tools/context.ts` 按白名单裁剪 `ExternalTask.fields` |
| L2 附件元信息 | 文件名、类型、大小、页数 | **必进** | 同上 |
| L3 附件正文 | 解析结果 | **按次授权**（`attachment_policy = on_demand`） | `approval_request_attachment` 只发起申请 → 用户在详情页「允许读取」（`POST …/tasks/{id}/analyze` 带附件 id）→ 只注入本次分析 |

`attachment_policy`：`never`（缺附件依据直接 `blocking`）/ `on_demand`（默认）/ `always`（向导须给风险提示）。附件授权的留痕方式已定：写本地结构化日志（§8.2 owner 2026-11-28 已定行；方案 §13 #3）。

### 5.3 C6 存储层与 `approval_record` 复用 spike

- `storage/schema.ts` 导出 `EXT_APPROVAL_DDL`，在 `storage/sqlite.ts` 构造函数的 `db.exec` 之后、`migrateOwnershipTables()` 之前调用一次。沿用仓库现有做法：`CREATE TABLE IF NOT EXISTS` + 后续列用 `ALTER TABLE ... ADD COLUMN` 放进现有 `try/catch` 数组，不引入迁移框架。

- `storage/tasks.ts` 乐观并发：更新带 `WHERE external_version = ?`，更新 0 行视为外部已变，调用方置 `stale`。
- `storage/executions.ts` 哈希链：按 `tenant_id + member_id` 递增序号，`entry_hash = SHA-256(prev_hash ‖ 规范化行)`。
