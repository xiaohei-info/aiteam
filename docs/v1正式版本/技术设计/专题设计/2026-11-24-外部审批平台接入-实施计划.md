### 1.3 关键技术选择（方案未展开的部分）

**(1) 凭据：企业应用 Secret 归企业侧 Manager 换票，本机用户级 Token 复用桌面宿主本地加密 Vault（不引入原生 keyring 依赖）**

现成形态：`clients/desktop/src-tauri/src/local_directory_host.rs` 已经是「桌面宿主 → Agent」的私有授权通道（Unix `0700` 目录 + `0600` UDS + 每启动随机 72 字符 token，即两个带连字符 UUIDv4 拼接 `format!("{}{}", Uuid::new_v4(), Uuid::new_v4())`，文件头注释即「Credentials never enter the WebView」），Agent 侧对应 `server/agent_service/src/local-directory-host.ts` 的 `NativeDirectoryHost`，token 与 socket 路径经 `AITEAM_LOCAL_HOST_*` 注入后**立即从 `process.env` 删除**。`secure_session.rs` 已有 `CREDENTIALS_VAULT_FILE_NAME = "credentials-vault.json"` 与 AES-256-GCM + HKDF 封装——**实际实现为 Windows 用 DPAPI 包裹主密钥，macOS/Linux 为 `0700` 目录下的 `0600` 文件 `master.key`（未调用 Keychain / Secret Service）**。本地审批 SQLite 不做库级落盘加密，依赖用户私有目录权限与 OS 全盘加密。

分层归属（2026-11-25 拍板）：企业自建应用 Secret（ClientSecret/AppSecret/EngineSecret）统一加密托管在**企业侧 Manager**（生产部署在企业服务器上，由平台方实施交付、企业持有，与 Operator 分离部署且不共用服务器与数据库；开发/测试环境按正式独立部署条件验证，不做运行期部署形态开关；实施代录 Secret 须在交付验收时由企业重置/改写，见 `09-部署分发与入户绑定.md` §14.4），仅用于 OAuth 换票/续期与集中轮换/吊销（Manager 在换票/续期期间瞬时经手但不持久化用户级审批 Token，`no-store`，记录成员可查的换票审计并支持企业侧一键停用），不向每台桌面端分发静态应用 Secret；本专题在 Tauri 侧新增 `credential_host.rs`（**本地凭据托管 Broker / Vault Broker**，不称「密钥环 broker」），仅保护本机用户级审批 Token（`cred_put` / `cred_get` / `cred_delete` / `cred_list`）。Node 侧 `credentials/host-broker.ts` 只在 Adapter 发起外部调用的那一刻取值并注入请求头，取回的值包在不可序列化的注入器里，**不进 SQLite、不进日志、不进 Pi entries**（方案 §4.1、§9.1）。SQLite 只存 `credential_ref` / `token_ref`。

本地 HTTP 通道鉴权与 CSP 收口：Node Agent 仅监听 `127.0.0.1`，所有 `/api/agent/approvals/*` 路由统一走 `Authorization: Bearer <token>`（当前登录成员短期会话 JWT）+ CORS 来源白名单（`server/agent_service/src/http/server.ts` 中的 `AITEAM_AGENT_ALLOWED_ORIGINS`，未知 `Origin` 的 `OPTIONS` 预检返回 403，非预检请求靠 Bearer JWT 鉴权，不称「同源校验」），且不提供返回明文凭据的路由。桌面端正式交付前另需收紧 `clients/desktop/src-tauri/tauri.conf.json` 的 CSP（移除 `img-src` 通配 `https:` 及硬编码测试服地址 `https://aifred.cn`、`http://121.40.78.201:8783`，见方案 §9.2）。

已知缺口：`local_directory_host.rs` 当前是 `std::os::unix`，`NativeDirectoryHost.status()` 还要求 `platform === "darwin"`。凭据通道必须跨平台，因此 C16 要同时落 Windows 命名管道实现（带当前用户 DACL），不能照抄 UDS。

**(2) 常驻：桌面宿主负责进程生命周期，Agent 负责对账**

Agent 是桌面端 sidecar，其存活期等于桌面应用进程存活期。所以方案 §7.5 的 7 项能力里，后台常驻、开机自启、托盘角标、单实例、唤醒事件归**端 C（Tauri）**；"唤醒后增量对账"归**端 B（`hub/reconciler.ts`）**，由端 C 在系统唤醒 / 网络变化时调一次 `POST /api/agent/approvals/sync`。

新增 Rust 依赖：`tauri-plugin-single-instance`、`tauri-plugin-autostart`，托盘用 Tauri 2 核心 `tray-icon` 能力；通知复用已有 `tauri-plugin-notification` 与 `src/lib/systemNotifications.ts`。

**(3) 轮询：复用 `ScheduleService` 的调度机制，但不复用其 misfire 语义**

氚云轮询与定时对账复用 `server/agent_service/src/schedule.ts` 的定时器与重试落库形态（方案 §1.3 已指明），但审批任务**不能用 `misfire: skip`**：跳过一次轮询等于漏单。实现为 `hub/reconciler.ts` 内独立的 `catch-up` 语义：错过的周期合并成一次带游标的增量对账，游标只在成功后推进（方案 §7.4、数据流转 §7.3）。

**(4) 审批群聊：复用现有群聊，不新建第二套会话**

`store/conversations.ts` 只存 `task_id ↔ conversation_id` 绑定与 roster/snapshot 版本；会话创建走 `src/services/group-creation.ts` 的 `GroupCreationService.create()`，消息投递走 `src/services/group-message-delivery.ts`。「只有路由员工能提交正式建议」由 `agent-tools/tools.ts` 在 `approval_submit_proposal` 内按 `flow_binding.employee_id` 判定，其他参与者的意见落 `audit` 而不落 `proposal`。

**(5) HTTP 路由：不再往 3721 行的 `http/server.ts` 里堆**

`src/http/server.ts` 已 3721 行。本专题的 25 条路由集中在 `ext-approval/http/routes.ts` 导出一个 `registerExtApprovalRoutes(server)`，在 `server.ts` 的 `registerRoutes()` 里只加一行调用。这既符合 AGENTS.md §3.8（不沿用旧 `app/` 的巨型单文件写法），也让契约快照 diff 可读。

**(6) 多设备单活：靠「凭据不跨设备」实现，不引入分布式锁**

2026-11-24 已拍板「只允许一台设备活跃处理事务」。本架构没有云侧执行器、Manager 也不进入审批路径，所以**不存在可以放租约的中心**。落地方式是把单活变成凭据的物理属性：

- 用户在哪台设备完成外部授权，`credential_ref` 指向的密文就只存在那台设备的 vault（`credentials-vault.json`，见 (1)），**绝不跨设备同步**。其他设备没有凭据 → 既订阅不到事件、也执行不了写操作，天然单活。
- 其他设备的表现：`ext_approval_account` 本地无记录 → 平台连接页显示「未在本设备授权」，不是「只读」，也不展示任何任务（没有凭据就拉不到数据）。
- 接管：在新设备重新走一次授权向导。旧设备的 token 在平台侧失效后，其权限自检（方案 §2.5）失败 → 必须映射为专门的 `authorization_taken_over` 态，提示「此账号的授权已在其他设备接管」，而不是笼统的「授权失效」。
- 同一台机器内的单实例（二次启动只聚焦）仍由 C26 的 `tauri-plugin-single-instance` 负责，这是两件不同的事。

对提交的影响：C16 加「vault 不含同步/导出路径」用例；C17 加 `authorization_taken_over` 的错误映射用例；C30-2 向导里必须显式告知「在此设备授权后，其他设备不再接收与处理」。**不新增表、不新增跨端接口。**

**(7) 用量：审批分析的 token 必须进既有用量链路，因此分析一定走 SessionHost**

2026-11-24 已拍板「审批产生的 token 消耗都要进」。现有链路已经是现成的：`pi/session-host.ts:1921` 在每个回合结束时构造 `UsageCapture` → `aggregateUsage()`（`src/usage.ts:116`）按 `tenant+member+employee+小时` 聚合 → 落本地 usage outbox → `UsageFlushService`（`src/usage-flush.ts`）每 15s 上报 Manager `/api/manager/usage/upload`。

关键约束：**这条链路只覆盖走 SessionHost 的回合**。如果 Hub 为了省事直接调模型（绕过 Pi Session）做审批分析，token 就不会被计入。因此：

- 审批分析必须以**路由员工的 Pi Session 回合**执行，由 `agent-tools` 触发，不得在 `hub/` 里新开模型调用通道。
- 新增提交 **C22-1** 专门验证这件事：分析一次 → `usage_outbox` 多一条、`input_tokens + output_tokens > 0`、`employee_id` 等于路由员工；并加守卫用例断言 `ext-approval/hub/**` 不 import 任何模型客户端。
- 既有的 `useFauxModel` 分支会跳过用量记录，假平台联调（C25）要注意区分「假平台 + 真模型」与「假模型」，前者才能验用量。

**(8) 上下文裁剪：表单字段必进，附件按次授权（2026-11-24 定案）**

「原文不进模型，模型怎么知道要做什么」——原文**必须进**，否则没有可分析的对象。真正需要裁的是范围，分三层：

| 层 | 内容 | 默认 | 说明 |
|---|---|---|---|
| L1 表单字段 | 绑定时勾选的业务字段（标题、金额、供应商、事由、预算科目、申请人、部门、流程节点等） | **必进** | 这就是模型的分析对象。绑定向导里勾选哪些字段，`flow_binding.field_whitelist` 就存哪些，裁剪按这份白名单执行 |
| L2 附件元信息 | 文件名、类型、大小、页数 | **必进** | 用于判断「该看哪份附件」，以及在 `missing_items` 里点名缺哪份材料 |
| L3 附件正文 | PDF/表格/图片的解析结果 | **按次授权**（`attachment_policy = on_demand`） | 模型判断需要读某份附件时，通过 `approval_request_attachment` 工具发起一次请求 → 用户在详情页点「允许读取」→ 该附件正文只注入这一次分析，并落 `ext_approval_audit` |

`flow_binding.attachment_policy` 三个取值：`never`（永不注入正文，缺附件依据时直接 `blocking`）、`on_demand`（默认）、`always`（绑定时即授权全部附件，适合企业私有化模型局域网闭环场景）。

对提交的影响：

## 4. P0 PoC（用户侧前置，阻塞写操作）

P0 不是代码任务，是**决定 P2/P3 能不能开放写操作的前置验证**。下列资源必须由你（或企业实施方）提供，否则 C3 无法完成，C28/C29 只能做到「可分析，暂不可提交」，C31–C33（氚云，含写操作）直接阻塞。

| 需要的东西 | 用途 | 缺了会怎样 |
|---|---|---|
| 钉钉测试企业 + 可创建企业内部应用的管理员 | Stream 订阅、审批读写、机器人与互动卡片、卡片回调点击人字段 | 钉钉只能做提醒与分析；C29 的写操作与卡片确认阻塞 |
| 飞书测试企业 + 可创建自建应用的管理员 | 长连接、审批定义读取、`user_access_token` 写权限、机器人消息与卡片 | 飞书只能做提醒与分析；C28 的写操作阻塞 |
| 氚云测试账号 + 可配置自定义接口与发布的权限 | 工作项读写、真实操作人审计、是否有实时事件、连接器 MCP 资格与套餐 | 氚云永久停在「提醒 + 分析 + 打开氚云处理 + 结果对账」，方案 §11 P3 的写操作不开放 |

PoC 必须给出结论的 12 项（调查 §8 的 P0-1–P0-12，含卡片可验证点击人、新授权旧 Token 失效与纯用户级长连接）：

1. 三平台能否以**当前用户身份**执行同意/拒绝，且外部审计显示该用户（方案 §4.3）。
2. 重复确认是否会向外部重复写入（幂等保护是否可做到外部侧）。
3. 氚云自定义接口能否保留真实操作人。
4. 氚云是否存在实时事件，还是只能轮询。
5. 钉钉 Stream 多桌面端连接的投递行为与离线补偿。
6. 附件读取、事件重推、断线重连、限流、模板变更的实际行为。
7. 企业自建应用在企业侧 Manager 配置凭据后，普通用户能否仅扫码完成 OAuth 授权而不填 API/Secret/流程编码（方案 §2.4）。
8. 氚云连接器 MCP 能否由本桌面端直接接入（资格与套餐）。
9. 三平台的权限自检项能否全部读到（授权身份、可读流程、写权限、支持动作）。
10. **P0-10**：外部卡片回调能否取得**可验证的**真实点击人身份，从而完成方案 §3.6.1 的硬条件 1。
11. **P0-11**：新设备重新授权后，旧设备的用户级 Token 在平台侧是否立即失效（验证多设备单活的外部前提）。
12. **P0-12**：桌面端仅持 Manager 换回的用户级 Token（不持应用级 Secret）能否建立钉钉 Stream / 飞书 WS 长连接；若平台强制长连接需应用凭据，明确只读事件子应用隔离或轮询降级方案。

每项结论写进 C3 的验证记录并回填至 [需求与设计 §3.1.1 三平台能力实测矩阵](./2026-11-23-外部审批平台接入-需求与设计.md#311-三平台能力实测矩阵p0-验证口径)，格式为「通过 / 不通过 / 未验证 + 证据 + 阻塞的提交编号」。**不通过与未验证一律按不通过处理**，对应能力不得出现在 UI（方案 §3.1 最后一句）。

## 5. P1 文件级实施步骤

P1 是本专题的地基，这里细到文件与关键函数。每步先写测试（AGENTS.md §10.3），红→绿后再进下一步。

### 5.1 C4 协议层

- `protocol/types.ts`：方案 §3.1/§3.3/§3.4/§3.5/§3.6 的类型照抄为 TS 类型 + TypeBox schema 双份（TS 给内部，TypeBox 给 HTTP 与工具参数）。`ApprovalTaskState` 的 13 个值、`ApprovalAction` 的 6 个值、`ApprovalCapability` 的 20 个值一个不少。
- `protocol/mapping.ts`：`resolveStateMapping(external, table, version)` 返回 `ApprovalStateMapping`。四条规则：统一值缺失时**不得**近似转换，落 `unknown`；一原始值对多语义落 `ambiguous`；平台/身份明确不支持落 `unsupported`；无法确认时任务落 `mapping_failed` 并阻止路由与写操作（方案 §3.2）。保留 `external.value`、`label`、`observedAt` 与 `mappingVersion`。
- `protocol/capability.ts`：`assertCapability(descriptor, capability)` 与 `assertTransition(descriptor, from, action)` 必须**都过**才允许建执行单。这是 Review Gate 的前置条件，不是 UI 的展示逻辑。
- `protocol/evidence.ts`：`evidence_json` 的 TypeBox schema（方案 §3.8 全部 13 个键）+ 五条约束：每条 `reasons` 必带 `citation`；`risk_rules` 取值必须是 `ext_approval_policy` 里存在的规则 ID；`missing_items.blocking=true` 时禁止直接进同意；`confidence < medium` 时置「依据不足」标记；`policy_refs` 必须指向已装载的制度版本。
- `protocol/events.ts`：§2.3 的 38 个事件名 + 8 个分类常量。audit 与 metrics 都从这里取名，禁止各处写字面量。

### 5.2 C5/C6 存储层

- `store/schema.ts` 导出 `EXT_APPROVAL_DDL`（字符串），在 `storage/sqlite.ts` 构造函数的 `db.exec` 之后、`migrateOwnershipTables()` 之前调用一次。沿用仓库现有做法：`CREATE TABLE IF NOT EXISTS` + 后续列用 `ALTER TABLE ... ADD COLUMN` 放进那个 `try/catch` 数组，不引入迁移框架。
- **16 张表**，严格按方案 §6 的表清单逐条对应，表名加 `ext_approval_` 前缀：`account`、`identity`、`flow_binding`、`event`、`task`、`task_snapshot`、`proposal`、`execution`、`audit`、`sync_cursor`、`task_conversation`、`bot_binding`、`bot_event`、`feedback`、`outcome`、`policy`。一张不少，不得把 `feedback`/`outcome`/`policy` 推到后期（方案 §14.5 第 1 条：指标字段必须 P1 随表落库）。
- 全部表带 `tenant_id` 与 `member_id`，即使当前单用户（方案 §6 末段）。
- 关键索引：`ext_approval_event` 唯一索引 `(provider, account_id, external_event_id)`；`ext_approval_bot_event` 唯一索引 `(provider, account_id, external_message_id)`；`ext_approval_execution` 唯一索引 `(idempotency_key)`；`ext_approval_task` 唯一索引 `(provider, account_id, external_instance_ref, external_task_ref)`。
- `store/tasks.ts` 的乐观并发：更新必须带 `WHERE external_version = ?`，更新 0 行即视为外部已变，调用方把任务置 `stale`。
- 进程重启语义：参照 `storage-restart.test.ts` 与现有 `approval_record` 的做法——重启时把 `executing` 的执行记录置为不可执行并保留诊断，不能让它看起来还能继续。

### 5.3 C7/C17 凭据层

- `credentials/store.ts`：

  ```ts
  interface CredentialInjector { apply(headers: Headers): void }          // 不可序列化
  interface CredentialStore {
    put(ref: CredentialRef, secret: string): Promise<void>;
    injector(ref: CredentialRef): Promise<CredentialInjector>;           // 没有 getPlain
    delete(ref: CredentialRef): Promise<void>;
    list(owner: Owner): Promise<CredentialRef[]>;                        // 只返引用
  }
  ```

  **故意不提供返回明文字符串的方法**，让「Secret 进日志 / 进模型 / 进 SQLite」在类型层就写不出来。
- `credentials/host-broker.ts`：socket 路径与 token 从新增的 `AITEAM_CRED_HOST_SOCKET` / `AITEAM_CRED_HOST_TOKEN` 读取后立刻 `delete process.env[...]`（照 `local-directory-host.ts:8-11`）。请求失败时抛 `ExtApprovalError("credential_unavailable")`，Hub 据此把连接状态置为「不能执行用户级审批」，只保留分析与提醒（方案 §3.6.1 硬条件 3 的处置）。

### 5.4 C9–C14 Hub 关键实现

- `hub/inbox.ts`：`accept(rawEvent)` 只做「验签/连接身份 → 去重落 `ext_approval_event` → 立即返回」，然后把 `event_id` 丢进进程内队列异步处理。平台回调线程里**不得**出现 `SessionHost` 调用与 Adapter 写方法——用注入的 spy 在测试里断言调用次数为 0（方案 §7.1 第 3 条、§7.2 第 6 条）。
- `hub/router.ts`：路由键严格按方案 §5.1 的 `provider + account_id + template_ref + node_ref + external_user_ref`，不得采信事件正文里的显示名（方案 §7.1 第 5 条）。匹配到唯一绑定才置 `assigned` 并把 `binding_revision` 冻结到任务上。
- `hub/review-gate.ts`：票据载荷 = `{task_id, external_version, snapshot_version, action, member_id, exp}`，HMAC 用 Agent 本地实例密钥；核销走一次性消费（`consumed` 列，仿 `approval_record.consumed`）。`review_confirmed` 只落库，不触外部。
- `hub/executor.ts`：唯一允许调用 Adapter 写方法的地方。顺序固定为：核销票据 → 重读外部详情 → 比对处理人/状态/`external_version`/`snapshot_version` → 生成或复用 `idempotency_key` → Adapter 写一次 → 记 `external_request_id` → 查询或等事件确认 → 置 `executed`。超时或结果不可确认时置 `execution_unknown` 并**禁止直接重试**，转 `reconciler`（方案 §7.3、§2.3 执行类事件）。
- `hub/card-guard.ts`：`verify(click)` 返回 `{passed, failures[]}`，三条是**与关系**。硬条件 1 的点击人必须来自平台回调的可验证字段或随后的平台查询，**不得采信卡片 payload 自带的用户 ID**（方案 §3.6.1 补充约束 1）。三条结果逐条写 `ext_approval_audit`，不记 Secret/Token/完整表单。
- `hub/reconciler.ts`：四个入口共用一个带锁的 `reconcile(accountId, mode)`。`mode` ∈ `startup | scheduled | wakeup | manual`。对账范围按方案 §7.4 第 4 步的五个状态；外部已完成/取消/超时的关闭本地入口；只重投「仍由当前用户负责且外部仍可操作」的任务。

### 5.5 C18/C19 Agent 工具与群聊

- `agent-tools/tools.ts` 用 `defineTool`（仿 `src/tools/delegate.ts`）注册方案 §3.7 的 8 个工具 + `approval_request_attachment`（§1.3 (8)），共 9 个。接线点是 `pi/session-host.ts` 的 `customTools` 路径（`session-host.ts:1312`、`:1383`），按员工授权过滤：只有当前任务流程绑定的员工拿到 `approval_submit_proposal`，其他已授权员工只拿读取与会话上下文工具。
- 守卫测试断言「注册工具名集合 ∩ /execute|approve|reject|transfer/ = ∅」，这条和 C1 的 import 守卫一起构成「自然语言不能触发外部写」的双重保证。
- `agent-tools/context.ts`：`toModelContext(task, binding)` 按 `binding.field_whitelist` 裁剪 `form` 与 `attachments`，并把外部表单内容统一包成「不可信输入」块（方案 §9.1 第 1 条）。白名单变更后旧建议置 `stale` 且不可执行（数据流转 §11.9）。

### 5.6 C20 HTTP 与契约

- 25 条路由按方案 §10 原样落地，前缀 `/api/agent/approvals`。
- 四条写接口（`execute`、`review`、`comment`、`transfer`）过 `http/ticket.ts` 中间件；`execute` 额外要求调用方来源标注为桌面 UI，模型工具来源直接 403（方案 §10 第 3、4 条）。
- 机器人卡片回调走独立入口，只能创建 Review Gate 请求，自己不签票据（方案 §10 第 6 条）。
- 契约同步**必须与路由同一提交**：`bash scripts/check-openapi.sh` 产出 `agent.json` → 刷新 `clients/desktop/docs/api.json` → 同步 `clients/desktop/src/api/agent/contract.ts` 的 `documentedRoutes` → `pnpm check:api-contract` 绿。注意 `check:api-contract` 做的是**集合全等**断言，漏一条就红。
