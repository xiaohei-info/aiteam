# 技能 / MCP 命名空间、出处、编辑与更新提示 — 需求与设计

> 日期：2026-11-20 · 分支 `feat/capability-namespace-updates`（基于 `feat/enterprise-skill-mcp-clawhub` @ `9b099798`）
> 可视化沟通稿：同目录 `2026-11-20-技能MCP命名空间出处与更新提示-可视化.html`
> 前置设计：`2026-11-20-企业端技能MCP新增与ClawHub打通-需求与设计.md`（§4.7 技能编辑器与运营端自建技能）

## 0. 需求原文

> 1. 添加编辑按钮。2. 其他平台来源的要注明出处。3. 运营端生产的 skill 和 mcp 要用 taiyim/ 为前缀，企业端则以企业名/命名；如果是其他平台的被我们编辑了则加上前缀。4. 如果 skill 和 mcp 有改动要在企业端和用户端提示是否更新，更新则在用户端使用最新的同名 skill；这一块，如果你有更好的想法或设计能优化体验和实现复杂度可以提出来。

## 1. 已决定（用户 2026-11-20 拍板）

| # | 决定 |
|---|---|
| D1 | 前缀 = **命名空间字段 + 全端展示**（`taiyim/weather`）。SKILL.md `name` 与 MCP `ref` **不改**：Agent Skills 规范 / pi 要求 name 只含小写字母、数字、连字符，pi 同名只加载第一个；MCP `ref` 是跨端安装标识。 |
| D2 | 平台前缀 `taiyim`（按用户原样拼写，集中在一个常量）；企业前缀 = **企业名称**，展示时取当前值，未设置时回退**企业代码**。 |
| D3 | 运营端 ClawHub 技能、企业端平台市场技能都加「编辑」；保存后生成**我方副本**（我方前缀 + 「改自 …」），**原件保留，两者并存**；副本不再跟随上游更新。 |
| D4 | 更新 = **状态徽标 + 原地更新**：每层同一技能只有一条；企业端「平台有新版本」+「更新」；桌面「有更新」+「N 项有更新 · 全部更新」；新版本从**下一次对话**生效，进行中的对话不变；管理员配给专家的技能随管理员确认的更新走；不做推送、不弹窗。 |

## 2. 现状核对

### 2.1 命名

- pi：`name` 声明与目录名不一致不报错；同名技能保留第一个并警告（pi `docs/skills.md:83-85`）。所以前缀不能写进 `name`。
- MCP `ref` 正则 `^[a-z][a-z0-9_-]{0,63}$`（`server/shared/mcp_config.py:19`），ref 一经创建不可改（`server/manager_service/mcp_catalog.py:11`、`server/operation_service/platform_mcp_market.py:128`）。
- 运营端技能卡副标题：自建为「平台自建 · slug」，ClawHub 为「owner/slug」（`web/operation/src/features/skill-market/SkillMarketPage.tsx:137`）；ClawHub 技能只有「查看」。
- 企业端技能来源标签（`web/manager/src/features/capability/CapabilityPage.tsx:486-491`）：平台市场 / 自定义 / 网址 / ClawHub；没有前缀概念。
- 企业名称在 `enterprise_settings.enterprise_name`（`server/manager_service/settings_repository.py:63`），可为空；企业代码在控制库 `tenant_registry.enterprise_code`，`/me` 已做「名称为空回退代码」的读取（`server/manager_service/routes_me.py:23-37`、`me_service.py:62-63`）。

### 2.2 出处

- 运营端 ClawHub 技能有 owner/slug（`platform_skill.external_owner/external_slug`，`server/operation_service/migrations/0008_platform_skill_market.sql:8-9`）；自建技能 `external_owner='platform'`（`platform_skill_market.py:194`）；网址导入的自建技能没有记录来源网址的位置（包版本表有 `source_url`，`platform_skill_market.py:403`）。
- 企业端导入记录 `config.origin = {kind,label,url}`（`server/manager_service/skill_import_service.py:221-222`）；**在线编辑后 origin 变成 editor，原来的 ClawHub / 网址来源丢失**（同文件 `:241`，`config` 覆盖 `origin`）。
- 桌面已装技能来源标签：平台技能市场 / 企业自建技能 / ClawHub / 自定义（`clients/desktop/src/pages/Capabilities/capabilityLabels.ts:7-13`），不显示具体出处。

### 2.3 更新

- **MCP 三端已有修订号更新链**：运营端每次编辑 revision+1（`platform_mcp_market.py:128`）→ 企业端 `update_available`（`mcp_catalog.py:202`）→ 桌面「从企业拿」`update` 状态与「企业已更新这个 MCP」提示（`server/agent_service/src/connectors.ts:718-736`、`clients/desktop/src/pages/Capabilities/CatalogMcpPanel.tsx:114`）。缺的是：企业端 MCP 页以外的位置、桌面「能力」页已装列表上看不到。
- **技能缺口**：
  - 企业端安装平台技能新版本时新增一行，tenant skill_id 带版本（`server/manager_service/platform_skill_service.py:34-35`、`:121-131`）。成员目录里出现两条，专家仍绑旧行；`installed_versions` 列出多个版本（`:69`）。
  - 桌面「添加技能 · 从企业拿」已有 `upgrade` 状态（`capabilityLabels.ts` `installableSkillState`），但因为平台新版本 skill_id 变了，实际显示成「另一个可安装技能」而不是「可更新」；「能力」页已装列表没有更新提示（`clients/desktop/src/pages/Capabilities/index.tsx:115-160`）。
  - Agent 只按 skill_id 判断已装（`connectors.ts:429`）；不同 skill_id、同 SKILL.md name 的两个技能都能装上，pi 只加载第一个。
- 招募 / 方案应用按固定版本安装平台技能（`server/manager_service/recruit_service.py:524` → `install_all`，`platform_skill_service.py:151-157`）。

## 3. 目标与非目标

目标：
- 三端统一展示「命名空间/名称」与出处（「来自 ClawHub owner/slug ↗」「改自 …」）。
- 运营端 ClawHub 技能、企业端平台技能可「编辑」→ 我方副本。
- 技能更新在企业端、桌面端有明确的「有更新」状态和一键更新；MCP 补齐同样的入口。

非目标：
- 不改 SKILL.md `name`、MCP `ref`、tenant skill_id 等已有标识；不迁移成员机器上的已装记录。
- 不做自动更新开关、推送通知、弹窗（D4）；不做版本回滚。
- 副本不跟随上游（不做三方合并）。

## 4. 方案

### 4.1 命名空间与出处的统一口径（共享）

新增共享常量 `server/shared/capability_namespace.py`：`PLATFORM_NAMESPACE = "taiyim"`。

每条技能 / MCP 在列表接口里新增两个**只增字段**：

```
namespace: string            # "taiyim" | 企业名称（回退企业代码） | ""（原样取自其他平台、未经我们编辑）
provenance: {                # 只有来自其他平台的才有；我方从零写的为 null
  kind: "clawhub" | "url" | "platform",
  label: string,             # 例 "ClawHub steipete/weather"、"github.com/acme/skills"、"taiyim/weather"
  url?: string,              # 可点的出处链接（新标签页打开）
  version?: string,          # 改编时的上游版本
  edited: boolean            # false = 来自（原样）；true = 改自（我们编辑过）
} | null
```

展示规则（三端一致）：标题 `namespace ? namespace + "/" + 名称 : 名称`；副标题 `edited ? "改自 {label} v{version}" : "来自 {label}"`，有 url 时带 ↗ 链接。

归属规则：

| 条目 | namespace | provenance |
|---|---|---|
| 运营端从零写 / 文件夹 / zip / .md / 粘贴的自建技能 | `taiyim` | null |
| 运营端网址导入、未编辑 | `""` | `{url, edited:false}` |
| 运营端 ClawHub 导入 | `""` | `{clawhub, "ClawHub owner/slug", edited:false}` |
| 运营端编辑 ClawHub / 网址技能后的副本 | `taiyim` | `{…, version, edited:true}` |
| 运营端 MCP（全部人工登记） | `taiyim` | null |
| 企业端从平台市场装的 | 继承运营端 | 继承运营端 |
| 企业端自建（从零写 / 文件夹 / zip / .md / 粘贴） | 企业名 | null |
| 企业端网址 / ClawHub 导入、未编辑 | `""` | `{url｜clawhub, edited:false}` |
| 企业端编辑导入技能后 | 企业名 | `{…, edited:true}` |
| 企业端编辑平台市场技能后的副本（新） | 企业名 | `{platform, "taiyim/x"｜"ClawHub o/s", version, edited:true}` |
| 企业自建 MCP | 企业名 | null |

存储：
- 运营端：迁移 `0026_platform_skill_provenance.sql` 给 `platform_skill` 加 `provenance jsonb NULL`。ClawHub 行的出处由 owner/slug 计算，不入列；网址导入与副本写入该列。`namespace` 读取时计算。
- 企业端：存 `skill_catalog.config.provenance`（jsonb，无迁移）；旧行没有时按 `config.origin`（kind=clawhub/url）推导 `edited:false`。企业名在读取时取当前值，不落库（改名立即生效）。平台行在安装 / 更新时把运营端给的 `namespace`、`provenance` 写进 config。

### 4.2 编辑他方技能 → 我方副本（D3）

- **运营端**：ClawHub 卡片「查看」改为「编辑」（只读提示删除）。保存走现有 `POST /api/operation/skill-market/custom`（来源 `editor`），请求附带 `fork_of = 原 skill_id`；服务端读取原条目生成 `provenance`（ClawHub owner/slug、当时版本、edited:true）存入副本；副本按 SKILL.md name 归入自建（同名自建已存在则成为其新版本）。原 ClawHub 条目不动（D3「并存」）。
- **企业端**：平台市场装来的行「查看」改为「编辑」；对话框说明「保存后生成企业自己的副本（企业名/x），平台原件保留」。保存走现有导入接口（`editor`），附 `fork_of = 原 catalog_id`，服务端写入 `config.provenance`（kind=platform，label 取原行 namespace/name 或 ClawHub 出处，version）。两个开关仍可在原件上单独改。
- 企业自己的网址 / ClawHub 导入技能编辑时：保留旧 `origin` 推导出的出处并置 `edited:true`（修复 §2.2 的丢失）。
- **同名提示**：副本与原件 SKILL.md name 相同。成员两个都装时，桌面显示「冲突」状态，安装需「替换」（§4.4）。编辑对话框里提示管理员：如需两者并存给成员用，可改名。

### 4.3 企业端：原地更新 + 「平台有新版本」（D4）

- `PlatformSkillService.install(ctx, ref)`（市场「安装 / 更新」按钮）：同一平台技能已有行时**原地替换**该行的版本、文件、哈希与 config 中的 source_version / namespace / provenance，skill_id、两个开关、专家绑定保持不变；没有时新建，skill_id 用不带版本的 `platform-{平台 skill_id}`。旧数据里同一平台技能有多行时只更新最新一行，其余保留原样。
- 招募 / 方案应用（`install_all`）带固定版本：企业已有该平台技能时**沿用现有行**（不升不降），没有时按固定版本新建。
- 仓储新增 `replace_platform_package`，只允许 `config.source='operator'` 的行；现有 `update_skill` 的平台行守卫不变（§4.7 已做）。
- 「技能管理 · 企业技能」表：平台行有新版本时「来源」旁显示「平台有新版本 v…」，操作列加「更新」（调用同一安装接口）。「平台技能市场」页沿用「可更新 / 更新」。
- MCP：企业端 MCP 市场已有「已启用 · 有更新」，不改。

### 4.4 桌面端：「有更新」与同名冲突（D4）

- Manager `GET /grants/skills` 与 `GET /grants/mcp-servers` 新增 `namespace`、`provenance`；技能另加 `name`（SKILL.md name；平台行取安装时解析的 name，旧行回退 slug，企业行即 skill_id）。Agent manager-client 透传；Agent `GET /api/agent/capabilities/installable-skills` 透传（只增字段）。
- 桌面「能力」页加载已装列表时**同时**取两个企业目录（失败不影响已装列表）：
  - 已装行标题显示 `namespace/名称`，副标题显示出处；
  - 目录版本与已装不同 → 行内「有更新 v… 」徽标 +「更新」按钮；
  - 页顶「N 项有更新 · 全部更新」：依次更新；某个 MCP 需要登录时停在那一项并打开登录窗。
- 「添加技能 · 从企业拿」：显示命名空间与出处；状态加「冲突」（本机已有同名技能且不是这一条），按钮「替换安装」。
- Agent 安装企业技能：本机已有**同 SKILL.md name** 的其他技能时返回 `skill_exists`（「本机已有同名技能 x（来自 …）」），`replace=true` 时先撤销那一个再装。同名判断用目录里的 `name`；本机自导入技能的 ref 即 name。
- 生效时机：本机 Agent 每条消息都重建会话并重新读取已装技能 / MCP，所以安装 / 更新后**下一条消息起**可用（同一个对话里也是），正在生成的那条回复不变。文案统一为「下一条消息起…」（2026-11-21 改，原「下一轮对话起」偏保守）。

### 4.5b 更新红点与检查时机（2026-11-21 用户追加）

需求原文：「能力有更新的时候，tab 的分栏标题要有红点提示」「如果客户端更新能力，员工对话能马上用上吗」。用户选定：

| 位置 | 红点条件 |
|---|---|
| 桌面左侧栏「能力」 | 本机已装、企业目录里状态为 `update` 的技能 + MCP 数 > 0（只显示点，不显示数字；数字在能力页顶部「N 项有更新」） |
| 桌面能力页「MCP」「技能」分栏标题 | 该分栏里「有更新」的行数 > 0 |
| 企业端侧栏「技能管理」、「企业技能」标签 | 平台技能市场里 `installed && update_available` 的条数 > 0 |
| 企业端侧栏「MCP 市场」 | 平台 MCP 里 `enabled && update_available` 的条数 > 0 |

检查时机（都是本机 / 浏览器主动拉取，企业端不向用户电脑推送）：
- 桌面：登录后一次（只读目录，登录时刚同步过专家配置）、每 10 分钟、窗口切回前台（距上次检查不足 1 分钟则跳过）。定时与切回时**先同步专家配置**（`POST /api/agent/grants/sync`），再读两个企业目录。能力页读到目录后也写回同一份计数，页面上点「更新」后红点立即消失。
- 企业端：仅 owner / enterprise_admin；进入后一次、每 10 分钟、切回窗口（1 分钟内不重复）；技能管理 / 平台技能市场 / MCP 市场页面读到列表后写回计数。
- 读不到某个目录时保留上次的数字，不让红点忽闪。

管理员配给专家的技能：Manager 每次同步都返回所有授权专家的最新技能包（与专家配置版本无关），所以只要桌面定时同步，企业端「更新」后最迟约 10 分钟（或切回窗口时）专家就拿到新版本，下一条消息起生效。以前只在登录 / 恢复会话时同步，要重新登录才生效。
- 同步会清掉旧版本技能文件，所以**有回复正在生成时跳过这次同步**（只读目录），留给下一次检查；桌面感知不到的后台自动化任务不在此保护内（与登录时同步的现状相同）。

### 4.5 运营端 / 企业端展示

- 运营端技能卡：标题 `taiyim/name`（或无前缀），副标题出处 + 版本；ClawHub 卡出处可点（新标签页）。MCP 目录行显示 `taiyim/ref`。
- 企业端技能表「名称」列显示 `namespace/name`；「来源」列保留类别（平台市场 / 自定义 / 网址 / ClawHub），出处放在名称下第二行。MCP 市场条目显示 `taiyim/` 或企业名前缀。

## 6. 风险

| 风险 | 处置 |
|---|---|
| 原地更新后，按旧固定版本招募 / 应用方案会拿到新版本 | §4.3：已有行沿用，不降级；方案里的版本只在企业还没有这个技能时生效。记录在 §8 |
| 旧数据同一平台技能多行 | 只更新最新一行；其余仍可用，管理员可删 |
| 副本与原件同名，成员同时需要 | 桌面冲突提示 + 替换；管理员可在编辑时改名 |
| 企业改名后前缀变化 | 前缀展示时计算，所有地方同时变；不影响标识 |
| `taiyim` 拼写 | 集中常量，改一处 |

### 10.1 P4 实测（2026-11-20，本机三端 + 真 PG）

- 链路：运营端编辑自建技能出新版本 → 企业端技能表「平台有新版本 v…」→「更新」（skill_id 不变）→ 桌面能力页「1 项有更新」→「全部更新」→ 本机版本变为新版本。
- 编辑他方技能：运营端 ClawHub「Weather」→ `taiyim/weather · 改自 ClawHub steipete/weather v1.0.0`，原件仍在；企业端平台技能「Proactive Agent」→ `太一科技/proactive-agent · 改自 ClawHub halthelobster/proactive-agent v3.1.0`，平台原件仍在。
- 桌面「添加技能」：本机自导入的 `ppt-outline` 与企业 `太一科技/ppt-outline` 显示同名冲突，「替换安装」后只剩企业那个。
- 实测修复（`e4a1e543`）：① 自导入技能与企业技能同标识时被误判为「有更新」，替换时会留下自导入文件——改为只认目录安装为同一项、替换时删自导入文件；② 「添加技能」装完不刷新状态；③ 「平台有新版本 v<12 位哈希>」被来源列截断——徽标与版本号分两行。
- 环境说明：本地测试企业的 tenant_registry 没有企业代码，未设企业名称时企业前缀为空（与原样取自他方的技能看起来一样）；实测前在「设置」填了企业名称「太一科技」。

### 10.2 红点与定时同步实测（2026-11-21，本机三端 + 真 PG，1440×640，真实鼠标点击）

- 企业端：`live-custom-demo` 平台有新版本 → 侧栏「技能管理」与「企业技能」标签出现红点（「1 项有更新」），「MCP 市场」无红点；点「更新」后两处红点立即消失。
- 桌面：企业端更新后，窗口切回前台（距上次检查 ≥ 1 分钟）→ 自动发 `POST grants/sync` + 两个目录请求 → 侧栏「能力」红点（收起侧栏时仍在图标上）；能力页「技能」标题红点、「MCP」标题无红点；行内「更新」后侧栏、标题红点与顶部横条都消失，提示「下一条消息起用新版本」。
