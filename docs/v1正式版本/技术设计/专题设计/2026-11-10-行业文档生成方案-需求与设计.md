# 行业文档导入自动生成解决方案 — 需求与设计（草案）

> 状态：**草案，待确认**。本文只做需求细化与方案设计，未开始编码。
> 口径依据：v1 概要设计 00 / 04 §6.2.1 / 05 F03·F07·F10 / 03 §9.7；AGENTS.md §3.2、§3.4、§3.5、§8、§10。

## 1. 目标与边界

**目标**：运营端和企业端都能上传行业文档，由 AI 分析并生成一份行业解决方案（专家组成、协作说明、交付要求），经人工审核后发布，并通过现有「应用方案 → 授权 → Agent 同步」链路装载给 AI 员工。

**已确认决策（2026-11-10 用户确认）**

| # | 决策 |
|---|---|
| D-A | 两端同期：运营端和企业端同时建设，共享一个生成核心 |
| D-B | 两层方案池：平台公共池（运营端持有）+ 企业私有池（企业端持有）。运营端**可以看到**企业私有池，并可**复制**成公共池方案 |
| D-C | 企业不能直接改公共池方案，只能「复制成私有副本」再改 |
| D-D | 文档支持 Excel / PPT / Word / Markdown / HTML / TXT 等；涉及企业敏感信息的内容必须人工审核后才能保密处理或发布 |
| D-E | 方案可包含 Skill、知识种子、连接器依赖、可运行制品（脚本、Web），生成时统一封装，目标是拆箱即用 |
| D-F | 客户电脑环境不满足时必须有补救：B 私有目录自动安装（用户确认）、C 分步引导、D 降级运行，三档都做 |
| D-G | 运行时（如 Python）**首次需要时下载**，不打进安装包；运营端新增「运行环境镜像」管理页，企业可配自己的内部镜像 |
| D-H | 脚本纳入范围（由「保证用户不会因环境问题运行不了脚本」推断） |
| D-I | 运营端可读企业私有方案正文，但公司名、部门名、人名、关键金额必须脱敏；脱敏由企业端在返回前完成，企业管理员确认后方案才对运营端可见（2026-11-10 确认） |
| D-J | 运营端读取并复制企业私有方案，用于提炼优化后进入公共池；每一步双侧审计（已确认，跨端契约获批） |
| D-K | 旧格式 .doc / .ppt / .xls 支持：隔离 worker 内用 LibreOffice 无界面转换为新格式后再解析 |
| D-L | 网页链接抓取与图片/扫描件识别本期做，抓取需防 SSRF；图片识别提供 **A 专用 OCR 服务 / B 多模态模型** 两种可插拔方案（见 §3.8），默认值由 P0 对比后定 |
| D-M | 生成模型由使用者选择，范围限定在自己已付费、已授权的模型内；提示词分「平台版本化模板」与「使用者补充说明」两层，补充只能追加不能覆盖规则 |
| D-N | 新增共享契约（`components`、`requirements`、镜像目录投影、环境汇总上报）获批；发布顺序：先升级 Manager 和 Agent，Operator 再发布带新字段的方案包 |
| D-O | 首期支持 macOS arm64、Windows x64；Linux 暂不支持 |
| D-P | 下载源顺序：本机已有满足版本则不下载 → 企业镜像 → 平台镜像 → 官方上游；默认允许直连官方上游；上游下载仍须匹配目录登记的 sha256 |
| D-Q | 脚本运行阶段网络策略选 B：只做首次运行确认，沿用现状；不做运行时禁网与域名放行 |
| D-R | 生成核心中「理解 / 综合 / 分类 / 标注」由**服务端 AI Agent** 承担；Agent 以共享运行时内嵌在 Operator 与 Manager，两端共用同一 Agent 定义与工具集 |
| D-S | Agent 的模型配置由**宿主服务**解析注入（Operator = 平台模型 + 内部额度；Manager = 企业授权模型 + 企业额度）；Agent 不发现、不持有密钥，范围限定已授权、已付费模型 |
| D-T | 服务端 Agent 使用 **Pi SDK**（与 `server/agent_service` 同版本），**每个生成任务起一个 Node 子进程**（`server/solution_authoring_worker`）：Python 宿主经 stdin 传任务与注入的模型配置，经 stdout 收结构化结果；只注册受控 custom tools，不启用 bash / 文件工具；不新增监听端口与跨系统通信面（2026-11-12 确认） |
| D-U | 首期交付 = 运营端端到端纵切（上传 → 生成 → 草稿 → 审核 → 发布到 `catalog_template`）；实施计划见 `2026-11-12-行业文档生成-运营端纵切-实施计划.md` |
| D-V | 图片识别首期只实现方案 B 多模态 + 统一 `ImageRecognizer` 接口；OCR（方案 A）后续接入 |
| D-W | 验证：自动化测试用 Pi faux provider；P0 对比使用用户提供的真实模型与 3 套样例资料 |

**非目标（本期不做）**
- AI 自动发布，一律草稿 → 人工审核 → 发布。
- 会话内容参与生成，会话内容不上传。
- 企业直接修改平台模板。
- 平台方案升级后自动合并到企业副本，只做「有新版本」提示。
- 脚本运行时的禁网沙箱与域名放行（D-Q，后续另议）。
- Linux 桌面端（D-O）。

## 2. 现状与缺口

| 项 | 现状 | 缺口 |
|---|---|---|
| 方案真相 | Operator `catalog_template`（`solution_template`），状态 draft/published/unpublished，版本化 | 只能手工注册，没有文档生成 |
| 企业端 | 只能应用平台方案成 `solution_instance` | 没有企业自有方案真相，也没有复制副本 |
| 方案包 | `SolutionPackage`：协调专家、有序专家、协作说明、工作流 Skill 引用、交付要求；**不含租户知识 ID、成员/部门 ID** | 无需改 |
| 文档解析 | `manager_service/document_parser.py` 支持文本类、HTML、docx、pdf | **不支持 pptx / xlsx**；Operator 侧没有解析能力 |
| 装载 | apply → `member_grant` → Agent 同步并冻结快照，已通 | 需要让 apply 能识别「私有来源」 |

## 3. 总体设计

### 3.1 共享生成核心 `server/shared/solution_authoring/`

两端复用同一套代码，只在「草稿存放位置」和「调用哪个模型」上不同。其中「分段摘要 → 行业综合 → 部件分类 → 敏感标注」由**服务端 AI Agent 生成内核**承担（见 §3.2），解析、分块、schema 校验、签名与持久化仍由确定性代码负责。

```
上传文档 → 解析成文本(分块+来源定位) → Agent 分段摘要(带证据引用)
        → Agent 行业综合(角色/流程/术语/交付物) → 生成 SolutionPackage 候选
        → Agent 部件分类 + 敏感信息扫描(规则 + LLM 标注) → 草稿(ready_for_review)
```

- 输出严格遵守现有 `SolutionPackage` / `ExpertTemplateDetail`（`extra=forbid`），生成结果必须通过 schema 校验，否则重试后标记失败，不落半成品。
- 每个生成项带 `evidence`（来源文档 + 片段位置），审核人可追溯。
- 长文档按 map-reduce 分块，生成走异步任务（任务状态：`queued → parsing → analyzing → succeeded | failed`；成功后草稿进入 `ready_for_review`），带 token 预算上限。
- 解析层：把 `document_parser` 抽到 `shared`，补 `.pptx`（zip+xml）、`.xlsx`（zip+xml，按 sheet 输出）；Manager 的知识库入库改为引用共享实现，行为不变。
- 图片 / 扫描件：独立图片、扫描 PDF、docx / pptx 内嵌图片统一经 `ImageRecognizer` 识别（OCR 或多模态二选一，见 §3.8），输出同构文本块后再分块。

### 3.2 服务端 AI Agent 生成内核

**定位**：把 §3.1 中需要理解与判断的环节（分段摘要、行业综合、部件分类、敏感标注）交给一个部署在服务端的 AI Agent 执行。Agent 是控制面内部的生成执行体，**不是第四个端**：不承载会话、不向用户机器入站、不持有跨租户真相、不接触用户本地数据。

**部署形态（D-T）**：Agent 基于 Pi SDK，代码在 `server/solution_authoring_worker/`（Node）。宿主（`operation_service` / `manager_service`）的任务 worker 领取任务后，经共享的 `server/shared/solution_authoring/runner.py` **为每个任务起一个 Node 子进程**：stdin 传任务与模型配置，stdout 收结构化结果。子进程属于宿主的部署单元，不监听端口。同一份 Agent 定义（system prompt、工具集、输出 schema、预算策略），两个宿主各自注入模型配置与租户上下文。

- 为什么是宿主内子进程而不是独立服务：不新增跨系统通信面与所有权边界（AGENTS §3.2 / §3.4 窄通信面）；模型凭据只在宿主服务内解析，经 stdin 交给子进程，不跨网络传递、不落盘、不进环境变量。
- 子进程隔离：每任务临时空目录作工作目录；Pi 的 extensions / skills / 上下文文件发现全部关闭；只注册受控 custom tools，不启用 bash / read / write / edit。
- 后续若生成量增大，可在**同一部署单元内**拆出独立 worker 进程（同库、同服务身份），仍不新增跨系统边界；不建议做成独立的「生成服务」对外暴露。

**模型配置从当前服务获取**：

| 宿主 | 模型来源 | 额度 | 注入内容 |
|---|---|---|---|
| `operation_service` | 平台 Provider/模型目录（`platform_provider` / `platform_model`）+ 内部 NewAPI Relay | 平台内部额度 | `base_url`、`api_protocol`、`model_id`、短期 relay token、能力参数、预算 |
| `manager_service` | Operator 平台目录只读投影 + 企业授权（`TenantProviderAccess` / `resolve_tenant_access`） | 计入企业 | 同上，另带 `tenant_id` 与 `allowed_model_ids` 约束 |

- Agent **不发现、不持有**模型密钥；模型范围限定在宿主服务已授权、已付费的模型内（D-M）。
- 使用者在前端选择的模型，只是「从宿主可用集合中指定一个」；宿主校验通过后注入。
- relay token 短期、限定 model/tenant、最小权限；日志与审计只记 `model_id` / `provider_code`，不记 token。
- 密钥不下发到用户端 Agent，不写入草稿或方案包。

**Agent 运行模型**：

```text
规划（拆解行业理解任务）
  → 取证（读取已解析分块 / 检索定位 / 必要时抓取或对低置信度图片补识别）
  → 起草（按平台提示词模板 + 使用者补充说明生成结构化候选）
  → 自检（schema 校验、证据覆盖、敏感标注完整性、预算）
  → 修订（不通过则定向重试，超过次数标记失败）
  → 输出（SolutionPackage + components + requirements + evidence + sensitive_findings）
```

- 提示词分两层（D-M）：平台版本化模板 + 使用者补充说明；补充只能追加，不能覆盖规则。
- 工具集：文档分块读取、证据检索与定位、受控网页抓取（防 SSRF）、图片补识别 `recognize_image`（按配置走 OCR 或多模态，见 §3.8）、知识库检索（可选，限企业授权范围）、schema 校验器、敏感扫描器、部件分类器、预算查询。工具最小权限，文档内容一律视为**数据**而非指令（防 prompt injection）。
- 预算与步数：单次任务最大步数、token 预算、超时；超限终止并标记失败，不落半成品。
- 输出必须通过 `SolutionPackage`（含 `components` / `requirements`）schema 校验；失败自动修复重试，仍失败则任务置 `failed`，进入死信与告警。
- Agent 不写业务库：只返回结构化结果与证据，由宿主服务落库、记录审计。
- 会话/执行内容不上传：生成输入是用户上传的文档（本就存在本端），输出是方案草稿；不触碰会话内容。

**两端共用**：

- 同一 Agent 定义、同一套工具、同一 schema 与预算策略；差别只在宿主注入的模型配置、租户上下文、草稿落库位置与审计。
- 运营端：生成公共池方案，模型走平台内部额度。
- 企业端：生成私有方案，模型走企业 Relay 额度，租户隔离。
- 生成后的审核、发布、共享、装载链路不变。

### 3.3 对象与状态

```
solution_source_document   上传的原始文档（同端存储，保留期可配）
solution_generation_job    一次生成任务
solution_draft             方案草稿：package(jsonb) + evidence + 状态
solution_sensitive_finding 敏感信息发现项：类型/位置(脱敏展示)/处理结果
solution_review_event      审核与操作审计
```

草稿状态：`draft → generating → ready_for_review → in_review → approved → published`，另有 `rejected`、`archived`。已发布版本不可变，修改即新版本。

- **平台侧**：发布 = 写入现有 `catalog_template`（`solution_template`），公共池沿用现有 `visible_scope`。
- **企业侧**：发布 = 写入新表 `enterprise_solution`（tenant 作用域，`ENABLE + FORCE RLS`，经 TenantContext 访问）。字段含 `origin`（`generated | forked | promoted_in`）、`source_ref`（来自哪个平台方案/版本）、`confidentiality`（见 §5）。
- 两端草稿表结构一致、物理分库，不跨库读写（AGENTS §3.2）。

### 3.4 装载给 AI 员工（链路不变，仅扩展来源）

1. 企业应用方案时指定来源：`platform`（现状）或 `tenant`（企业私有）。
2. 私有方案内的专家以内联 `ExpertTemplateDetail` 存在，ID 用 `tenant:<uuid>` 命名空间，避免和平台模板 ID 冲突；展开成 `employee` 的逻辑复用 `apply_solution`。
3. 授权仍用 `member_grant`（部门/成员），Agent 同步和快照冻结不改。
4. 文档里的企业内部知识**不进方案包**；企业端生成时可勾选「同时导入企业知识库」，走现有 knowledge intake，由 employee knowledge binding 绑定。

### 3.5 方案包部件清单 `components`

`SolutionPackage` 新增 `components[]`，每个部件声明类型、版本、内容哈希和环境需求（§3.6）。新增字段属共享契约变更。

| 部件类型 | 内容 | 装载方式 | 现状 |
|---|---|---|---|
| `expert` | 专家模板 | 沿用 apply_solution 展开为 employee | 已有 |
| `skill_text` | 文本 Skill（`SKILL.md` + `references/*.md`） | 沿用签名分发 | 已有 |
| `knowledge_seed` | 种子文档 | 应用时走企业知识入库，再绑定员工，**不携带租户知识 ID** | 需扩展 |
| `connector_requirement` | 依赖的连接器或 MCP 及所需凭据，**只声明不打包服务本体** | 就绪检查生成配置清单，管理员只填密钥 | 需扩展 |
| `artifact_web` / `artifact_script` | 静态 Web、脚本及锁定的依赖文件 | 签名制品，本地运行前经用户确认 | 新增 |

- Skill 现有格式只接受 `SKILL.md` 和 `references/*.md`（`shared/contracts/skill.py:28`），脚本一律走 `artifact_script`，不放进 Skill。
- 制品带 `sha256`，签名沿用 Skill 的 Ed25519 机制；发布后版本不可变。
- 生成核心增加「部件分类」一步，判断文档内容该落成哪类部件；分类和内容都进入人工审核。

### 3.6 环境就绪与补救（拆箱即用）

**原则**：体检和补救只发生在用户本机，Manager、Operator 不入站；任何失败都必须落到补救或降级，不允许死路。

**1. 环境需求声明 `requirements`**（每个部件）
- 运行时与最低版本（python ≥3.10、node ≥20 等）、系统与架构
- 依赖锁定文件及哈希（缺锁定文件的制品不得发布）
- 需访问的域名、磁盘占用
- 需要的连接器或凭据

**2. 本机体检**
- 位置：桌面端 `project_runner` 的检测逻辑扩展，经 Agent 本地接口暴露。
- 结果：`ready`、`fixable`、`blocked`，附结构化错误码。
- 沿用现有「实际执行验证版本」的做法，不靠文件存在判断，并识别 macOS 假 Python 桩。
- 向 Manager 只回传脱敏汇总（就绪人数、错误码计数），不含机器细节、路径或日志。

**3. 补救分级**

| 级别 | 触发 | 动作 | 权限 |
|---|---|---|---|
| A 免安装 | 随包运行时满足（Node） | 直接运行 | 无 |
| B 私有目录自装 | 缺运行时或版本过低且可补救 | 首次需要时下载便携运行时到 `<app data>/runtimes/<name>/<version>`，建 venv 并装依赖。**先展示将下载的地址、大小、哈希和将执行的命令，用户确认后才执行** | 用户确认，无需管理员权限 |
| C 引导修复 | 需要管理员权限，或 B 失败（系统 Python、Xcode 命令行工具、杀毒拦截等） | 按系统展示分步指引，带复制按钮和「重新检测」；**绝不静默提权** | 用户手动 |
| D 降级运行 | 最终仍不满足 | 只启用文本部件（专家、Skill、知识），明确告知哪些功能不可用及原因 | 无 |

**4. 下载源解析顺序**：企业内部镜像 → 平台镜像 → 官方上游（企业策略可禁用）。每一级失败自动换下一级，全部失败进入 C 或 D。

**5. 失败诊断**：错误码固定映射到补救动作，例如 `runtime_missing`、`runtime_too_old`、`download_unreachable`、`hash_mismatch`、`pip_install_failed`、`port_in_use`、`permission_denied`、`disk_full`。日志只在本机分析，不上传。

**6. 安全要求**
- 下载物必须校验目录中的 `sha256`，目录本身经 Ed25519 签名；只允许从目录登记的地址下载。
- 安装限私有目录，不改系统环境变量，不执行目录之外的脚本。
- 现状项目运行**没有沙箱**，只靠首次确认兜底（`clients/desktop/docs/workbench-projects.md:121`）。方案分发的制品风险更高，已决定（D-Q）：首期沿用现状，只做首次运行确认，不做运行时禁网；这是已知风险，所以 P4 的人工逐文件审核、静态扫描、签名校验不能省。

**7. 能保证什么**
- 能保证：每个失败都有对应的补救路径或降级，文本部件始终可用，运营端镜像覆盖不足的方案不能发布（见 §3.7 发布闸门）。
- 不能保证：用户完全断网且无离线包、磁盘已满、企业安全策略拦截下载。这些情况落入 C 或 D，并提示联系管理员。

### 3.7 运营端「运行环境镜像」管理

**所有权**：镜像目录真相归 Operator（oper 库）。Manager 拉取后保存 tenant 可见的只读投影；Agent 经 Manager 同步，沿用 F03、F10 的方向，不向用户机器入站。

**数据对象（oper 库）**

```
runtime_artifact   运行时制品：runtime(python|node…)、version、os、arch、url、sha256、size、signature、
                   upstream_origin、status(draft|enabled|disabled|deprecated)
package_mirror     依赖源：kind(pip|npm)、index_url、upstream、优先级、凭据引用（不存明文）、status
mirror_probe       探测结果：artifact_id/mirror_id、last_probe_at、status、latency、last_error
env_report_rollup  各企业回传的脱敏汇总：错误码计数、成功/失败次数（无机器明细）
```

**制品入库**
- 「从上游导入」：Operator 从官方发布地址拉取，校验上游公布的哈希，存入平台对象存储，再计算自有 `sha256` 并签名。
- pip、npm 使用成熟的代理缓存服务（部署选型待确认），Operator 页面只管理源条目与探测，不自己实现 registry。

**页面（`web/operation/`，新增「运行环境镜像」）**
- 运行时制品列表：运行时、版本、系统/架构、状态、健康度。
- 覆盖矩阵：运行时 × 系统 × 架构，无 `enabled` 制品的格子高亮缺口。
- 依赖源（pip、npm）管理与「立即探测」。
- 导入、启用、停用、弃用；弃用时提示仍引用该版本的方案。
- 回传汇总看板：各错误码占比、下载失败率，用于发现镜像问题。

**发布闸门**：方案声明的运行时，在镜像目录里必须有覆盖目标系统/架构的 `enabled` 制品，否则不能发布。这是「用户不会因环境问题跑不了」的硬保证之一。

**企业侧覆盖（Manager，`owner`/`enterprise_admin`）**
- 配置企业内部镜像地址（运行时、pip、npm）和离线包位置。
- 策略开关：`allow_platform_mirror`、`allow_upstream_fallback`。
- 配置存 tenant 数据空间，经 TenantContext/RLS 访问；Agent 同步时随授权配置下发。

### 3.8 图片识别：OCR 与多模态两种方案

独立图片、扫描 PDF、docx / pptx 内嵌图片，都先抽成图片，再经统一的 `ImageRecognizer` 接口识别，输出同构的 `RecognizedText`（文本块 + 来源定位 + 置信度 + 类型：文字 / 表格 / 图表）。分块、证据、敏感扫描、Agent 下游不感知用了哪种方案。识别放在「解析」阶段统一预处理，Agent 只读识别后的分块；工具 `recognize_image` 仅用于对低置信度图片按需补识别。

**方案 A：专用 OCR 服务**（不依赖模型视觉能力）

```text
预处理(纠偏/去噪/限尺寸) → OCR 引擎(文本块+坐标+置信度) → 版面还原(段落/表格) → 分块
```

- 部署：自部署开源引擎（如 PaddleOCR / Tesseract），放在与文件转换同级的隔离 worker 或独立容器；也可接云 OCR（图片出内网，保密约束同方案 B）。
- 优点：单页成本低且稳定；可私有化，图片不出内网；输出确定、可复现；Agent 用任何文本模型即可。
- 缺点：只出文字，不理解图表 / 流程图 / 架构图含义；表格与版面需额外还原；多一个服务要运维扩容；手写、低质量扫描依赖引擎。
- 适合：扫描件、合同表格、文字为主的截图，保密要求高的企业。

**方案 B：多模态模型识别**（依赖模型视觉能力）

```text
预处理(分页/缩放/切图) → 视觉模型(宿主注入; 转写+图表描述) → 结构化为 RecognizedText → 分块
```

- 实现：复用 §3.2 的模型配置注入，不新增服务。所选模型须在 `capabilities` 声明 `supports_vision`（并在已授权、已付费范围内），宿主创建任务时校验，不满足则此方案不可选。
- 优点：零新增运维；能读懂图表、流程图、架构图并输出语义描述；复杂版面和表格还原较好。
- 缺点：按图计 token，成本高；可能漏字或幻觉，须配置信度与抽检；速度慢，受模型限流；图片内容经 Relay 发往模型上游。
- 适合：流程图、架构图、统计图表、版面复杂的资料。

**对比**

| 对比项 | A 专用 OCR 服务 | B 多模态模型 |
|---|---|---|
| 新增部署 | 需要（OCR worker / 容器 + 容量监控） | 不需要 |
| 文字准确率 | 印刷体高、稳定；手写依赖引擎 | 较高，偶有漏字 / 幻觉 |
| 图表 / 流程图语义 | 不支持，只得到零散文字 | 支持，输出结构与含义描述 |
| 单页成本 | 低、可预估（自有算力） | 较高，随图片大小与模型价格变化 |
| 保密 | 私有化时图片不出内网；云 OCR 则出网 | 图片经 Relay 发往模型上游；企业端使用企业授权模型 |
| 可复现 | 高 | 较低（温度、模型版本影响） |
| 对模型的要求 | 无 | 所选模型须支持视觉 |
| 额度计入 | 自有算力，不计模型额度 | 运营端计平台额度；企业端计企业额度 |

**两种方案共同遵守**

- 识别结果和文档一样是**数据而非指令**：图片文字可能带「忽略以上规则」之类内容，进入 Agent 前按同一套注入防护处理。
- 识别出的文本**必须再过敏感扫描与脱敏**：图片里的公司名、人名、金额同样适用 D-D / D-I。
- 置信度低于阈值的文本块标记 `low_confidence`，审核页提示人工核对，不静默采用。
- 单图识别失败不丢弃：记一条 `image_unrecognized` 发现项交审核人处理；失败比例超阈值则整个任务置 `failed`。
- 限制每任务图片数、单图像素与大小、PDF 页数；超限截断并记录；页数 / token 计入任务预算。

**选择方式与建议**

- 宿主服务配置默认 `image_recognizer = ocr | vision`；创建任务时使用者可在「可用集合」内改选。B 仅当所选模型支持视觉时可选；A 仅当宿主已部署 OCR 服务时可选。
- 接口统一、两种实现都做成可插拔；P0 用同一批真实资料对比准确率、成本、耗时后定默认。倾向：文字为主的扫描件走 A，图表类走 B；按图片类型自动路由作为后续优化，本期先做「二选一」。
- 保密：企业端若保密级别较高，B（及云 OCR）默认需企业管理员显式允许「图片发送到所选模型 / 外部服务」，否则只能用私有化 OCR。

## 5. 保密审核

- 生成时自动扫描：手机号、身份证号、邮箱、密钥/Token、金额与客户名等，输出 `sensitive_finding`，每项必须处理为 `redacted`（替换）、`removed`（删除）或 `accepted_internal`（确认仅内部使用）。
- **发布闸门**：存在未处理发现项，禁止提交审核。
- **运营端首期口径（2026-11-12 实施调整）**：运营端发布即进入公共池，没有「仅内部」这一档，处理动作为 `redact`（替换）/ `remove`（删除）/ `accept_public`（确认可公开）；Agent 备注与未识别图片这类提示项用 `acknowledge`（已知悉）。发现项状态为 `open / redacted / removed / accepted_public / acknowledged`。提交审核、通过、发布三处都检查闸门。`accepted_internal` 只属于后续的企业端私有方案。详见实施计划 §7。
- **公共池闸门**：进入公共池的草稿不得有 `accepted_internal` 项，且需 `system_admin` 逐项确认保密审核通过，并记录审核人与时间。
- 企业私有方案：含 `accepted_internal` 项时，发布需要**不同于编辑人**的第二位管理员确认。
- 方案包内容进入日志或审计时只记摘要，不记正文；错误体不含文档内容。

## 6. 运营端查看、提炼与复制企业私有方案

跨端契约已获批（D-J）。

- 方向：**Operator → Manager 服务间调用**（现有方向，不涉及向用户机器入站）。
- **可见性**：企业管理员先确认脱敏结果，并把方案标记为 `shared_with_platform`；未标记的方案，运营端只能看到列表元数据（租户、名称、版本、状态），读不到正文，也不可复制。
- **脱敏位置**：在 Manager 完成。公司名、部门名、人名、关键金额替换为占位符（如 `[公司A]`、`[金额]`），原文不出租户。自动识别可能漏检，所以企业管理员的确认是必经步骤。
- **提炼优化流程**：
  1. 运营人员读取已脱敏方案，复制成一份**独立的平台草稿**（`origin=promoted`，记录来源 tenant 与方案版本）；
  2. 在草稿上合并同类专家、补充通用流程、去掉企业特有内容；
  3. 走 §5 的公共池闸门，由 `system_admin` 审核发布。
- **存储**：Operator 不持久化租户原文。提炼用的草稿只含脱敏内容，属平台自有数据；复制后与原私有方案互不影响。
- **审计**（只记事件，不记正文）：
  - Manager 记录：哪位运营人员、何时、读取或复制了本企业哪个方案和版本；
  - Operator 记录：谁、何时、读取或复制了哪个租户的哪个方案，并在草稿中保留来源；
  - 企业可查看被平台访问的记录，也可撤销 `shared_with_platform` 标记（撤销后不能再读取，已复制的脱敏草稿不受影响，需在界面上说明）。
