## 1. 目标与边界

### 1.1 目标

1. **招募即可用**：员工落库时一定带有企业可用的模型，未选模型的招募请求整单失败、不留半成品。
2. 9 项能力都落在正确端：R1–R5 在 Operator，R6–R9 在 Manager；Agent 侧不新增业务逻辑，只复用既有「不可用」提示。
3. UI 不新增页面，统一放进现有列表的行菜单 / 抽屉 / 确认弹窗。
4. 危险操作（删除草稿、重置负责人凭据、删除企业）均二次确认，删除企业要求输入企业名称确认。

### 1.2 非目标（本期不做）

- 行业方案「断点续跑」（解析 / 识别中间结果不持久化，见 §2.1，本期「继续生成」= 用原资料重新跑一次）。
- 企业级「默认模型」自动兜底（招募已强制选模型，不再需要）。
- 标签字典的独立管理页（本期标签为自由文本 + 联想）。
- 远程清理用户本机数据（红线：Operator / Manager 不向用户机器入站）。
- 修改平台角色模型（`system_admin | system_operator` 维持现状，仅对删除企业新增 `system_admin` 限定）。

## 3. 方案设计

### 3.1 R1 未完成草稿：删除 / 继续生成

**定义「未完成」**：`status ∈ {draft, generating, ready_for_review, rejected}`（即未进入审核且未发布）。列表默认显示全部未归档，新增顶部筛选「未完成 / 全部」（默认「未完成」）。

**列表行菜单（`⋯`）——按状态显示，不可用的不出现，不放灰按钮：**

| 草稿情形 | 显示的操作 | 行为 |
|---|---|---|
| `draft` 且从未成功（无 package） | 继续生成、删除 | 继续生成 = 用原资料重新生成（新幂等键） |
| 上次任务 `failed`（列表展示「生成失败」+原因 tooltip） | 继续生成、删除 | 同上；无资料时提示「请先上传资料」并跳详情 |
| `generating` 且正常 | 查看进度 | 跳详情 |
| `generating` 且疑似卡住（见下） | 取消生成、删除（取消后） | 取消后回到可编辑态 |
| `ready_for_review / rejected` | 继续编辑、重新生成、删除 | 继续编辑 = 跳详情；重新生成会覆盖当前正文（确认弹窗说明） |

**「删除」语义**：沿用现有 `DELETE /drafts/{id}`（软删除 = 归档 + 清原件），UI 文案统一为「删除」，确认弹窗说明「删除后列表不再显示，已上传资料将被清除，操作不可恢复」。审计记录按现有只追加设计保留。**不做物理删除**（审计表无 CASCADE 且只追加，见 §2.1）。

**「取消生成」（新）**：
- `POST /drafts/{id}/generation/cancel`（幂等键可选）：在草稿行锁内把活跃任务置 `failed`、`error_code=cancelled`，草稿按现有失败回退规则回到 `draft` / `ready_for_review`；`lease_owner` 清空。
- 正在执行的 worker 在下一次续租时发现任务已非活跃 → 放弃写结果（现有路径，`solution_authoring_jobs.py:177-179,238`；`complete_job` 也会因任务不再归属而拒写，`solution_authoring_repository.py:305-310`）。
- **取消时结束子进程（新）**：现在租约丢失后生成子进程仍会跑到结束或超时（最长 15 分钟，`server/shared/solution_authoring/runner.py:120`），而 worker 默认并发为 1（`solution_authoring_dependencies.py:91-95`），取消后马上「继续生成」会一直排队。因此把「租约已丢失」信号传给 runner，由它结束子进程（复用已有 `_kill`，`runner.py:155`），最迟一个心跳周期（约 30 秒）内释放 worker。
- 不新增 `cancelled` 状态枚举（用 `failed + error_code=cancelled`，避免改状态 CHECK 约束），已决定 #2。
- 「疑似卡住」判定：任务 `queued` 超过 10 分钟仍未被领取，或 worker 未启用（列表接口回 `worker_available=false`）。正常生成中只显示「查看进度」，避免误操作。

**列表接口补字段**：`DraftOut` 增加只读 `latest_job: {status, error_code, created_at, started_at, finished_at} | null`（不含错误详情原文；任务表没有 `updated_at` 列，「排队超过 10 分钟」按 `created_at` 判断）；仓储事务接口新增「批量取各草稿最近任务」一个方法（PG 用一次子查询，内存实现同步），避免 N+1。

### 3.2 R2 运营端配置专家不选模型（模型只在企业端选）

**原则**：专家模板只描述「这个岗位做什么」（名称、岗位提示词、技能、知识、头像、标签等）；「用哪个模型」完全由企业在招募时决定（规则见 §3.6）。运营端没有任何「推荐模型」或「默认思考档位」。

**运营端（Operator）**
- 前端：注册表单删除「大模型服务 / 模型」「默认思考等级」两个下拉（`ExpertTemplateFields.tsx:56-75`）；模板详情删除模型与思考档位编辑（`TemplateOverview.tsx:129-189`）；目录卡片删除「模型」一栏（`CatalogPage.tsx:68,103`）。表单少两项必填，更短。
- 后端：`catalog_schemas.py` 注册 / 编辑 / 响应体删除 `platform_model_ref` 与 `thinking_level`；删除注册、编辑、发布时的模型校验（`catalog_service.py:219-224,308-346,393-438`）；拉取列表不再按模型跳过模板（删 `:603-605`）；`_backfill_expert` 不再往 `recommended_config` 写模型（`:471-492`）。
- 行业方案发布：生成出的专家注册时**不带模型**（改 `solution_authoring_service.py:353`）。草稿上的「生成模型」只用于生成文档本身，与员工模型无关（同步改 `solution_authoring_schemas.py:41` 的说明）。
- 存量数据：迁移脚本清除 `catalog_template.payload` 中的 `platform_model_ref / thinking_level`；已招募员工的模型存在 Manager 的 `employee` 表，**不受影响**。

**跨端契约**：`ExpertTemplateDetail` 删除 `platform_model_ref`（`server/shared/contracts/crosstier.py:112`，**高风险，共享契约**）。分两步：先改为可选并由 Manager 忽略 → 两端都不再使用后删除字段。

**企业端（Manager）**
- `_filter_templates_by_model_access` 与 `_filter_solution_packages_by_model_access` 删除（`routes_recruit.py:122-155`）：模板、方案与模型无关，不再按企业模型白名单隐藏；企业能选哪些模型仍由 `allowed_model_refs` 控制（在招募弹窗的模型下拉里体现）。**这两处提前到 P1 随 R6 一起做**（只改 Manager，不动契约）：否则 P1 上线后会出现「模板自带的模型企业没开通，模板被隐藏」，而那个模型其实已不再使用。
- `recruit_service._resolve_platform_model` 删除（`recruit_service.py:64-78`）：员工模型与思考档位**只**来自招募请求（§3.6）。

**Agent / 桌面端**：Agent 人才市场的 `model_name` 取自模板的 `platform_model_ref`，取不到时已回落为空字符串（`server/agent_service/src/manager-client.ts:700-702`），不会报错；桌面端人才市场卡片与详情需隐藏空的「模型」一栏（P2，S）。

**顺带影响**：「平台模型下架」专题里统计「有多少模板引用该模型」的部分不再需要，下架影响面只看企业端员工。

### 3.3 R3 发布范围（行业 / 标签）

**数据**
- Operator `enterprise_account` 新增 `industry text NULL`（单选，取自固定行业字典，复用行业方案的行业取值）与 `tags text[] NOT NULL DEFAULT '{}'`（自由文本，最多 10 个，每个 ≤ 20 字）。
- 在「企业开通」表单与账号行菜单「编辑企业信息」（新）里维护。
- `visible_scope` 结构化（Pydantic 严格模型，`extra=forbid`）：

```json
{ "mode": "all" }
{ "mode": "limited", "industries": ["制造业"], "tags": ["华东", "KA"] }
{ "mode": "none" }
```

- 匹配规则：`mode=all` 全可见；`limited` 时 **行业命中 或 标签任一命中** 即可见（两者都空视为非法）；`none`「暂不开放」：模板保持已发布，任何企业都看不到（2026-11-14 变更，替代 main 上的「隐藏」，不必下架即可暂停对外）。
- 迁移 `0021`：main 上的 `{"hidden": true}` 先迁移为 `{"mode":"none"}`；其余旧的空 / 自由 JSON 一律迁移为 `{"mode":"all"}`。
- 改为「暂不开放」算收窄（各企业已招募的员工停用），从「暂不开放」改为任何范围都算放开（自动恢复）。

**拉取与过滤（Operator 单写者，Manager 不拿企业属性真相）**
- `GET /api/operation/catalog/pull/expert-templates` 与详情 pull 增加必需的 `tenant_id`（与 `list_platform_catalog` 同一服务身份校验方式，`operator_catalog.py:150-158`）；Operator 按该 tenant 的行业 / 标签过滤。
- **详情 pull 也校验范围**：防止 Manager 绕过列表直接按 id 招募。
- **方案内的专家也单独按各自范围过滤（已决定 #8）**：Operator 下发方案详情时，只带上对该 tenant 可见的专家，另附 `hidden_expert_count`；Manager 应用方案时只展开可见的专家，弹窗提示「另有 N 个专家不在本企业可见范围，不会招募」，其余照常展开（已决定 #17）；方案内专家对本企业**全部**不可见时，该方案不在方案列表中展示。
- 运营端发布方案时，若方案的范围比其中某些专家的范围宽，发布弹窗提示「以下专家在部分企业不可见：…」，不阻止发布。

**范围收窄后已招募员工：停用（已决定 #7）**
- 触发：Operator 修改范围后发 `CatalogReleaseNotify`（契约已有 `action=visibility_changed`，`server/shared/contracts/crosstier.py:69`，不新增取值；收端 `server/manager_service/routes_catalog_notify.py:27`）作为提示。收端现在只记日志，需新增对账：收到通知后，按 `tenant_registry` 逐个 tenant 遍历（与用量上报同一方式，`server/manager_service/usage_delivery_service.py:173-179`），在各自 TenantContext 内查是否有来源于该模板的员工，有则带 `tenant_id` 重新 pull 并对账（不绕过 RLS 做跨租户查询）；另在企业管理员打开人才市场 / 专家列表时对本 tenant 再对账一次，没收到通知也能兜底（Manager 没有定时目录刷新）。真相仍来自 pull（05 §5.1），不新增跨端通道。
- 处理：本 tenant 内 `source_template_id` 指向已不可见模板的员工（单独招募和方案展开的都算）→ `status=paused`（已有状态，`0014_employee_status.sql:16`），新列 `status_reason='catalog_scope_revoked'`。
- **核查补充 · 原本就不是启用状态的员工**：范围收窄时员工若已被管理员手动暂停，同样要挡住「启用」和「复制」，但范围恢复后不能替管理员启用。因此 `status_reason` 用两个取值：`catalog_scope_revoked`（原为 active，被自动暂停，恢复时回到 active）与 `catalog_scope_revoked_keep_paused`（原本就不是 active，状态不变，恢复时只清空原因）。两者都使「启用」返回 409、不能复制。
- **核查补充 · 协调专家不可见**：应用方案要求协调专家必须在展开的专家里（`server/manager_service/recruit_service.py:279`，否则 409）。所以方案的协调专家对本企业不可见时，该方案同样不展示；运营端发布方案时对「协调专家范围比方案窄」给出警告。
- **核查补充 · 拉取接口的身份校验**：现在目录拉取只校验通用服务令牌，不绑定 tenant（`server/operation_service/routes_catalog.py:180-183`）。加 `tenant_id` 参数的同时，改成与平台模型目录相同的「签名服务身份 + tenant 绑定」（`server/manager_service/operator_catalog.py:150-158`、`server/operation_service/routes_platform_provider.py:230`），否则任一持通用令牌的调用方可冒用别的 tenant 查看范围外模板。
- 生效：非 `active` 员工不出执行快照（`server/manager_service/snapshot_service.py:106`）→ Agent 下次 sync 把该员工标为不可用（现有 partial sync，`server/agent_service/src/http/server.ts:2228-2265`）。进行中的执行不中断，用户本机历史会话保留。
- 企业端：列表显示「已停用 · 不在发布范围」；「启用」返回 `409 template_out_of_scope`；不能复制。
- **范围恢复后自动恢复（已决定 #15）**：对账发现模板重新可见时，只把 `status_reason='catalog_scope_revoked'` 的员工恢复为 `active` 并清空原因；管理员手动暂停的员工不动。
- **复制品不停用（已决定 #16）**：复制品 `source_template_id=NULL`，已是企业自有专家，不参与范围对账；被停用的员工本身不能再复制（`409 template_out_of_scope`）。
- **通知企业管理员（已决定 #19）**：每次对账有员工被停用或自动恢复时，向本企业 owner / enterprise_admin 发一条站内通知，列出受影响员工与原因。复用现有收件箱表与列表（`server/manager_service/in_app_notification_service.py:69`），新增 Manager 内部投递方法（现有只有 Operator 来源的 `deliver_from_operation`，`:21`）；同一次对账合并为一条，按「模板 + 对账批次」幂等，避免重复。

**UI**：发布弹窗增加「发布范围」单选：`全部企业` / `指定行业或标签` / `暂不开放`（选「暂不开放」显示一句说明：模板保持已发布、企业都看不到）；选后者出现两个多选（行业、标签，标签带已有值联想），底部实时显示「预计可见企业：N 家」（新增 Operator 内部计数接口）。

### 3.4 R4 企业管理员密码重置

- **入口**：企业账号列表行菜单新增「重置管理员密码」，自动带入该企业，**不再手输 `enterprise_id`**；原企业开通页的独立重置表单下线（同一能力只留一个入口）。
- **流程**：确认弹窗（说明「将生成新的一次性登录凭据，负责人旧密码立即失效、已登录会话被踢下线、**通行密钥等二次验证被清除**，首次登录须修改密码」）→ 调现有 reset 接口 → 复用 `BootstrapSecretDisplay` 展示一次（复制按钮 + 「关闭后不可再查看」）。
- **后端补强**：
  1. Manager `sync_owner_bootstrap_in_session` 在「替换已有账号」分支同事务吊销该 owner 的全部会话。现有 `auth_sessions.revoke_user` 会另开连接（`auth_sessions.py:61-68`），不能直接复用，需在同一 session 内执行同样的 UPDATE。
  2. Operator 重置写 `operation_audit_event`（actor 取 JWT 主体，不再写死 `"system_admin"`，`routes_admin.py:~303`）。
  3. 回执明文：`completed` 后保留 24 小时供网络重试重放，过期后清空 `bootstrap_secret_ciphertext`（下次访问时惰性清空，只清 `completed` 的回执）——缓解「Operator 长期持可解密凭据」，已决定 #3。该列现在是 `NOT NULL`（`server/operation_service/migrations/0014_onboarding_receipt.sql:16`），需要一个迁移放开为可空，读取回执的代码同步处理空值；过期后用同一幂等键重放返回 `409 bootstrap_receipt_expired`。
  4. **同时清除二次验证（已决定 #4）**：同一事务删除该 owner 的 passkey（`passkey_credential`，`0013_mfa.sql:45-58`）及其他已登记的二次验证凭据；同时删除该 owner 的第三方登录绑定（`oauth_connection` 与 `auth_identity` 中 provider=oauth 的行都要删，登录会两处都查，`server/manager_service/oauth_service.py:104-125`；已决定 #14）。结果：负责人在企业端网页和桌面端的**全部登录立即下线，必须用新凭据重新登录** → 强制改密 → 企业要求二次验证时重新登记 → 需要第三方登录时重新绑定。审计记录写明「已清除二次验证、已解绑第三方登录」。

### 3.5 R5 企业账号删除

**两步走，避免误删**：只有已「注销」（`closed`）的企业才出现「删除企业」；删除需 `system_admin` + 输入企业名称确认。

**删除语义 = 下线 + 延迟清理（软删除）**

| 端 | 立即生效 | 保留期后（30 天，期内 system_admin 可恢复为 closed，已决定 #9） |
|---|---|---|
| Operator | `operation_status=deleted`（新增枚举值）+ `deleted_at`；列表默认隐藏、筛选可见；吊销该 tenant 的 NewAPI 令牌与用户（`platform_provider_tenant_access.status=revoked`，`relay_token_operation` 记 `revoke`）；人才市场 / 治理汇总不再计入 | 企业名称 / 手机号匿名化；**充值、计量、审计记录保留**（财务与审计合规） |
| Manager | 新服务端点下线租户：`tenant_registry.status=deleted`；吊销全部会话；登录、token 校验、Agent sync、知识库窄通道一律返回 `problem+json code=tenant_deleted` | 后台按 tenant 清理业务数据、RAG workspace、对象存储、Hindsight bank、签名私钥 |
| Agent（用户本机） | 下次访问 Manager 时收到 `tenant_deleted` → 本地提示「企业已删除，无法再同步或登录」；**本地会话留在本机**，不远程删除 | — |

- **注销也真正生效（顺带修复）**：`close` 动作同样调用 Manager 下线（`status=closed`，拒新登录与 sync）。**核查补充**：注销在运营端是终态，不能恢复为正常（`server/operation_service/admin_repository.py:273-277`）；本方案只新增 `closed → deleting → deleted` 与保留期内 `deleted → closed` 两条流转，状态机和 CHECK 约束（`migrations/0003_enterprise_lifecycle_quota_audit.sql:43-44`）同步放开。
- **暂停 / 封禁也联动 Manager（已决定 #10）**：暂停（`suspended`）= 拒绝新登录，已登录会话只能读、写操作返回 `403 tenant_suspended`；封禁（`banned`）= 与删除相同的拒绝行为（`tenant_banned`），但不清理数据，解封后恢复。
- **核查补充 · 「只读」不能按 HTTP 方法一刀切**：用户端向企业端的同步、用量上报、记忆写入都是 POST（`server/agent_service/src/manager-client.ts:225,397,422,426`），退出登录也是 POST。暂停时按「GET / HEAD 放行 + 白名单放行（退出登录、用户端授权配置同步、用量与结算上报）」处理，其余写操作返回 `403 tenant_suspended`。现有验签依赖拿不到请求方法（`server/shared/auth/__init__.py:315-324`），需在 Manager 入口加一层统一检查，而不是改各路由。
- **核查补充 · 暂停期间能否继续用模型**：方案原先没有规定。暂停只限制企业端管理操作的话，成员仍可在用户端继续对话并产生费用。见待决策 #20。
- **核查补充 · 状态端点用管理连接**：业务连接对 `tenant_registry` 只有读权限（`server/manager_service/migrations/0001_tenant_base.sql:123`），写状态与开通接口一样走管理连接（`server/manager_service/routes_tenant.py:46-48`）。
- **核查补充 · 企业代码占用**：企业代码在两端都是唯一约束（Operator `migrations/0001_enterprise_account.sql:50`，Manager `tenant_registry.enterprise_slug`）。删除后保留期内代码仍被占用；保留期清理时把两端的代码 / slug 改成 `deleted-<tenant_id>`，之后才能被新企业复用。
- **核查补充 · 匿名化范围**：除企业账号表外，开通 / 重置回执表也存有企业名称与负责人手机号（`server/operation_service/migrations/0014_onboarding_receipt.sql:13-15`），一并匿名化。
- **核查补充 · 数据清理方式**：Manager 租户表很多且有外键，清理任务按「所有带 `tenant_id` 列的表 + 外键依赖顺序」生成删除清单（从数据库元数据读取，不手写表名单），用管理连接执行，分批、可重试、可重入；作为 P3 的 P0 验证项先在测试库证明「清理后该 tenant 行数为 0，其他 tenant 行数不变」。
- **删除仅 `system_admin`（已决定 #11）**：`system_operator` 只能注销。
- Operator → Manager 新增网关方法 `set_tenant_status(tenant_id, status, reason)`，服务端点 `POST /api/manager/tenants/{tenant_id}/status`（`service_purpose="tenant:lifecycle"`，幂等键必带）。
- Manager 失败处理：Operator 先写本地 `deleting`（中间态）→ 调 Manager → 成功后 `deleted`；失败保留 `deleting` 并在列表显示「删除未完成，重试」。

### 3.6 R6 企业端专家选择模型（招募必选）

**规则（已确认）**：企业招募员工时必须选择模型；未选择，则招募失败、不落库。

**招募单个专家**
- 招募弹窗（现 `RecruitDepartmentDialog`，`MarketplacePage.tsx:349-416`）改为两项：**模型（必填）** + 授权部门。
  - 模型下拉与员工抽屉同源：企业已开通（`allowed_model_ids`）、`published`、价格已知的平台模型。
  - 默认为空，「招募」按钮在选好模型前不可点；企业只有 1 个可用模型时默认选中（已决定 #5）。
  - 思考档位不在招募弹窗出现：招募时留空（即按模型自身默认行为；平台模型能力里没有「默认档位」字段，只有可选档位列表），之后可在员工抽屉里调整（抽屉已支持，`EmployeeConfigDrawer.tsx:72-81`）。
  - 企业一个可用模型都没有：弹窗显示「企业暂未开通可用模型，请联系平台运营」，不能招募。
- 接口：`RecruitExpertRequest` 新增**必填** `model_policy: {provider_ref, model, thinking_level?}`（`thinking_level` 可省略，省略即留空）。
- 后端校验（在写任何数据之前，复用 `employee_config_service._validate_platform_model` 的同一套规则，再加「价格已知」）：
  - 缺少或为空 → `422 problem+json`，`code=model_required`。现有校验函数对不可用模型抛的是 404 / 409（`employee_config_service.py:99-152`），招募路径包一层统一转成下面的 422。
  - 模型不在企业可用范围 / 未发布 / 价格未知 → `422`，`code=model_unavailable`（不透露是「未开通」还是「不存在」，与现有隐私口径一致）。
  - 校验失败时员工、技能安装、授权**都不写入**（校验放在招募事务之前，和现有 grant 校验同位置，`recruit_service.py:209-211`）。

**应用方案（一次展开多个专家）**
- `ApplySolutionRequest` 新增 `expert_models: {template_id: model_policy}`：方案里**需要新建**的每个专家都必须有一项；已招募过、直接复用的专家**可选**（不传 = 沿用当前模型；传了 = 在同一事务里改成新模型，已决定 #12）；复用专家当前没有模型时也必须传。
- 任一新建专家缺模型或模型不可用 → 整单 `422`，`errors[]` 逐个列出 `template_id`，**不部分展开**。
- 弹窗：列出方案里全部专家。需新建的每行一个模型下拉（默认为空）；已招募的预填当前模型、可改，行尾标注「已招募 · 修改会影响正在使用它的成员」。顶部「全部使用同一模型」只作用于新建的专家，避免误改已招募的。
- 改动已招募专家的模型 = 员工版本号递增，Agent 下次 sync 拿到新快照（与在抽屉里改模型同一路径）。

**编辑：允许清空模型（已决定 #6）**
- 员工 PUT 保持现状，允许清空模型（`employee_config_service.py:102-103`）。抽屉里清空时二次确认：「清空后该专家立即不可用，使用它的成员无法再对话，直到重新选择模型」。
- 「待配置模型」筛选与行内「选择模型」按钮作为**常规功能**保留，覆盖历史无模型员工和被清空模型的员工；不自动补模型。
- 模型之后被平台下架，属于「平台模型下架」专题的处理范围，不在本规则内。

### 3.7 R7 复制专家生成企业专家

- **入口**：专家列表行菜单「复制」；弹窗只问一项「新专家名称」（默认「原名称 - 副本」），确认后创建并**直接打开编辑抽屉**。
- **接口（新）**：`POST /api/manager/employees/{employee_id}/copy`，body `{display_name}`，`Idempotency-Key` 必带，owner / enterprise_admin。
- **复制内容**：`persona / model_policy / execution_policy / tools / skills / knowledge_refs / connector_refs / memory_policy（策略） / department_ids / role_title`、当前生效的 prompt 版本、skill 绑定、头像。
- **不复制**：成员授权（`member_grant`，复制品默认无人可用，需重新授权，避免授权悄悄扩散）、员工个人记忆内容、来源模板关系。
- **来源标识**：新增 `employee.origin text NOT NULL DEFAULT 'recruited'`（`recruited | solution | copied | custom`）与 `copied_from_employee_id uuid NULL`；复制品 `source_template_id=NULL`，因此**不占**「同模板只招一次」名额（`0027:35-37`），人才市场「已招募」标记不受影响。
- **核查补充 · 复制要带齐的表**：除 `employee` 行外，提示词版本（`employee_prompt_version`）、技能 / 知识 / 连接器绑定、记忆设置各有独立的表（`server/manager_service/migrations/0014_employee_bindings.sql:21-99`），都要在同一事务里复制，否则复制品打开后配置是空的。
- **核查补充 · 头像要复制文件**：头像表存的是对象存储路径，源专家换头像时会删旧文件（`server/manager_service/employee_avatar_service.py:140-141`）。复制品必须复制一份文件并登记自己的路径，不能共用同一路径。
- **核查补充 · slug 与存量数据**：复制品的 slug 复用现有的去重生成逻辑（`server/manager_service/recruit_service.py:499`）。`origin` 的存量回填：无来源模板的 → `custom`；来源于「应用方案」事件的 → `solution`（`recruit_event.action=apply_solution`，`recruit_service.py:429`）；其余 → `recruited`。
- **编辑**：复用现有员工抽屉与 PUT；列表加来源标签「市场 / 方案 / 企业」。招募来的专家本期也可编辑（现状即可），不加锁。
- 模型：复制品沿用源专家的模型，创建前按 §3.6 规则重新校验；源专家没有模型或其模型已不可用时，复制弹窗增加必填的模型选择，否则复制失败（`422 model_required / model_unavailable`）。
- 新建状态：复制品创建为 `draft`，可直接启用（与现有生命周期一致）。

### 3.9 R9 企业端设置新密码

- **入口**：账号菜单「设置新密码」（R8）。仅对有密码登录方式的账号显示（`GET /api/manager/me` 的 `has_password`，见 §3.8；`/api/auth/session` 不改）。
- **弹窗**三项：当前密码、新密码、确认新密码；新密码下方实时显示规则（规则取自 `GET /api/manager/me` 的 `password_policy`；后端规则是最小长度 + 大写 + 小写 + 数字 + 符号，`auth_password_policy.py:52-66`），两次不一致或与当前密码相同时「确定」不可点。
- **接口（新）**：`POST /api/auth/password`（需登录，任意角色），body `{old_password, new_password}`。
  - 校验当前密码 → 复杂度 → 更新凭据、`must_reset=false`、刷新密码修改时间（复用 `owner_reset` 同一套逻辑，`auth_service.py:242-262`）。
  - 当前密码错误：`422 old_password_incorrect`，写登录审计。**企业端目前没有登录失败锁定机制**（`record_attempt` 只记审计，`auth_service.py:381-391`），所以本接口自带限制：同一账号 15 分钟内输错 5 次后，返回 `429 too_many_attempts`，15 分钟后恢复；计数读登录审计表。登录接口本身的锁定不在本期范围。
  - 新密码与当前密码相同：`422`（后端也校验，不只靠前端）。
  - 成功后：其他登录全部下线（其他浏览器、桌面端），当前页面保持登录（已决定 #18）；写登录审计。
- **成功提示**：「密码已更新，其他设备需要重新登录」。
- 首次登录的强制改密、运营端重置后的改密仍走现有 `owner-reset`，不合并。
- 桌面端本期不加入口。

1. R6 招募必选模型：Manager 后端与 `web/manager` 同一次发布（同 tier），无跨端顺序问题。

## 9. 不能保证的事

- 「继续生成」不是断点续跑：会用原资料重新跑一次，耗时与模型费用与首次生成相当。
- 取消生成时，若 worker 正在调用模型，已产生的模型费用无法退回；结果会被丢弃。
- 删除企业后，用户本机已有的会话与本地数据仍留在用户电脑上，平台无法远程清除；已离线用户在 token 过期前本地仍可查看历史，但不能再同步或发起需要 Manager 的操作。
- 招募必选模型只保证「招募那一刻模型可用」；模型之后被平台下架，员工仍会变为不可用（见「平台模型下架」专题）。
- 发布范围收窄会停用范围外企业已招募的员工，但用户端要到下次同步后才生效；进行中的执行不中断，本机历史会话仍可查看。
- 重置管理员密码会清除其通行密钥并解绑第三方登录，负责人需要重新登录、重新登记二次验证和重新绑定第三方账号；已离线的桌面端要等下次联网访问企业端时才会被要求重新登录。
- 设置新密码后，已离线的桌面端要等到下次联网访问企业端时才会被要求重新登录。
- 本方案上线前已开通的企业，企业端没有存企业名称，顶栏会先显示企业代码，直到企业管理员在企业设置里填写名称。
- 企业端登录接口本身没有失败锁定；本期只给「设置新密码」加了输错限制。
- 财务与审计记录在删除企业后仍会保留（匿名化），不是彻底抹除。
- 企业注销后不能恢复为正常状态（现有规则）；删除后 30 天内只能恢复到「已注销」。
- 方案里的某个专家因发布范围收窄被停用后，该方案在这家企业的群聊协作会缺少这名专家，直到范围恢复。
