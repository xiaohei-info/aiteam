## 3. 实施中发现的偏差（先记后改）

1. **行业字典不存在**：代码里没有现成的行业取值字典可复用。`industry` 改为 ≤20 字的文本（企业开通 / 编辑时填写），界面联想已有取值，不另建字典表。
2. **拉取参数一步到位**：设计里 `tenant_id` 先可选再必需是线上分步发布顺序；本分支一次提交最终形态（`tenant_id` 必需、`hidden_expert_count` 已进契约），发布时仍须按设计 §6 的顺序灰度。
3. **R2 契约兼容**：`ExpertTemplateDetail` 读入时丢弃旧 Operator 返回的 `platform_model_ref`，避免严格模式下整包解析失败。

4. **R5 租户状态拦截放在入口中间件**：设计要求“在统一入口加一层检查，而不是改各路由”。落地为 Manager 的 ASGI 中间件：先用现有验签器验证 Bearer，验签通过才按 `tenant_registry.status` 判定（验签失败交给路由返回 401，不泄露租户状态）；状态读取带 5 秒进程内缓存，所以状态变更最多 5 秒后在各 Manager 进程生效。登录统一在 token 签发出口 `_issue` 拦截（覆盖密码 / passkey / 第三方登录）。
5. **R5 服务间新用途**：新增 `tenant:lifecycle` 范围与 `tenant-lifecycle` 能力（`shared/service_token.py`、`service_ingress.py`），路径 `POST /api/manager/tenants/{tenant_id}/status`、`/purge`，按“只带 tenant、不带企业声明”绑定，并要求路径 tenant 与签名主体一致。
6. **R5 暂停 / 封禁 / 注销 / 删除时的模型访问**（决定 #20=A）：Operator 的 `_allowed_model_refs` 对非 active 企业返回空白名单，沿用现有“白名单收缩先吊销再签发”路径，因此不会再给被暂停企业重新签发中转令牌；状态变更时另调 `revoke_tenant_access` 立即吊销已有令牌（上游 NewAPI 不可用时记录告警、不阻断状态变更，由签发时的围栏兜底）。恢复为 active 后下一次解析自然重新签发。
7. **R5 状态同步顺序**：暂停 / 封禁 / 注销 / 恢复：**先调 Manager，成功后再写 Operator 本地**，失败则整体失败、状态不变，避免两端分裂；删除按设计走 `closed → deleting →（Manager）→ deleted`，Manager 失败停在 `deleting`，前端显示“删除未完成，重试”。
8. **R5 数据清理的触发**：仓库里没有定时任务框架，30 天后的清理不做自动调度；改为 system_admin 在保留期满后手动触发 `POST /enterprises/{id}/purge`（未满期 409）。自动调度列为已知限制。清理函数的“该 tenant 行数为 0、其他 tenant 不变”验证需要真实 PG，本机无 PG，随 CI 的 PG 集成测试验证。

### 5.1.2 PR #198 复审发现（先记后改）

只读复审在 PR 开出后又发现以下问题，本分支继续修：

1. 阻断：旧的企业操作接口 `POST /enterprises/{id}/actions` 的 `close` 走 `_transition`，状态表允许 `deleted / deleting → closed`，系统运营员可绕过“仅 system_admin、保留期、已清理”的限制。修：`_transition` 拒绝删除流程中的企业；恢复与放弃删除不经过 `_transition`。
2. 阻断：`PgAdminRepository.list_enterprises` 构造对象时漏了 `deleted_at / purged_at`，生产环境“清理数据”入口不出现、已清理企业仍显示“恢复”，补同步命令会反复下发已清理企业而失败。修：改用 `_state_from_row`。
3. 应修：PG 写状态是先读后写，并发的“继续删除 / 放弃删除”可能静默覆盖。修：按读到的旧状态做条件更新，被并发改过返回 409；两端若因此不一致，用补同步命令修复。
4. 建议：删除 / 恢复 / 清理三个路由是 `async def` 内同步调用 Manager 与数据库。修：改为普通函数，由框架放到线程池执行。
5. 建议：清理不可撤销，前端也要求输入企业名称确认（后端接口不变）。

处理结果：1–5 均已修复。验证：`test_admin_routes.py`（deleting / deleted 企业经旧操作接口的 close、reactivate、unban、suspend、ban 一律 409）、`test_repo_pg_mock.py`（列表带删除 / 清理时间；条件更新命中 0 行返回 409）、`DeletionDialog.test.tsx`（清理须输入企业名称）；运营端后端 709 用例、账号管理前端 41 用例通过。

### 5.1.3 PR #198 第 2 轮复审发现（先记后改）

1. 应修：复制专家路由是 `async def`，内部同步读库、调运营端目录、复制文件，会卡住事件循环。修：改为普通函数。

3. 应修：运营端重置负责人凭据不看企业状态；Manager 收端只判断租户是否登记，清理后登记仍在，会在已清理的租户里重新建出负责人账号。修：运营端对已注销 / 删除中 / 已删除 / 已清理的企业返回 409；Manager 收端对 `closed / deleted` 或已清理的租户返回 409。
4. 建议：Manager 登录与负责人自助改密先写“成功”审计、先改密码，再在签发 token 时才因企业不可用被拒，暂停 / 封禁企业的负责人仍能改掉密码。修：校验完租户后立即检查企业状态。
5. 建议：管理员打开列表触发的响应后对账会写员工状态，企业暂停时等于绕过“只读”。修：企业非 active 时跳过对账。
