## 1. 目标与边界

### 1.1 起因

「招聘专员」的 persona 要求「第一动作加载 recruitment-dispatch 调度 skill」，但员工的 `skills: []`（本机 `loaded_employee_projection` 快照核对）。用户问「你能做什么」时，模型去找这个不存在的技能，再把探测过程当答案讲出来。

追下去发现这不是个例，而是**配置 → 下发 → 装载 → 展示**整条链路里「声明」和「实际」之间没有任何一致性保障：管理员能配出到不了用户的技能，技能被删后员工配置里留着悬空引用，用户端把声明当能力展示。

### 1.2 目标

1. 管理员配置技能 / MCP 时，**看得见每一项是否真的能到达员工**，配不出到不了用户的东西。
2. 目录里删除、停用技能或 MCP 时，**受影响的员工配置同步处理**，不留悬空引用，且有审计。
3. 用户端展示员工能力时，**区分「可用 / 企业已移除 / 暂时不可用」**，不再把声明当能力。
4. 技能和 MCP **共用同一套「能力引用」机制**，不各做一遍。
5. 清掉没人读的旁路绑定表与接口，只留一个真相源。

### 1.3 非目标

- 不改知识库的绑定模式（有三态、撤销记录、文档级例外的真实需求，见 §3.3）。
- 不做逐条技能的开关与参数（目前没有需求）。
- 不做「常驻技能」（建会话时强制注入正文），另立专题。
- 不改技能包签名、验签、缓存的既有机制。
- 不做 persona 内容的语义理解；只做目录已知名字的匹配提示。

### 1.3.1 已决定

| 事项 | 来源 |
|---|---|
| 技能「加载失败就跳过，在回复末尾提示失败，原则是保证流程顺利进行并给出结论」，persona 中依赖缺失项的「失败即停」也按此处理，是有意的产品口径 | owner 余飞，PR #223 评论 |
| 员工技能以 `employee.skills` 为唯一来源 | 用户，2026-11-22 |

### 2.2 两个「真相源」：`employee.skills` 与 `employee_skill_binding`

| | `employee.skills`（员工表 JSON 列） | `employee_skill_binding`（独立表） |
|---|---|---|
| 写 | 员工配置保存、招募、复制员工 | `/api/manager/employees/{id}/skill-bindings` 的 CRUD、复制员工 |
| 读 | 快照、同步签发、选择器、Agent 就绪检查——**整条执行链路** | **只有它自己的 CRUD 和复制员工**（`employee_copy_service.py:110`） |
| 设计意图 | 员工有哪些技能 | `0014_employee_bindings.sql:43` 注释：「`enabled` 控制是否生效，`config` 放级联参数」，未接上 |

核对方式：在 `server/`（排除测试）搜 `EmployeeSkillBindingRepository`、`skills.list_all`，只出现在 `employee_bindings_*`、`routes_employee_bindings.py`、`employee_copy_service.py`；在 `web/`、`clients/` 搜 `skill-bindings` 无任何调用。

**结论：通过 skill-bindings 接口改绑定，对员工能用什么没有任何影响，是第二个（无效）真相源。**

### 2.3 MCP（连接器）：同样结构，另有缺口

| 环节 | 现状 | 位置 |
|---|---|---|
| 员工身上的清单（运行时使用） | `employee.connector_refs` | `snapshot_service.py:266`、`agent_service/src/connectors.ts:141-150` |
| 旁路绑定表（没人读） | `employee_connector_binding`，同样只有自己的 CRUD 和复制 | `0014_employee_bindings.sql:88`、`routes_employee_bindings.py:496`、`employee_copy_service.py:116` |
| 管理端能否给员工配 MCP | **员工配置抽屉里没有任何连接器 / MCP 选择**（`EmployeeConfigDrawer.tsx` 无 connector 相关代码）；`connector_refs` 只在招募（`recruit_service.py:239,392`）和复制（`employee_copy_service.py:95`）时被写入 | 同左 |
| 企业目录有两套 | `connector_catalog`（供 `employee.connector_refs` 指向，`schemas.py:690`）与 `mcp_catalog`（MCP 市场，成员自装用，`mcp_catalog.py:268` `installable`） | |
| 成员自装 | 个人 MCP `connector_my_*`，不经员工绑定 | `connectors.ts:186-200` |
| 删除 | `delete_connector`、MCP 市场 `delete`/`disable` 都不查员工引用 | `capability_catalog_service.py:167`、`mcp_catalog.py:159,223` |
| Agent 侧 | 员工绑定的连接器读本机连接器配置（url / tools / token_env 校验） | `connectors.ts:40-47` 附近 |

**未验证：** 市场里的 MCP 能否由管理员配给员工。读到的路径是「成员自装」，员工绑定走旧的连接器目录；没有找到把市场 MCP 绑到员工的入口。

### 2.4 知识库为什么用绑定表（对照）

- `employee.knowledge_refs` 被强制写空，`employee_knowledge_binding` 是唯一来源（`employee_config_service.py:59,89`）。
- 快照和每次检索都走同一个 `KnowledgeAccessPolicy.resolve()`（`knowledge_access_policy.py:64`、`snapshot_service.py:135`）。
- 三态（继承 / 允许 / 拒绝）；撤销保留带 `revoked_at` 的拒绝记录，重建索引不恢复权限；有文档级例外；有 `policy_revision / source / actor` 审计字段。
- Manager 每次检索实时校验，撤销立刻生效。

这些是真实需求，所以用绑定表。技能和 MCP 只有「有 / 没有」两态，执行点在用户本机，不具备这些需求。

**未验证：** 知识空间被删除后，员工的知识绑定行是否被清理；绑定表对空间无外键（`0014_employee_bindings.sql:58-70`，只有到 `employee` 的外键），知识库自己可能也有悬空问题，设计阶段单独查。

## 3. 总体设计

### 3.1 原则

1. **单一真相源**：技能与 MCP 以员工身上的清单（`employee.skills` / `employee.connector_refs`）为准，Manager 单写。
2. **单一读取入口**：所有读清单的地方（快照、同步、就绪、选择器）经同一个「能力引用服务」，返回「有效清单 + 每项状态」。参照 `KnowledgeAccessPolicy.resolve()` 的做法。
3. **不让配置悄悄失效**：不可下发、已被移除的项必须被看见，有状态、有原因、有动作。
4. **技能与 MCP 共用机制**，不各做一遍。
5. 文案面向管理员和用户，不出现 `skill_id`、「绑定」等技术词。

### 3.2 能力引用服务（新）

`manager_service/employee_capability_refs.py`（暂名），对 `kind ∈ {skill, connector}` 统一提供：

| 能力 | 说明 |
|---|---|
| `resolve(ctx, employee_id)` | 返回有效清单与每项状态 |
| `validate_additions(ctx, before, after)` | 只校验**新增**项：必须存在于企业目录、可下发；存量不受影响 |
| `status(ctx, ref)` | 状态枚举：`ready` / `draft` / `invalid` / `disabled` / `missing` |
| `employees_using(ctx, kind, ref)` | 反查哪些员工在用（JSON 包含查询，量大再加索引） |
| `remove_from_employees(ctx, kind, ref, actor)` | 同一事务内从员工清单去掉，升员工版本号，写审计 |

约束：全程经 `TenantContext` / RLS，不手写租户过滤；员工清单仍由 Manager 单写。

引用标识：员工清单存 `skill_id`（授权同步已支持 `skill_id@version`，`authorized_config_service.py:212`）。跨端契约里统一以 `skill_id` 为身份（AGENTS §3.9）；契约测试必须有「Manager 写、Agent 读」的闭环用例。

### 3.3 为什么不用绑定表（方案对比）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 删旁路，保留清单列 | 最小，与运行时一致 | 无外键保证、无逐项开关 |
| B | 绑定表为唯一来源（像知识库） | 有开关、参数，反查方便 | 迁移存量、改快照 / 同步 / 招募 / 复制 / 前端保存五条路径；无现实需求；高风险 |
| **C（采用，A+C）** | 清单为真相 + 统一能力引用服务 | 解决悬空、状态可见、删除联动；技能与 MCP 一次做完 | 新增一个服务 |

判断标准（写入概要设计 04）：**有逐项授权状态、实时校验、审计要求的能力用绑定表（知识库）；只表达「有 / 没有」的能力用员工清单 + 能力引用服务（技能、MCP）。**

### 3.4 主流程

1. 管理员打开员工配置 → 前端取目录与**每项状态** → 选择器置灰不可用项、标出已失效项。
2. 保存 → 后端 `validate_additions`，不可用的新增项返回 409 并列出原因。
3. 同时返回 `warnings`（persona 提到了目录里存在但没配给员工的技能名）。
4. 管理员删除 / 停用目录项 → 后端 `employees_using` → 无引用直接删；有引用返回 409 与员工列表，确认后 `remove_from_employees`（同事务）。
5. Agent 周期同步 → 快照来自统一入口；同步响应带「被跳过的引用及原因」。
6. 建会话 → 提示词只列**实际装载成功**的技能；persona 引用缺失项按产品口径跳过、文末提示。
7. 桌面端展示 → 可用 / 企业已移除 / 暂时不可用 三类。

### 3.5 状态与处置

| 状态 | 管理端选择器 | 保存新增 | 同步下发 | Agent 装载 | 桌面展示 |
|---|---|---|---|---|---|
| `ready` | 可选 | 通过 | 签发 | 装载 | 可用 |
| `draft` | 置灰「还没完成，暂时不能给员工用」 | 409 | 不签 | — | 暂时不可用 |
| `invalid` | 置灰「内容有问题，请重新导入」 | 409 | 不签 | — | 暂时不可用 |
| `disabled` | 置灰「已被停用」 | 409 | 不签 | — | 暂时不可用 |
| `missing`（目录无） | 标「已失效」+ 一键去掉 | 409 | 跳过 | `skill_removed` 跳过 | 企业已移除 |

存量悬空项只警告，不阻塞保存。

### 3.6 红线核对

- **不向用户机器入站**：仍由 Agent 周期 / 触发式 sync 拉取。
- **会话内容不上传**：同步响应与审计只含引用 ID 和原因，不含会话内容。
- **单写者**：员工清单由 Manager 写；Agent 只读投影。
- **租户隔离**：反查、联动在同一事务，经 `TenantContext` / RLS。

## 8. 不能保证的事

- 提示词只能降低弱模型「先叙述探测过程」的概率，不能保证每次遵守。
- persona 提示只识别**目录里已存在**的技能名；persona 里写了从未入库的名字（如本次的 `recruitment-dispatch`）发现不了，仍需管理员自己核对。
- 不会自动补上缺失的技能；缺什么由管理员决定。
- 删除联动不会中断正在运行的对话；已离线的用户重新同步前仍按旧清单工作（Agent 同步时有运行中会话只加不清，`server.ts` 同步段 `hasActiveRunsFor`）。
- 本设计未覆盖：`employee_prompt_version`（同一批迁移，是否也是旁路**未验证**）、知识空间删除后的绑定清理（P0 验证）。
