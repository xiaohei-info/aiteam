## 0. 一句话

**需要鉴权的 MCP 由 MCP 服务方发起鉴权；成员本人到服务方网页登录（或录入服务方发的固定令牌），成员本机 Agent 拿到鉴权结果存进本机文件，之后调用时直接取出使用；令牌全程不进模型、不出成员电脑。** 同时补齐「粘贴配置导入」和「自动读取工具」。

## 1. 场景与角色

用户提出的例子：

```json
"cr-test": { "type": "streamableHttp", "url": "https://mcp-test.cycplus.com/mcp/cr-test", "timeout": 30000 }
```

**谁给谁鉴权**

| 角色 | 做什么 |
|---|---|
| MCP 服务方（例：cycplus） | 校验调用方带的令牌；不带或无效返回 401，并在 `WWW-Authenticate` 里告诉调用方去哪登录 |
| 成员（真人） | 到服务方网页用**自己的服务方账号**登录授权；或粘贴服务方发给他的固定令牌 |
| 成员本机 Agent | 发起登录、接收回调、换取并保存令牌；调用 MCP 工具时带上令牌；令牌过期自动刷新 |
| 模型 / 专家 | 只看到「已安装 / 需要登录 / 工具结果」，**看不到**令牌、授权码、回调地址参数 |
| 企业端 / 运营端 | 登记与启用 MCP 条目（地址、工具、鉴权方式），**不持有、不经手**任何成员令牌 |

**两种凭据都要适配（用户确认 2026-11-18）**

| 类型 | 典型场景 | 服务方看到的身份 | 谁录入 |
|---|---|---|---|
| 浏览器登录（OAuth） | cr-test：成员用自己的 cycplus 账号登录 | 成员本人 | 成员在浏览器登录，Agent 自动接收 |
| 固定令牌（Bearer / 自定义请求头） | 服务方给了一串 API Key / Token | 令牌对应的账号（可能是个人、也可能是团队共用的那串） | 成员在桌面端的密码输入框录入 |

## 3. 设计

### 3.1 鉴权方式（auth）

每个 MCP（目录条目或本机已装项）带一个 `auth`：

| 值 | 含义 | 由谁判定 |
|---|---|---|
| `none` | 不需要鉴权 | 探测 200 |
| `oauth` | 服务方网页登录 | 目录声明，或探测 401 且能发现受保护资源 / 授权服务器元数据 |
| `bearer` | 固定令牌；默认 `Authorization: Bearer <令牌>`，可声明自定义请求头名（如 `X-API-Key`，此时原样放令牌） | 目录声明，或探测 401 但发现不到 OAuth 元数据 |

目录条目可以声明 `auth`；手动地址由 Agent 探测判定。目录声明与探测不一致时以**探测**为准（服务方升级了鉴权），并在审批弹窗如实显示。

### 3.2 成员本机凭据存储（参考 pi `mcp-bearer-store` / encrypted-file）

- 位置：Agent 数据目录下 `mcp-credentials/`，每个（成员、MCP 标识）一个文件；目录 0700、文件 0600（Windows 用当前用户 ACL）。
- 内容：OAuth 令牌（access / refresh / 过期时间）、动态注册得到的 client 信息；或固定令牌与请求头名。
- **加密**：AES-256-GCM，密钥文件与凭据分开存放（`mcp-credentials.key`，0600）。说明：密钥与密文在同一台机器同一用户下，**只能防止误拷贝 / 误上传凭据目录，不能防同一系统账号下的恶意程序**；与 pi 的 encrypted-file 后端同一安全等级。桌面端后续可把密钥移入系统钥匙串（见 §8 待决策 3）。
- **绑定地址**：记录写入时的 MCP 地址（规范化 origin + path）；读取时地址不一致即视为无凭据，不会把 A 服务的令牌发给 B 服务（pi 的 URL binding）。
- **不进模型**：`capability_install` 参数里没有任何凭据字段；工具结果、错误信息、审批摘要、时间线事件、日志一律不含令牌 / 授权码 / state / code_verifier。
- **不出电脑**：不上传企业端 / 运营端；治理摘要只记「某 MCP 被调用 N 次」这类已有计量，不含凭据。
- **删除**：卸载该 MCP、在设置里「退出登录 / 清除令牌」、成员退出登录本机账号时，删除对应凭据文件。

### 3.3 浏览器登录流程（oauth）

```
专家：capability_install(kind=mcp, ref=cr-test, url=…)
Agent：探测 → 401 + resource_metadata → auth=oauth
审批弹窗：「cr-test 需要登录服务方账号（mcp-test.cycplus.com）」[拒绝] [允许并登录]
成员点「允许并登录」
Agent：发现元数据 → 动态注册（或复用已注册 client）→ 生成 PKCE + state
      → 用系统默认浏览器打开服务方授权页（同时把链接给弹窗，便于手动打开 / 复制）
成员在浏览器登录 cycplus 并同意
浏览器 → http://127.0.0.1:<Agent 端口>/api/agent/mcp-auth/callback?code&state
Agent：校验 state → 用 code + verifier 换令牌 → 加密存本机 → 带令牌读工具列表 → 完成安装
模型收到：「已安装 cr-test，工具 N 个」（不含任何令牌）
```

- 回调路由是 Agent 本机 loopback 上的**免登录**路由（浏览器带不了 Agent 会话令牌），靠一次性 `state`（随机 32 字节、10 分钟过期、用后即焚）+ PKCE 防伪；只接受 `127.0.0.1` 来访。这是用户自己的浏览器访问本机 Agent，**不是控制面入站**，不违反「不向用户机器入站」。
- 等待登录：安装调用最多等 10 分钟（与审批时效同量级）；成员关闭弹窗或超时 → 安装失败，模型收到「用户未完成登录，可稍后重试」。
- 刷新：调用前令牌将过期则用 refresh_token 刷新并回写；刷新失败 → 该 MCP 状态变为「需要重新登录」。
- 浏览器打开方式：Agent 用系统命令打开（macOS `open`、Windows `start`、Linux `xdg-open`，与 pi 相同）；失败时弹窗里的「在浏览器打开」按钮兜底。

### 3.4 固定令牌流程（bearer）

- 审批弹窗显示「cr-xxx 需要访问令牌」+ 密码输入框（不回显）+ 可选「请求头名」（目录已声明则只读）。
- 令牌随审批决定**由桌面端直接提交给本机 Agent**（`POST /api/agent/approvals/{id}/decision` 新增 `credential` 字段），不经模型、不写审批记录、不进事件流；Agent 用它探测工具列表，成功才保存，401 则提示「令牌无效」并允许重填。
- 之后可在设置「个人能力」里「更新令牌」。

### 3.5 运行时

- 调用工具时按 `auth` 取本机凭据组装请求（oauth 用 SDK `authProvider`，bearer 加请求头）。
- 401 / 刷新失败：工具返回「需要重新登录 cr-test：请到 设置 · 个人能力 重新登录」，模型照此告知用户；**不**在对话中自动拉起浏览器（避免模型反复触发登录）。
- 超时：每个 MCP 可带 `timeout_ms`（1 000–300 000，默认 30 000），用于单次工具调用。

### 3.6 设置「个人能力」

每个已装 MCP 显示鉴权状态：`无需登录` / `已登录（到期时间）` / `需要重新登录` / `已填令牌`，按钮：
- oauth：「重新登录」（走 §3.3，不改安装记录）、「退出登录」（删令牌）
- bearer：「更新令牌」、「清除令牌」

### 3.7 与自动安装（§11.3）的关系

自动安装只跳过「是否允许安装」这一步，**不跳过登录**：
- `auth=none`，或本机已有该地址的有效凭据 → 按 §11.3 直接安装；
- 需要登录 / 填令牌 → 仍弹窗（弹窗只问登录，不再问是否允许）。

### 3.8 目录侧：`requires_credentials` 改为 `auth`

- 运营端条目字段 `requires_credentials: bool` → `auth: none | oauth | bearer`，`bearer` 时可填 `auth_header`（默认 `Authorization`）；新增可选 `oauth_scopes`、`timeout_ms`。
- 迁移：`requires_credentials=true` 的旧条目 → `auth=bearer`。
- **需要鉴权的条目进入成员可装列表**（凭据是成员个人的，不再排除）；企业仍通过「启用 / 停用」控制。
- 运营端、企业端**永不保存令牌**：导入配置里带的令牌会被丢弃并提示。

### 3.9 粘贴配置导入（运营端「登记 MCP」窗口 + 桌面端「添加 MCP」窗口）

窗口顶部加「从配置导入」文本框，接受：

| 输入 | 例 |
|---|---|
| 单条带名称 | `"cr-test": { … }` 或 `{ "cr-test": { … } }` |
| Claude / Cursor 格式 | `{ "mcpServers": { "cr-test": { … } } }` |
| 单条无名称 | `{ "type": "streamableHttp", "url": "…" }` |
| 纯链接 | `https://mcp-test.cycplus.com/mcp/cr-test` |

映射：名称 → 标识（不合规则给出建议改法）、`url` → 地址、`timeout` → 超时、`type`：`streamableHttp` / `streamable-http` / `http` 接受，`sse` / `stdio` / 带 `command` 的拒绝并说明「只支持 streamable HTTP 远程服务」；`headers` 中出现 `Authorization` 或 `*key*` / `*token*` → 自动设 `auth=bearer`（及请求头名），**令牌值丢弃**并提示「令牌不会保存到平台，成员安装时自行填写」。多条时列出让人选一条。纯前端解析，导入后仍可逐项修改。

**桌面端「添加 MCP」窗口（新）**：在「个人能力」页，成员自己粘贴配置 / 链接 → Agent 探测 → 需要时登录或填令牌 → 安装（来源 `user_url`，审批人为本人）。好处：令牌只在桌面端 → 本机 Agent 之间流转，完全不经过对话。对话中让专家安装（`capability_install`）的路径保留。

### 3.10 应用编号（OAuth client）：自动注册优先，可选手动填写（参考 pi）

浏览器登录时服务方要知道「是哪个应用来要授权」，即应用编号 `client_id`（部分服务还配一串 `client_secret`）。取编号顺序与 pi `mcp-oauth-provider.ts` 的 `clientInformation()`（393 行起）一致：

1. 条目填了 `oauth_client_id` → 用它（有 `oauth_client_secret` 一并使用，令牌端点认证方式 `client_secret_post`，否则 `none`）。
2. 否则**自动注册**（Dynamic Client Registration）：向服务方注册接口报 `client_name: "AI Team"`、回调地址 `http://127.0.0.1:<Agent 端口>/api/agent/mcp-auth/callback`、`grant_types: [authorization_code, refresh_token]`；领到的编号与令牌一起存成员本机凭据文件，绑定 MCP 地址与授权服务器 issuer，下次复用；回调地址变了或服务方作废编号 → 下次登录自动重新注册（pi 484–490 行同逻辑）。
3. 两者都没有且服务方不支持自动注册 → 登录失败，提示「该服务需要先到服务方开发者后台申请应用编号，填入『高级 · 应用编号』，或改用固定令牌」。

不做 pi 的第三种方式（用公开网址当编号，CIMD）。

**手动填写的编号存哪（用户确认 2026-11-18：自动加密保存）**

| 来源 | client_id | client_secret |
|---|---|---|
| 成员「添加 MCP」 | 本机凭据文件 | 本机凭据文件（与令牌同一加密） |
| 运营端平台目录 | 目录条目普通字段（不算机密） | 运营端用 `shared/crypto` 加密入库（与平台 Provider 管理令牌同一做法，`operation_service/platform_provider_service.py:1313`）；接口**只写不读**，页面只显示「已设置 / 替换 / 清除」 |

平台目录 secret 的流转：Manager 经服务间拉取得到（同 §11.3 的 `/mcp-market/pull/servers`，仅 service token），用 Manager 自己的密钥加密存入 `mcp_catalog`（同 `provider_credential_service.py`）；成员 Agent 仅在**登录 / 刷新令牌那一刻**调成员级接口 `GET /api/manager/grants/mcp-servers/{server_id}/oauth-client` 取回，只放内存，不落盘、不进模型。`GET /grants/mcp-servers` 列表只返回 `oauth_client: "preregistered" | "dynamic"`，不带 secret。

> 说明：桌面应用里的 client_secret 本质上无法对成员保密（OAuth 规范把桌面应用归为「公共客户端」，主要靠 PKCE 防护）。加密保存防的是数据库 / 备份泄露和误展示，不是防成员本人。

### 3.11 自动读取工具（运营端）

- 新接口 `POST /api/operation/mcp-market/probe`（system_admin / system_operator）：入参 `{url, timeout_ms?, auth_header?, test_token?}`；返回 `{status: ok|needs_oauth|needs_token|unreachable, auth, tools[], scopes_supported[], server_name?}`。
- `test_token` 只用于这一次探测，**不保存、不记日志**。
- 需要 OAuth 的服务运营端无法替成员登录 → 返回 `needs_oauth` + 鉴权信息，工具名需手填（或留空，见 §8 待决策 4）。
- 防 SSRF：仅 https；解析域名后拒绝私网 / 回环 / 链路本地 / 组播 / 文档地址段；不跟随重定向；10 s 超时；响应体上限 1 MiB。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 令牌泄露给模型 | 参数无凭据字段；所有对模型可见文本走统一出口，测试断言不含令牌 / code / state |
| 令牌发错服务（A 的令牌给 B） | 凭据绑定地址，读取时比对 |
| 恶意 MCP 在授权元数据里指向钓鱼授权页 | 弹窗显示授权页域名；授权服务器元数据校验 issuer（SDK 默认）；手动地址的授权页与 MCP 不同域时弹窗醒目提示 |
| 本机回调被其他网页伪造 | 一次性 state + PKCE；仅 127.0.0.1；只接受本 Agent 发起过的 state |
| 运营端探测被用作 SSRF | §3.10 地址段 / 重定向 / 超时 / 大小限制 |
| 服务方不支持动态注册 | 「高级 · 应用编号」手动填写；仍无则提示改用固定令牌（§3.10） |
| 平台目录 client_secret 泄露 | 两端加密入库、接口只写不读、成员取用只放内存；本质无法对成员保密（见 §9） |

## 9. 不能保证的事

- 服务方的 OAuth 实现不规范（不发 `WWW-Authenticate`、无元数据、不支持动态注册）时，浏览器登录走不通，只能用固定令牌。
- 本机凭据文件加密只防误拷贝 / 误上传，**不防**同一系统账号下运行的恶意程序。
- 平台目录里手动填写的 client_secret 会到成员电脑内存里使用，懂技术的成员能取到；这是桌面 OAuth 的固有限制。
- 服务方吊销令牌后，Agent 只能在下次调用 401 时发现，届时提示重新登录。
- 成员在对话里直接粘贴含令牌的配置时，令牌已经进入对话上下文（这是成员自己的输入）；Agent 不会使用、也不会保存它，并会提示改用「添加 MCP」窗口或审批弹窗录入。
