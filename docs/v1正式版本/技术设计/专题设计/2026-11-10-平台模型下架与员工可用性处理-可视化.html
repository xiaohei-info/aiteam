平台模型下架 → 员工可用性处理 2026-11-10 · 设计草案，未写代码

一句话：运营端下架模型后，员工不会「突然不可用」——平台公告下架时间，企业端提前看到受影响员工并能一键切换，用户端在宽限期内继续可用、到期才阻断，已冻结会话与进行中的 Run 不受影响。

可感知

Operator 下架主动通知 Manager；Manager 扫描本 tenant 受影响员工，企业端列表可见。不再等用户投诉才发现。

可处置

Manager 批量切换模型（只能选已发布且 tenant 可见），version 递增，旧会话历史保留。

可恢复

切换后 Agent 下次 sync 拉到新快照，自动清除不可用标记，用户无需重新登录。

阅读提示：工作量用 S / M / L 粗估，只表示相对大小，不是排期承诺；UI 为示意图，不是最终视觉稿；表格里标「新」的是仓库里目前没有的东西。配套设计文档：2026-11-10-平台模型下架与员工可用性处理-需求与设计.md。

1 解决什么问题

现在的问题本方案怎么解决谁受益
下架没有产品入口，只能靠 discovery 同步顺带发生或直改库，也没有影响面提示运营端新增「公告下架 / 立即停用」动作，带 sunset_at 与影响面统计（tenant 数、employee 数）运营
Manager 被动感知：平台模型上下架不通知，只能等 Agent 拉快照失败才被发现扩展 CatalogReleaseNotify，下架后 Manager 主动扫描本 tenant 引用该模型的员工并标记企业管理员
企业管理员看不到哪些员工受影响，也没有处置入口员工列表增加「依赖不可用」状态与筛选，提供批量切换模型入口（version 递增、旧历史保留）企业管理员
员工突然不可用，用户端只提示「模型暂不可用」，没有恢复路径用户端三态提示：宽限期内可用但横幅提示；硬停用 409 + 明确指引；员工下架单独提示企业成员
归因单一：下架 / 硬停用 / 价格未知 / provider 停用混成一个错误码错误码细分：employee_dependency_deprecated / employee_dependency_disabled / platform_price_unknown企业成员、客服
价格未知也硬阻断，价格同步延迟会误伤正常员工价格未知降级为「按 unknown 计价 + 上报」，不阻断执行；仅模型本身不可用才拒绝快照企业成员、财务
恢复要靠用户重新登录或重新装载管理员切换后 version 递增，Agent 下次 sync 自动清除标记，无需重新登录企业成员
不能保证的事（需要对外口径一致）：模型被硬停用（合规 / 供应商断供）时，宽限也无法继续，只能由企业管理员切换模型；已冻结会话在 Manager 离线期仍可跑，但新会话无法开始。我们保证「不死路、可恢复」，不保证「下架永不影响新对话」。

3 数据流

边界不变：不向用户机器入站；平台模型状态只有 Operator 能写；会话内容不上传；已冻结快照不被改写。

3.1 总图：谁在哪一端做什么

实线 = 同端流程；虚线 = 跨端调用。方向只有两种：Operator→Manager 服务间调用、Agent 主动访问 Manager。没有任何入站到用户机器。

→

3.4 状态与处置矩阵

状态新招募 / 改配置新快照下发本地已冻结会话用户端
published允许允许允许正常
deprecated禁止允许（带 deprecation 元数据）允许宽限横幅，不阻断
disabled禁止拒绝允许（已冻结快照）409 阻断 + 指引
draft禁止拒绝不适用不可用

已冻结快照与进行中 Run 始终可跑（D5 / F11 / D14）；下架只影响「新快照下发」，不打断正在执行的会话。

3.5 群聊场景（coordinator + participant）

群聊结构：1 个 coordinator + N 个 participant；无 @ 消息只投递 coordinator，@ 消息直接投递 participant（不经过 coordinator），coordinator 用 mention_employee 工具主动 @ 成员。

场景实际表现是否牵连别人
coordinator 模型停用无 @ 消息：409，整条发不出；有 @ 消息：直接投递 participant，可用；coordinator 无法再用工具 @ 人只阻断无 @ 消息
participant 模型停用人工 @ 他：409，整条发不出（即使同时 @ 别人）；coordinator 工具 @ 他：返回 error，可改 @ 别人人工多 @ 时可能阻断整条
其他 participant正常不受影响
进行中的 Run不中断—
custom / free 群可通过成员编辑移除 / 替换（coordinator 不可移除）—
solution 群roster 冻结，不可通过成员编辑替换恢复路径长

问题：coordinator 单点故障；人工多 @ 全有全无；coordinator 不知成员不可用（buildGroupContext 不给可用性）；solution roster 冻结；无群级健康提示。

场景建议
coordinator 不可用群顶部横幅「协调专家暂不可用，@提及成员可直接投递」；无 @ 消息保持阻断（降级选人风险大）；Manager 侧提供「更换协调专家」
participant 不可用工具 @ 失败错误带 employee_dependency_disabled；把不可用成员写进 buildGroupContext，coordinator 一开始就避开
人工多 @改为部分投递：可用的先投递，不可用的汇报给用户；至少前置校验返回明确列表让用户确认
roster 维护custom / free 群：前端暴露移除 / 替换；solution 群：允许管理员替换单个成员（version 递增、roster 重新冻结）
群健康群详情页显示成员可用状态与原因；下架事件触发时在群内提示
恢复切换模型 → version 递增 → sync 更新 snapshot → available 自动恢复；更换 coordinator 后重新冻结 solution roster
