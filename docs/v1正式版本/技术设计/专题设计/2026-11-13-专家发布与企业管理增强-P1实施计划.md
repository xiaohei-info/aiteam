## 1. 目标与边界

**目标（与方案 §7 P1 验收一致）**
- R1：运营端草稿列表可对未完成草稿「继续生成 / 删除 / 取消生成 / 继续编辑」。
- R4：在企业账号行菜单重置管理员密码；重置后该管理员全部登录下线，二次验证与第三方登录被清除，审计可查。
- R6：招募与应用方案必须选模型；后端缺模型或模型不可用时 422 且零写入。
- R8：企业端顶栏显示企业名称与账号菜单。
- R9：企业端已登录用户可自助设置新密码。

**非目标（本期不做）**：R2 / R3 / R5 / R7 的任何改动；运营端模板仍保留模型字段（P2 才去掉，本期 Manager 只是**不再读取**它）；桌面端改密入口；「负责人账号找回」专题。

## 3. 关键设计（实施细节，方案未展开的部分）

### 3.1 R1 草稿列表与取消

- `solution_authoring_repository.list_drafts`（`server/operation_service/solution_authoring_repository.py:180`）所在的事务接口 `_Tx`（`:126-158`）新增一个「批量取各草稿最近任务」方法（PG 用一次子查询，内存实现同步），填 `DraftOut.latest_job: {status, error_code, created_at, started_at, finished_at} | null`（任务表没有 `updated_at`）。不返回错误详情原文。
- `DraftListOut`（或列表 envelope 的 meta）加只读 `worker_available`，取自现有 worker 启用配置（`solution_authoring_dependencies.py:28-29,81-95`）。
- 「未完成 / 全部」在前端过滤，不新增查询参数（草稿量小，避免扩大接口面）。
- 取消：`POST /api/operation/solution-authoring/drafts/{id}/generation/cancel`，`system_admin / system_operator`。仓储在草稿行锁内：活跃任务（`queued / parsing / analyzing`）→ `failed, error_code=cancelled, lease_owner=NULL`，草稿按现有失败回退（`:332`）回到 `draft / ready_for_review`；写一条 `solution_review_event`。无活跃任务时幂等返回当前草稿（200）。
- 不写结果：依赖现有路径（`solution_authoring_jobs.py:177-179,238`；`complete_job` 的归属检查 `solution_authoring_repository.py:305-310`）；P0① 用测试证明。
- **结束子进程（新）**：把 `lease.lost` 作为取消信号传给 runner，置位后结束生成子进程（复用 `server/shared/solution_authoring/runner.py:155` 的 `_kill`）。不做的话，被取消的任务仍占着 worker 最长 15 分钟（默认并发 1），紧接着的「继续生成」只能排队。
- 「疑似卡住」判定在前端：`latest_job.status=queued` 且 `created_at` 超过 10 分钟，或 `worker_available=false`。详情页的「取消生成」在生成中始终可用。
- 「继续生成」失败要给出原因：草稿的生成模型若已下架，后端会拒绝（`solution_authoring_service.py:220-221`），列表弹出该错误并提示「该草稿的生成模型已不可用，请删除后新建」（草稿没有改模型的接口）。

### 3.2 R4 重置管理员密码

- **Manager**：`sync_owner_bootstrap_in_session`（`server/manager_service/repository.py:137`）在「替换已有账号」分支、同一 `session` 内追加：
  1. `UPDATE manager_auth_session SET revoked_at=now(), revoke_reason='owner_bootstrap_reset' WHERE user_id=%s AND revoked_at IS NULL`。注意现有 `auth_sessions.revoke_user`（`auth_sessions.py:61`）会自开连接，**不能直接复用**，否则不在同一事务；改为在仓储里写 in-session 版本，或给 `revoke_user` 增加可选 `session` 参数。
  2. `DELETE FROM passkey_credential WHERE user_id=%s`。
  3. `DELETE FROM oauth_connection WHERE user_id=%s`；同时删除该用户 `auth_identity` 中 `provider='oauth'` 的行（已核实：第三方登录先查 `oauth_connection`，查不到再按 `auth_identity(provider=oauth)` 反查，并会顺手重建连接，`server/manager_service/oauth_service.py:104-125`；所以两张表都要删）。
  4. 返回值增加 `cleared: {sessions, passkeys, oauth}` 计数，供审计使用；跨端回执只带计数，不带任何凭据。
- **Operator**：
  - `reset_owner_bootstrap`（`server/operation_service/service.py:257`）增加 `actor_id / actor_name` 参数，路由从 JWT 取（`routes_enterprise.py:60`）；完成后写 `operation_audit_event(action='owner_bootstrap_reset', detail={cleared...})`。
  - 回执 24 小时：新增迁移把 `bootstrap_secret_ciphertext` 放开为可空（现为 `NOT NULL`，`server/operation_service/migrations/0014_onboarding_receipt.sql:16`）；`completed` 且 `completed_at + 24h` 之后，读取时惰性 `UPDATE ... SET bootstrap_secret_ciphertext=NULL`，`OnboardingReceipt` 读取处同步处理空值（`onboarding_receipt.py:149-166`）；`prepared` 状态的回执不清（断点续跑要用）；同一幂等键在过期后重放返回 `409 bootstrap_receipt_expired`（提示「请重新重置」），不再返回明文。`app_rw` 已有回执表 UPDATE 权限（`server/operation_service/migrations/0014_onboarding_receipt.sql:26`）。
- **前端**：`EnterpriseActions.tsx` 行菜单加「重置管理员密码」→ AlertDialog（文案含「通行密钥等二次验证会被清除、第三方登录会被解绑，网页和桌面端都须重新登录」）→ 复用 `BootstrapSecretDisplay`；`EnterprisePage.tsx:157-205` 独立表单删除，`web/operation/src/features/enterprise/useEnterpriseApi.ts:59-66` 的调用迁到 accounts 侧。

### 3.3 R6 招募 / 应用方案必选模型

- `RecruitExpertRequest`（`server/manager_service/schemas.py:591`）新增 `model_policy: RecruitModelPolicy`（`provider_ref, model, thinking_level?`，`extra=forbid`），OpenAPI 标为必填。
- `ApplySolutionRequest`（`schemas.py:622`）新增 `expert_models: dict[str, RecruitModelPolicy] = {}`。

- **校验位置**：`recruit_expert`（`recruit_service.py:117`）中，模型校验必须放在 `_track_provision`（建招募订单，本身就是一次写入）**之前**，与 `_validate_grant_subjects` 并列；`apply_solution`（`:244`）在展开任何专家前先校验全部新建专家 + 被改模型的复用专家，任一失败整单 422，`errors[]` 逐个列 `template_id`。

  - `SolutionsPage.tsx:192-268` 应用方案弹窗：新建专家逐行下拉 + 「新建专家全部使用」；已招募专家预填当前模型可改；422 时按 `errors[]` 逐行标红。

### 3.4 R8 顶栏企业名称

- 新增只读 `GET /api/manager/me`（任意已登录角色）：`enterprise_name`（读 `enterprise_settings`，只读、不建行）、`enterprise_code`（读 `tenant_registry`，业务连接有 SELECT，`0001_tenant_base.sql:123`）、`account_masked`、`roles`、`has_password`、`password_policy`。不能用企业设置读取接口：它只允许管理员（`settings_service.py:17`），成员会 403。
- 开通时把企业名称写入 `enterprise_settings.enterprise_name`（`routes_tenant.py:88` 现在只拿它生成 slug）；已开通企业不回填，显示企业代码。
- 顶栏用 Astryx `AppShell` 的 `topNav` 插槽 + `DropdownMenu`（运营端行菜单已在用，`EnterpriseActions.tsx:51`）；现在没有顶栏。
- 新增 `web/manager/src/shell/AccountMenu.tsx`：登录后拉一次 `me`，显示 `enterprise_name || enterprise_code`；菜单项：账号（手机号打码）+ 角色、企业设置（仅 owner / enterprise_admin）、设置新密码（`has_password` 为真时）、退出登录。替换 `AppShell.tsx:57` 的单独按钮。
- 企业设置页保存成功后通知顶栏重新拉取 `me`（一个 context，不另造全局状态）；名称为空且当前用户是管理员时，菜单里显示「去设置企业名称」。

### 3.5 R9 设置新密码

- 新接口 `POST /api/auth/password`（`routes_auth.py`，需登录，任意企业角色），body `{old_password, new_password}`。
- `AuthService.change_password(claims, req)`：校验旧密码 → 复杂度 → 更新 `secret / must_reset=false / password_changed_at`（复用 `owner_reset` 的同一段逻辑，`auth_service.py:242-262`，抽成私有方法供两处调用）→ 吊销该用户**除当前 jti 外**的全部会话（新增 `auth_sessions.revoke_user_except(ctx, keep_jti, reason)`）→ 写登录审计。
- 旧密码错误：`422 old_password_incorrect`，写登录审计。企业端**没有**现成的失败锁定（`record_attempt` 只记审计，`auth_service.py:381-391`），本接口自带限制：按登录审计表统计该账号 15 分钟内本接口的失败次数，达到 5 次返回 `429 too_many_attempts`；审计库未配置时该接口直接拒绝（生产必配）。
- 新旧密码相同返回 422；按 `user_id` 找到该用户的手机号身份后更新（现有 `update_secret` 按手机号定位，`repository.py:183-191`，需补一个按 `user_id` 查身份的方法）。
- `/api/auth/session` 不改（`TokenClaims` 是严格共享契约，`server/shared/contracts/auth.py:18-34`）；`has_password` 与密码规则放在 `GET /api/manager/me`。
- 前端 `ChangePasswordDialog.tsx`：三个输入框、实时规则提示（规则文案取自后端复杂度规则，不在前端另写一份）、两次不一致或与当前密码相同时「确定」不可点；成功提示「密码已更新，其他设备需要重新登录」。
