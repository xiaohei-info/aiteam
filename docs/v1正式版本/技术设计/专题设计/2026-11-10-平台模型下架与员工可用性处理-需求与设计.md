> 状态：**草案，待确认**。本文只做问题梳理与方案设计，未开始编码。
> 可视化版本：`2026-11-10-平台模型下架与员工可用性处理-可视化.html`（UI 示意与数据流图）。
> 口径依据：v1 概要设计 00（D18）、04 §6.7、05 §5.3 / F11 / F14 / F15、03 §9.7；AGENTS.md §3.2、§3.3、§8、§10。

## 1. 目标与边界

### 1.1 问题

运营端下架（停用 / 下架 / 价格失效）某个平台模型后，引用该模型的员工在用户端会立即不可用。当前链路是「Agent 拉快照失败 → 标记员工不可用 → 拒答」，存在三个断点：

- **下架动作没有产品化入口**：Operation 只有 `publish` 路由，没有 unpublish / disable；下架只能靠 discovery 同步顺带发生或直改库，也没有影响面提示。
- **Manager 与企业管理员被动感知**：平台模型上下架不通知 Manager，只能在 Agent 下次 sync 拉快照失败时被动发现；企业端员工列表看不出哪些员工受影响，也没有处置入口。
- **归因单一、无宽限期**：`employee_dependency_unavailable` 把「计划下架 / 硬停用 / 价格未知 / provider 停用」混成一个码；价格未知也硬阻断，可能误伤正常员工。

### 1.2 目标

1. 下架成为**可感知、可处置、可恢复**的闭环，而不是「员工突然不可用、无人处理」。
2. 已冻结快照与进行中的 Run 不被中途打断（D5 / F11）。
3. 职责边界不变：**Operator 决定下架与时间；Manager 负责影响面与切换；Agent 只做本地阻断与提示**。
4. 群聊场景有明确的降级与恢复路径（coordinator 单点、人工多 @、solution roster 冻结），见 §3.6。

### 1.3 非目标（本期不做）

- 平台静默把员工切到备用模型（除非企业管理员显式配置，见 §3.8）。
- 跨端实时事件总线；仍走 pull + 通知 + 本地投影（05 §5.1）。
- 下架历史的完整版本化目录（复用现有 `platform_model.version` 与 `platform_model_rate`）。
- 会话内容 / 执行明细上传；摘要口径不变（D13）。

## 2. 现状与缺口

| 环节 | 现状 | 位置 | 缺口 |
|---|---|---|---|
| Operator 模型状态 | `platform_model.status` = `draft / published / disabled`；`disabled` 由 discovery 同步在上游模型消失时自动打 | `server/operation_service/platform_provider_repository.py:297` | 无显式下架入口；无 `sunset_at`；无影响面统计 |
| Operator 路由 | 只有 `publish` / `publish-priced` | `server/operation_service/routes_platform_provider.py:173` | 无 unpublish / disable / 影响面查询 |
| Manager 写配置门槛 | 招募 / 改员工时校验模型必须 published + tenant 可见 | `server/manager_service/employee_config_service.py:99` `_validate_platform_model` | 无「已下架」提示，只有一般性 `NotFound` |
| Manager 快照门槛 | 拉执行快照时校验 provider/model published + price known，否则抛 `EmployeeDependencyUnavailable` | `server/manager_service/snapshot_service.py:148` `_resolve_pricing` | 不区分下架 / 硬停用 / 价格未知；无宽限期 |
| 跨端通知 | `CatalogReleaseNotify` 只覆盖 `expert_template / solution_template` | `server/shared/contracts/crosstier.py`、`server/manager_service/routes_catalog_notify.py` | 不覆盖平台模型 / provider 上下架 |
| Agent 感知 | sync 时单员工快照被拒 → 只标记该员工 `availability_reason=employee_dependency_unavailable`，其它员工照常（partial sync） | `server/agent_service/src/http/server.ts:2228-2265` | 归因单一；无宽限提示 |
| Agent 阻断 | prompt / mention 前 fail-closed 409；`session-host` 同一规则 | `server/agent_service/src/http/server.ts:2484`、`server/agent_service/src/pi/session-host.ts:1435` | 不区分「可用但提示」与「不可用」 |
| 用户端提示 | 桌面弹窗「部分员工暂不可用」+ 文案，历史消息可看 | `clients/desktop/src/components/GrantsSyncNotice.tsx`、`clients/desktop/src/lib/employeeAvailability.ts` | 文案不可操作（无恢复路径、无下架时间） |
| 企业端视图 | 员工列表只统计「未配置模型」 | `web/manager/src/features/experts/ExpertsPage.tsx` | 无「依赖不可用」状态 / 筛选 / 批量切换 |
| 已冻结会话 | 快照冻结后 Manager 离线也能继续跑 | 04 §6.3、05 §5.3 | 无需改，需在设计中明确保留 |
| 群聊 | coordinator + participant 投递；roster `available` 已按 `availability_reason` 计算 | `server/agent_service/src/services/conversation-reads.ts:89`、`server/agent_service/src/pi/session-host.ts:1775` | coordinator 单点；多 @ 全有全无；coordinator 不知成员不可用；solution roster 冻结 |

**结论**：「模型下架 → 员工不可用 → 拒答」这条链路已经实现了一半（Agent 侧 fail-closed + 局部标记 + 提示），**缺的是主动感知、影响面可见、处置路径**。

## 3. 总体设计

### 3.1 设计原则

- **快照冻结不被改写**：下架只影响「新快照下发」，不影响「已冻结快照的本地执行」。
- **fail-closed 不硬跑**：快照拿不到就拒绝新 Run，绝不用陈旧 / 缺失配置硬跑（05 §5.3）。
- **单写者**：平台模型状态只有 Operator 能写；Manager / Agent 只读（AGENTS §3.2）。
- **窄通信**：不新增跨端直连；通知复用 `CatalogReleaseNotify`（05 §5.1）。
- **最小必要**：先做「可感知 + 可处置」，主备兜底列为可选。

### 3.2 下架语义与状态模型（Operator）

现有 `platform_model.status`：`draft | published | disabled`；`platform_provider.status`：`published | disabled`。

建议在 `platform_model` 增加 `sunset_at`（计划停用时间，可空），并把状态扩展为：

| 状态 | 含义 | 新招募 / 改配置 | 新快照下发 | 本地已冻结会话 |
|---|---|---|---|---|
| `published` | 正常 | 允许 | 允许 | 允许 |
| `deprecated` | 已公告下架，未到 `sunset_at` | **禁止** | 允许（带警告） | 允许 |
| `disabled` | 硬停用（合规 / 断供），或已过 `sunset_at` | 禁止 | 拒绝 | 允许（已冻结快照） |
| `draft` | 未发布 | 禁止 | 拒绝 | 不适用 |

- `deprecated` 是「缓冲档」：给企业留出处置时间，同时给平台一个明确的停用时间点。
- `disabled` 是「立即生效档」：用于供应商断供、合规要求等场景。
- `platform_provider` 同步支持 `deprecated / disabled`，语义一致；provider 不可用时其下模型一律视为不可发布。

### 3.3 跨端感知链路

```text
Operator 下架（deprecated / disabled）
   │  CatalogReleaseNotify（扩展 catalog_type = platform_model | platform_provider）
   ▼
Manager 收通知 → 扫描本 tenant 内引用该模型的 employee
   │  → 标记「依赖不可用」（保留配置，不删除）+ 企业端列表警示
   │  → 提供批量切换模型入口
   ▼
Agent 周期 sync → 拉快照
   ├─ 成功（宽限期内）→ 清除标记，继续可用（带提示）
   └─ 被拒（disabled / 已过 sunset_at）→ availability_reason = employee_dependency_disabled
```

- 通知是「提前刷新的提示」，Manager 真相仍来自 pull（F03 口径不变）；未收到通知时，Agent 拉快照失败也会兜底发现。
- Manager 侧扫描是**主动感知**，让企业管理员在用户投诉之前看到影响面。

### 3.4 Manager：影响面与处置

1. **影响面视图**：员工列表增加「依赖不可用」状态与筛选；支持按模型 / provider 聚合。
2. **批量切换模型**：仅可选择当前 `published` 且 tenant 可见的模型；批量递增 employee version；旧 version 的会话历史保留。
3. **快照分级**：
   - `deprecated` 且未过 `sunset_at` → 返回 pricing + `deprecation` 元数据（可执行但提示）；
   - `disabled` 或已过 `sunset_at` → 拒绝快照，回明确错误码。
4. **错误码细分**（替换单一 `employee_dependency_unavailable`）：
   - `employee_dependency_deprecated`：宽限期内，可用但提示；
   - `employee_dependency_disabled`：硬停用 / 过宽限，不可用；
   - `platform_price_unknown`：价格未知（建议不阻断，见 §3.9）。

### 3.5 用户端提示与降级（三态）

`availability_reason` 从二态扩为三态：

| availability_reason | 用户可见 | 是否阻断 |
|---|---|---|
| `employee_dependency_deprecated` | 会话顶部横幅：「该员工使用的模型将于 X 日下架，请联系企业管理员切换」 | 否 |
| `employee_dependency_disabled` | 弹窗 + 输入框提示：「平台已下架该模型，请联系企业管理员切换」 | 是（409） |
| `employee_unavailable` | 「员工已下架，无法继续对话」 | 是 |

- 宽限期内**不阻断**，但持续提示；硬停用才 fail-closed。
- **恢复**：管理员切换模型后 employee version 递增，Agent 下次 sync 拉到新快照，自动清除标记，**用户无需重新登录**（现有 `replaceProjections` 已支持覆盖）。
- 桌面端 `GrantsSyncNotice` 与 `employeeAvailability` 同步扩展三态文案。

### 3.6 群聊场景（coordinator + participant）

群聊结构：1 个 coordinator（协调专家）+ N 个 participant；**无 @ 消息只投递 coordinator**，**@ 消息直接投递 participant**（不经过 coordinator），coordinator 通过 `mention_employee` 工具主动 @ 成员（`session-host.ts:1775`）。

**现状场景矩阵**

| 场景 | 实际表现 | 是否牵连别人 |
|---|---|---|
| coordinator 模型停用 | 无 @ 消息：`assertRunnableTargets` 检查 coordinator → 409，整条发不出；有 @ 消息：直接投递 participant，可用；coordinator 无法再用工具 @ 人 | 只阻断无 @ 消息 |
| participant 模型停用 | 人工 @ 他：409，整条发不出（即使同时 @ 别人）；coordinator 工具 @ 他：工具返回 error，coordinator 可改 @ 别人 | 人工多 @ 时可能阻断整条 |
| 其他 participant | 正常 | 不受影响 |
| 进行中的 Run | 不中断（sync 无取消逻辑） | — |
| custom / free 群 | 可通过成员编辑移除 / 替换（coordinator 不可移除，`server.ts:2054`） | — |
| solution 群 | roster 冻结，不可通过成员编辑替换（`editableGroupKind` 不含 solution 群） | 恢复路径长 |

**问题**：

1. **coordinator 单点故障**：coordinator 停用 → 所有无 @ 消息失败，群聊基本瘫痪。
2. **人工多 @ 全有全无**：一个不可用成员让整条消息发不出。
3. **coordinator 不知成员不可用**：`buildGroupContext` 只给名字 / 角色 / 工具，不给可用性，可能反复 @ 同一不可用成员。
4. **solution 群 roster 冻结**：用户端无法替换被停用成员，必须走 Manager / 方案侧。
5. **群级别无健康提示**：用户不知道群里谁不可用、为什么。

**建议**：

| 场景 | 建议 |
|---|---|
| coordinator 不可用 | 群顶部横幅「协调专家暂不可用，@提及成员可直接投递」；无 @ 消息保持阻断（降级选人涉及编排语义变化，风险大）；Manager 侧提供「更换协调专家」 |
| participant 不可用 | 工具 @ 失败错误带 `employee_dependency_disabled`；把不可用成员写进 `buildGroupContext`，coordinator 一开始就避开 |
| 人工多 @ | 改为部分投递：可用的先投递，不可用的汇报给用户；至少前置校验返回明确列表让用户确认 |
| roster 维护 | custom / free 群：前端暴露移除 / 替换；solution 群：允许管理员替换单个成员（version 递增、roster 重新冻结） |
| 群健康 | 群详情页显示成员可用状态与原因；下架事件触发时在群内提示 |
| 恢复 | 切换模型 → version 递增 → sync 更新 snapshot → `available` 自动恢复；更换 coordinator 后重新冻结 solution roster |

**本节决策项**：见 §9 第 6–9 条。

### 3.7 已冻结会话与运行中 Run

- 原则不变：已开始 Run 不被改写（D5 / F11）；已装载 session 在 Manager 离线期继续工作（D14）。
- 下架只影响「新快照下发」，不会打断正在执行的会话——这是现有设计的正确部分，需在新链路中明确保留。

### 3.8 可选：主备模型兜底（P2）

- employee 配置增加可选 `fallback_model_ref`，快照冻结主备两个模型。
- 主模型不可用时，Agent 在本地自动切换到备用模型（不跨端拉新配置）。
- **必须由企业管理员显式配置**（成本 / 质量变化不能由平台静默决定）；用户不能自选。
- 建议作为可选项，不做默认；避免引入「平台替企业选模型」的责任问题。

### 3.9 价格未知的处理

- `platform_price_unknown` 建议**降级为「按 unknown 计价 + 上报」**，不硬阻断执行。
- 仅当模型本身不可用（`disabled` / 过宽限）才拒绝快照。
- 理由：价格同步延迟不应让正常员工不可用；同时保留「未知价格不伪装为 0」的口径（D18）。

## 6. 安全与隐私

- 通知与投影**不含上游 / 管理密钥**，不含会话内容（D18 / D13）。
- 影响面统计只出聚合计数（tenant 数、employee 数），不出会话 / 执行明细。
- 审计：Operator 记录下架动作与影响面；Manager 记录员工标记与模型切换；Agent 不新增上传内容。
- 错误体不含密码、token、provider key、会话内容（AGENTS §13）。

## 7. 接口草案（需评审）

**运营端** `/api/operation/*`

- `POST /providers/{provider_id}/models/{model_id}/unpublish`（body：`sunset_at?`、`reason?`）
- `POST /providers/{provider_id}/models/{model_id}/disable`
- `GET /providers/{provider_id}/models/{model_id}/impact`（聚合：tenant 数、employee 数）
- `POST /providers/{provider_id}/disable`（provider 级）

**跨端契约（`CatalogReleaseNotify`）**

- `catalog_type` 增加 `platform_model | platform_provider`
- `action` 增加 `deprecated | disabled`

**企业端** `/api/manager/*`

- `GET /employees?dependency=unavailable`（或列表字段）
- `POST /employees/batch-switch-model`（body：`employee_ids`、目标 provider / model）

**用户端** `/api/agent/*`

- 沿用 `availability_reason` / `availability_revision`，取值扩展
- 快照附带只读 `deprecation` 元数据

全部遵循统一 envelope、`application/problem+json`、幂等键。

## 8. 分阶段实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 感知 | Operator 下架动作 + 通知扩展；Manager 收通知扫描受影响员工 + 列表警示 | 下架后 Manager 能列出受影响员工；未收到通知时 Agent 拉快照失败也能兜底发现 |
| P2 处置 | Manager 批量切换模型；version 递增；旧会话历史保留 | 切换后 Agent 自动恢复，无需重新登录 |
| P3 分级 | 三态 `availability_reason` + 宽限横幅 + 文案可操作；群聊 roster 可用状态、coordinator 提示、工具 @ 错误语义 | 宽限期内不阻断；硬停用有明确指引；价格未知不误伤；群聊不可用成员不阻断其他成员 |
| P4 可选 | 主备模型兜底；价格 unknown 降级为记账 + 上报 | 管理员配置备用后主模型不可用自动切换 |
