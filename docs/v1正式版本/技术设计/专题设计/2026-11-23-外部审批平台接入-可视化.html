核心只实现一条与平台无关的统一链路（插件 → 任务 → 员工会话 → 建议 → 本人确认 / 有条件放行 → 插件写回 → 对账），钉钉、氚云、飞书各以一个平台插件接入；桌面端把任务交给本地 AI 员工和本地审批群聊，经用户确认（或命中本人开启的有条件自动放行规则）后，以自己的第三方身份完成最终处理；申请人可在提交前对材料做预检。

一条统一链路

核心与平台无关：收单 → 建议 → 本人确认或有条件放行 → 写回 → 对账；平台差异收在插件的 9 个方法里，接新平台核心零改动。

桌面端单端

任务数据与审计在桌面端；凭据托管、事件接收与写操作承接方待定。

默认用户确认

AI 员工只形成建议；默认由用户确认后提交，本人开启且命中有条件自动放行规则时例外。

1 解决什么问题

现在的问题本方案怎么解决谁受益
三个平台的 ID、认证、事件和动作不同一条统一链路 + 平台插件（ExtApprovalPlugin 9 个方法），差异收在插件内，核心与平台无关用户和后续平台接入

3 触发事件与数据流

桌面端主动访问外部平台，平台不向用户机器发起 HTTP 入站。审批原文和运行事件留在本机，Manager 不进入审批执行路径。

3.1 总图：谁在哪一端做什么

虚线表示桌面端主动访问或本地跨组件调用，没有到用户机器的外部入站箭头。

3.2 业务事件 11 个，不单建事件表

每个事件落为 ext_approval_task 的状态与原因码变化，或 ext_approval_execution 的一行或状态变化；诊断信息写本地脱敏结构化日志。

外部任务

task_received 插件返回新引用，读详情、存白名单快照、路由 → task open。

task_changed externalVersion 或处理人变化，旧建议作废 → stale。

task_closed 他处已处理、撤销、超时、转交 → done + 原因码。

路由与建议

route_blocked 无绑定、多绑定冲突、员工不可用 → blocked + 原因码。

proposal_submitted 负责员工调用 approval_submit_proposal，校验结构后存 proposal_json。

本人确认

decision_requested 用户在 UI 发起确认，只生成待确认记录 → execution pending。

decision_confirmed 宿主经私有通道确认，或有条件放行双闸门通过 → executing。

写回与对账

execution_finished act 已受理且对账确认 → execution confirmed，task done。

execution_unknown 超时或结果暂不可确认，禁止直接重试，进入对账。

execution_failed 重读发现变化、身份不符或插件明确失败 → stale / blocked。

连接

connection_degraded 凭据过期、权限变化、同步失败：停写回、保留任务、提示重新授权 → binding 状态 + task blocked。

业务反馈（不是事件）

按原建议执行 / 修改后执行 / 推翻建议追加为 ext_approval_execution 的 feedback 条目（accepted / edited / overruled；补打分与标记误放行同样追加），不单建反馈表，不改已写入的行。

事件乱序、重复或断线恢复时，以 getTask 读到的外部详情修正状态。

3.5 AI 建议的依据链

建议不能是一段无法追溯的结论。四层依据进入分析，每条理由必须指回具体来源，执行结果再回流成下一轮的先例和反馈。

四层依据（缺一层就不能声称有依据）
层来源首期
制度企业上传的制度文件版本必选 未装载降级为「无依据」
流程规则Manager 规则投影（本机只读）：金额阈值、必需材料必选
历史先例已 done 的 ext_approval_task 与对应执行记录可选 样本不足不引用

7 责任主体与交付边界 谁来做这一次性的配置

技术上可接入不等于普通用户能自行接入。把一次性配置和日常使用拆开，才能既不骗用户，也不把工程量藏起来。

事项责任主体交付形态
企业应用创建、凭据填写、事件订阅、权限申请企业管理员 或 我方实施方管理员后台或实施方远程配置，不在桌面端普通路径
氚云自定义接口代码和发布实施方属于氚云插件交付物（P3），不进入核心；版本化维护
用户身份授权、流程选择、AI 员工选择每个审批人自己桌面端通用接入向导（按插件授权步骤），三步完成
制度文件上传和阈值维护企业管理员 或流程负责人企业侧 Manager 维护，桌面端「制度与规则」页只读展示
试运行自检和开启绑定审批人，管理员可代配置默认值桌面端向导内完成
对外口径只能说「两步走」：企业管理员在第三方开放平台建企业自建应用并在企业侧 Manager（生产部署在企业服务器上，由平台方实施交付、企业持有，与 Operator 分离部署）配置规则与治理策略（应用 Secret 的托管与换票方式待 P0 后裁决；若由企业侧托管且实施方代录，交付验收时须由企业重置/改写），之后普通员工在桌面端扫码完成本人 OAuth 授权即可使用。不得宣传企业零配置或应用市场一键免配接入。数据面与执行面固定在桌面端，不引入我方（运营端 Operator）云侧审批组件；开发与测试环境直接按正式独立部署条件验证，不做运行期部署形态开关。

7.2 数据防截取与防偷传的技术保证（有条件表述）

受控网络与完整出网白名单

Node Agent 仅监听 127.0.0.1（Bearer JWT + CORS 来源白名单 AITEAM_AGENT_ALLOWED_ORIGINS），零公网入站。企业出口防火墙白名单须覆盖：第三方平台域名（*.dingtalk.com / *.feishu.cn / www.h3yun.com）、企业模型/Relay 端点、企业侧 Manager 及交付包声明的静态资源（当前未启用 updater；交付前须收紧 tauri.conf.json 的 img-src 去掉通配 https: 并清理测试服硬编码地址，或按实显式声明）。

控制面数据面脱钩与策略契约

桌面端主动向 Manager 拉取治理策略（离线分层降级：人工沿用缓存、自动放行超时 24h 降级人工、治理摘要默认关）。摘要上报经白名单契约强拦截，治理摘要开启时桌面端常驻提示员工；孤岛模式可关闭上报。

凭据分层与本机防护边界（按实写）

用户级 Token 存本机凭据存储（McpCredentialStore）；应用 Secret 托管与换票待定。SQLite 依赖目录权限与 OS 全盘加密；同一操作系统账户下的其他进程无法阻挡。

模型路径与记忆/附件边界

v1 经平台内部 NewAPI Relay（私有化模型路径待定）：正文经过 Relay 与上游模型提供方（不落 Manager 业务库）。附件默认按次授权（on_demand）；审批会话不写记忆，知识库默认关闭。

企业白盒审计抽检标准（须对照所选部署前提）：企业安全团队可在测试机运行 Wireshark/mitmproxy 抓包，核验交付包 CSP 收口基线，验证全部出站命中声明白名单且发往 Manager 的请求不含表单正文、附件与聊天记录；核查分层守卫测试与离线/孤岛降级行为。
