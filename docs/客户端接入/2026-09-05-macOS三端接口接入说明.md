# macOS 三端接口接入说明（原问题 1—20）

本说明针对三端复合客户端：平台运营模块直接调用 Operator，企业管理模块直接调用 Manager，本地聊天/执行模块调用用户本机 Agent。分别维护 base URL 和对应身份；企业 token 不能冒充 Operator 平台身份。不新增 Agent 通用代理，不把会话、工作正文或执行明细上传控制面。当前执行链是本机 Pi Session，不是旧 Run/Task 执行引擎。

接口字段、必填项、响应类型、错误和示例，以实际运行版本的 API Docs 为准，本文只说明接哪一端、哪个入口及客户端如何改，不手工复制完整接口定义。

测试环境公开文档入口：Operator [API Docs](http://121.40.78.201:8781/docs) / [OpenAPI](http://121.40.78.201:8781/openapi.json)；Manager [API Docs](http://121.40.78.201:8782/docs) / [OpenAPI](http://121.40.78.201:8782/openapi.json)；测试 Agent [API Docs](http://121.40.78.201:8783/docs) / [OpenAPI](http://121.40.78.201:8783/openapi.json)。本机 Agent 则使用第 16 项发现的 base URL 加 `/docs`、`/openapi.json`。

上述 taiyi 三个地址分别为 `http://121.40.78.201:8781`、`:8782`、`:8783`，仅用于 TEST。本文“本轮新增/补齐”能力要求服务端和本机 sidecar 均使用包含 macOS 三端接入补齐的版本；联调前按发布说明核对已部署版本与实际 OpenAPI 中的接口/字段，不能只凭 `/healthz` 返回 200 判断支持。本文不构成这些能力已在 TEST 发布的承诺，也未提供生产地址、公钥或正式安装包。taiyi 的远程 Agent 不是最终用户本机 Agent，不能作为本地服务失败后的兜底数据面。

## 1. 市场招人：改接 Manager，不恢复 Agent recruitment

不要再调用拟议的 `POST /api/agent/recruitments`。复合客户端的企业招募模块直接调用已有 Manager `GET /api/manager/recruit/catalog/experts` 浏览目录、`POST /api/manager/recruit/experts` 招募，使用对应企业的 owner/enterprise_admin 权限及 Docs 要求的幂等信息。招募生成企业员工实例，不等于自动成为所有成员可执行的员工；完成实例配置、生命周期与成员授权后，本地模块调用 Agent `POST /api/agent/grants/sync`，再查 readiness。目录真相由 Operator 发布，但企业招募不应持平台管理员 token。

## 2. 会话摘要与未读数：使用真实 metadata

Agent `GET /api/agent/conversations` 及 `GET /api/agent/conversations/{conversation_id}` 本轮补齐真实 `last_preview`、`unread_count`。客户端移除 mock 摘要/未读计数：空或仅内部消息的会话摘要为空，未读只统计已读位置后的可见 assistant 消息，不把群 fan-out 输入或 streaming delta 多算。读到消息后用既有 PATCH/PUT metadata 的 `last_read_entry_id` 标记，推荐传 entries 返回的 `entry_ref`；非法、歧义、跨会话引用会被拒绝。会话列表继续原样传回 `page.next_cursor`，同时间戳也按稳定次序翻页，不把会话 ID 或当前时间拼成新游标。

## 3. 群聊真实成员与人数：调用 participant roster

本轮新增 Agent `GET /api/agent/conversations/{conversation_id}/participants`。客户端群成员弹窗、头像组和人数使用这里的真实固定 Pi participant 列表，不再用 `grants/experts` 的授权全集代替群成员。`employee_count` 只计数字员工，不计本机人类用户；协调者/参与者角色与岗位不是同一字段。历史撤权员工仍可见但 `available=false`，不能据历史可见性允许新投递；该可用性也不是上游模型或网络健康保证。服务不返回 Session 文件、workspace 或凭据。

## 4. 附件下载：已有带授权的二进制路由

使用 Agent 已有 `GET /api/agent/conversations/{conversation_id}/attachments/{attachment_id}` 下载附件，产物对应 `.../artifacts/{artifact_id}`；列表、上传、删除沿用同组既有接口。客户端用当前本地身份发请求，再将二进制保存到用户指定位置或创建受控临时展示 URL，不期待 metadata 自带公网下载地址，不把 bearer token 放 URL。文件 owner 校验与会话一致，不能改为云存储公开链接，也不将本地路径暴露给 WebView。

## 5. 正式 Manager 地址与 JWKS：机制已有，配置交付须独立确认

Agent 已支持公共 RSA RS256 JWKS 和 issuer/audience 本地验签；本轮补齐安装说明，未交付生产配置。客户端安装/升级除了复制 `agent.env`，文件型 JWKS 还须同时复制对应 `manager-jwks.json`。相对路径以所选 env 文件目录解析，内联 JSON 非空时优先；仅复制 env 会导致公钥文件缺失。

正式 Manager HTTPS 地址、准确 issuer/audience、可信公钥及技能验证公钥由部署方通过受控通道提供。issuer 必须逐字等于 Manager 签发值，不自动等于 Manager URL；现有正式打包器要求 HTTPS URL 型 issuer。公钥在启动时加载，不自动发现 issuer、抓取未知公钥或热更新。轮换先分发可信新旧公钥并重启，再切签名，重叠窗口结束后受控移除旧 key 并重启。完整启动/配置步骤见 [sidecar 集成说明](../../deploy/agent/CLIENT-INTEGRATION.md) 和 [公共配置模板](../../deploy/agent/config/agent.env.example)。禁止打包密码、私钥、service token 或 Provider/Hindsight/LightRAG secret。

## 6. 办公 feed 与 tasks/stats/logs：接真实来源，删除 mock

`getOfficeFeed` 应调用已有 Agent `GET /api/agent/office/feed`；它是本地定时会话摘要，不是所有工作事件的历史流。办公当前场景调用已有 `GET /api/agent/office/scene`，本轮修复冷读历史与补齐展示字段；它是近期会话活动概览，不是全量审计记录。工作列表/日志使用第 18、20 项新增 work-records，统计卡使用第 19 项；实时会话仍走现有 `.../events` SSE。客户端分别接入并显示空、未知、离线状态，不用静态任务数、随机事件或 mock 成功率补空白。

## 7. OfficeSceneEmployee 部门与岗位：展示全部真实关联

Agent `GET /api/agent/office/scene` 本轮明确提供 `department_ids` 与 `role_title`。部门是 Manager 员工配置的完整多部门集合，不是自动猜出的主部门；岗位缺失返回 null，部门缺失返回空列表。客户端可显示“岗位未设置”，但不要把 member/owner 权限、员工 persona 或模型名称当成岗位。需要部门名称时，复合客户端从已有 Manager `GET /api/manager/departments` 或组织树按 ID 关联，不能硬编码部门标签。

## 8. OrgTreeNode 岗位与 assignment 标识：统一一个拼写

企业组织模块使用已有 Manager `GET /api/manager/org/tree`；Agent `GET /api/agent/org/tree` 仍只是当前成员可见的只读裁剪投影。本轮员工节点增加唯一岗位字段 `role_title`，不新增 `position_title`/`role_name` 别名。岗位不是账号角色。多部门员工会在各部门下出现，客户端树节点 key 应包含父部门上下文；员工实体仍按同一个 employee 节点 `id` 识别。组织调整使用这个 employee_id，既有 assignment 响应也以它为 `assignment_id`，没有新分配表或需要客户端推导的独立 assignment ID。

## 9. 编辑部门归属：改接已有 Manager PATCH

不要调用拟议的 Agent `PATCH /api/agent/org/assignments/:id`。使用 Manager `PATCH /api/manager/org/assignments/{employee_id}`，仅 owner/enterprise_admin 可写；该接口是追加一个真实部门，重复追加不会重复写入，也不会替换原部门。需要替换/清空全部部门或修改岗位时，先读员工完整配置，再用 Manager `PUT /api/manager/employees/{employee_id}` 完整提交；PUT 省略 `department_ids` 会清空部门，省略或 null 的 `role_title` 会清空岗位，不能把它误用为局部 PATCH。实际配置变化会推进版本，客户端再触发 Agent grants sync 感知，不直写本地投影。

## 10. ExpertProjection 岗位与用量：岗位内联，用量专用查询

Agent 已有 `GET /api/agent/grants/experts` 返回当前成员已装载专家及技能引用，本轮显式补齐 `role_title` 和全部 `department_ids`。客户端不再等 `role_name`，也不把列表里缺少 `usage_summary` 视为可填零；按 employee_id 调第 19 项本机统计，需要逐次记录则调第 18 项。模板、企业实例与本机执行记录是不同对象，不能用模板 ID 拼员工用量，也不能把另一成员或另一台设备的统计混入本机卡片。

## 11. 消息全文搜索与历史分页：新增本地只读查询

本轮新增 Agent `GET /api/agent/messages/search`，按完整脱敏后的可见文本做大小写不敏感的字面搜索，可按会话/实际发送员工筛选；不搜索 thinking、工具或内部内容，不上传正文。客户端展示安全 snippet，按返回的 conversation_id 与 `entry_ref` 调 `GET /api/agent/conversations/{conversation_id}/entries` 定位。

entries 不带查询参数保持旧响应；带分页参数后按历史正序读取，搜索结果则最新优先。`entry_ref` 用于稳定消息身份/已读/定位，分页 cursor 用于原样续页，两者都不是 SSE `after`/`Last-Event-ID`。多个员工的原始 Pi `id` 可能相同，客户端应按 `entry_ref` 去重；不要承诺离线重放曾经所有 transient delta。筛选变化重置分页，非法或跨作用域游标返回 422。

## 12. 市场详情描述与技能：透出真实信息，不造商业字段

Agent 已有 `GET /api/agent/marketplace/templates` 与 `.../{template_id}` 本轮保留上游 `description` 及固定 `platform_skill_refs`（技能 ID、版本、内容哈希），计数优先依据合法现代引用，包括明确空列表。旧目录未提供固定引用时为 null，不从旧 ID 猜版本。复合客户端也可直接使用 Manager `GET /api/manager/recruit/catalog/experts` 的完整可招募目录按 template_id 选详情。

客户端可展示描述、固定技能与真实计数；模板 `usage_stats`、`price_tier`、跨企业商业使用统计没有本轮业务来源，不伪造为“免费”、零 token 或平台热度。未提供的招募计数为 null，不是零家企业；`is_recruited` 只代表当前企业已有有效实例。Operator 平台模型价格不是模板商业套餐价格，二者不能互相代填。

## 13. 市场搜索、分页与标签：当前客户端过滤

当前 Agent/Manager 小目录没有本轮新增的服务端市场关键词索引、分页或 tag 查询协议。客户端一次读实际可见目录，做名称/分类过滤；已有 tags 可展示，不把它当已经实现的服务端筛选参数。市场返回空 page cursor 不表示服务端市场翻页已支持。这里明确仍未实现的市场索引，与第 11 项已经实现的本机消息全文搜索是不同能力，不能混写为“全文搜索仍未实现”。

## 14. KnowledgeBase 管理：复合客户端直接调用 Manager

Agent 旧 `/api/agent/knowledge-bases` 系列返回 410，本轮不恢复本地知识库管理副本。企业知识页面先调用已有 Manager `GET /api/manager/knowledge-spaces`，使用服务返回的唯一企业知识空间 ID，再读取详情、更新展示名和管理文档；不要硬编码 ID 或实现通用多知识库新增/删除界面。当前每个 Manager 只有一个企业共享知识库，不支持创建第二知识库或删除企业知识库（删除返回 409）。知识管理写操作要求 owner/enterprise_admin 权限。

文档列表/上传在 `.../{knowledge_space_id}/documents`，URL 导入、文档删除、重试、重建索引和 ingestion 状态按 Manager Docs 使用；这里的文档删除不等于删除企业知识库。企业上传资料是显式知识管理操作，不是把普通聊天历史上传。

执行时仍由本机 Agent 的 Pi 知识工具通过 Manager 受控 RAG MCP 查询，不让客户端/模型选择企业 workspace 或直连 LightRAG。公共配置示例是 `AITEAM_RAG_MCP_URL=https://manager.example.com/api/manager/rag/mcp`，必须与 Manager 同 origin；测试值可用 `http://121.40.78.201:8782/api/manager/rag/mcp`。客户端既不要向 Agent 旧管理接口写，也不要把 LightRAG 密钥加入 sidecar 配置。

## 15. 市场招募前能力要求：与招募后实例绑定分开

已有 Manager `/api/manager/employees/{employee_id}/knowledge-bindings`、`connector-bindings`、`memory-setting` 管理招募后企业员工的知识、连接器、记忆配置，按该端权限及 Docs 接入。市场模板的 `knowledge_bindings`、`connector_requirements`、`default_memory_config` 尚无本轮明确的“招募前要求”契约。客户端隐藏或显示“模板未提供”，不能把某企业实例绑定、凭据、员工个人记忆配置拼入公共市场详情，也不能根据能力缺失推断一个默认要求。

## 16. 动态端口与 get_agent_base_url：原生宿主提供 IPC

Agent sidecar 已支持 `--port 0` 和 `DATA_DIR/agent-port.json`。原生宿主启动单实例进程后检查 port file 中的 PID 与本次子进程一致、host 为 loopback、端口合法，再检查 `/healthz` 和 `/readyz`；随后通过自己实现的 `get_agent_base_url` IPC/preload 返回 URL 给客户端 API 层。这个 IPC 不是后端新增 HTTP endpoint。

客户端所有本地请求使用发现的 URL，不写死 8180、8783 或安装时缓存端口；重启后重新发现。WebView origin 按公共配置精确允许，不用 `*`；退出等待子进程结束。升级替换 sidecar 代码/公共配置与配套公钥，但保留用户 DATA_DIR。taiyi 服务部署不会升级用户已安装的 sidecar，本轮 Agent 新能力须另外安装包含对应代码的包，并核对本机 OpenAPI。

## 17. AuthClaims.tenant_id：Agent 成功身份收紧

本轮 Agent 专用登录/重置结果和 `GET /api/agent/whoami` 的成功身份契约明确 `tenant_id` 为必有非空字符串；空企业、无企业或与当前身份矛盾的结果不能成功。客户端移除“登录成功但 tenant_id=null 仍继续聊天”的路径；按既有 `POST /api/auth/resolve-tenant-by-account` → `POST /api/agent/login` → whoami → grants sync/readiness 接入，503 依赖离线不等于本地进程未启动。

不要全局收紧三端共用 DTO：Operator 平台身份仍允许 nullable tenant_id，平台操作使用平台身份；Manager 企业身份与本机会话身份需保持对应。正式验签仍要求可信公钥和完全匹配的 issuer/audience，不因本项调整而容忍未知签名。

## 18. 名下员工工作历史：本轮新增观察记录

使用新增 Agent `GET /api/agent/work-records`，按当前认证成员、本机范围读取，可按员工与精确 UTC 时间范围筛选。记录对应一次实际员工 Pi prompt，包括用户群投递及协调者向成员投递；不是一条 HTTP 收据，更不是新 Run/Task 执行引擎。客户端展示真实开始/结束、观测结果、来源/条目位置、安全任务与结果摘要，以及有来源时的 token/费用；成功、错误、中止、仍执行和未知要分别处理，不能把 Promise resolve 当成功。

旧 Pi 历史会明确标识 `pi_history` 来源，只使用实际 Pi entry 时间，真实 prompt 起止、逐项用量/价格不可恢复时为 null；不要给老数据补假分钟精度、平均费用或默认成功。若原 Session 条目已缺失或其身份与记录区间不符，引用与摘要返回 null，客户端显示“原消息不可定位”，不能用另一条相同位置的消息代替。崩溃未确认的执行保持 unknown，不重放重计。会话删除会清除可定位工作内容与消息搜索结果，客户端同时处理第 20 项删除标记；正文始终留在本机。

## 19. 总花费与任务数：区分本机执行统计和企业汇总

本轮新增 Agent `GET /api/agent/usage/statistics`，统计当前成员在这台设备上的已记录小时摘要，包含 pending/sending/sent/failed 全部状态，不能只算未上报 outbox。计数口径是员工执行次数；群一次输入可能触发多个员工执行，客户端应标“员工执行次数”，不要称独立用户业务任务数。

范围按执行开始所属 UTC 小时桶取 `[window_start,window_end)`，两端必须一起提供且 UTC 整点对齐，否则 422；都省略读取全部留存摘要。它与第 18 项精确工作时间不是同等粒度，不能把某一分钟的历史列表行费用与整小时总额硬对齐。费用以高精度 USD decimal string 累计后最终显示舍入；未知总价为 null，同时有已知小计/未定价覆盖提示，不显示“未知=0”。已上报和删除会话后的无会话引用小时汇总仍保留，不缩水，也不把保留费用分摊给旧工作行。

企业所有成员/设备的摘要总览使用已有 Manager `GET /api/manager/billing/usage/overview`、`.../usage/records` 或 `/api/manager/usage/rollup`（权限、时间口径按该端 Docs），通过企业模块直连。这些是上报聚合，可能滞后，不是本机实时详情；不因企业统计需要而上传会话/工作正文。模板商业价格与跨企业市场使用统计仍不是这些接口的含义。

## 20. 历史向前翻与新变化轮询：不同游标，按 ID 合并

工作历史 `GET /api/agent/work-records` 的 `before` 消费上一页 `page.next_cursor`，用于加载更旧记录。首次历史响应保留 `meta.after` 水位，后续历史页延续该水位；加载历史后从此调用新增 `GET /api/agent/work-records/changes` 的 `after`。每次轮询用最新 `page.next_cursor` 续读，空页的游标也继续保留；`has_more=true` 应立即继续消费。

changes 返回同一记录的最新 upsert 和最小 delete，不只是新增行；客户端按 opaque 记录 ID 替换或删除，才能看到已加载 active 记录的完成/失败/中止及会话删除。它不是每个中间事件的永久回放，游标是稳定 keyset 而非内容快照；不以 created_at、最后一条时间、Pi entry_ref 或 SSE ID 代替 after。

变更流只接受当前 owner/可选 employee 筛选，不接受历史时间、会话或结果筛选。时间筛选页面仍订阅同 employee 的变更流，upsert 后重新应用本地时间条件，delete 按 ID 移除；更换员工或身份必须重置游标。删除标记不带会话/条目/标题/路径/工作时间，只保留 owner/员工作用域的 opaque ID 与变更次序，不能据它重新定位已删除正文。
