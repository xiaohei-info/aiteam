# 创建群聊：后端改造方案

日期：2026-09-11
状态：前后端已实现，待合并和发布；自定义建群使用独立新接口，旧接口保留原创建路径。
后端仓库：`FredServer`，主要改动范围为 `server/agent_service`。

## 1. 目标与范围

支持客户端通过以下三个步骤创建群聊：

1. 基本信息：群聊名称、群简介。
2. 选择成员：从当前授权 AI 员工中多选，并指定一位协调人。
3. 编排方式：自动或自定义。

不增加“确认创建”和“联动模块”。群配置与会话数据仅保存在用户端 Agent 本地，不写入 Manager 或 Operator。

新建群聊不再必须绑定协作方案。群成员由用户明确选择，协调人复用现有群内 AI 员工角色，不新增独立 Agent 或另一套工作流执行内核。

本期在创建时保存配置，用户发送任务后才执行协作。编辑已有群成员、修改运行中的编排、严格工作流节点恢复不属于本期范围。

## 2. 业务定义

| 概念 | 定义 |
| --- | --- |
| 协调人 | 群内一位 AI 员工，负责分工、传递结果、追踪进度和汇总回复；对应现有 `coordinator_employee_id` |
| 群简介 | 描述群用途；自动模式下作为编排依据，自定义模式下仅保存和展示，不作为额外编排指令注入 |
| 自动编排 | 协调人根据群简介、所选员工简介与能力、本次用户任务规划协作 |
| 自定义编排 | 协调人根据用户保存的协作提示词、所选员工信息和本次任务推进协作 |
| 成员名单 | 本次建群明确选择并持久化的员工集合，不随全部授权员工列表自动扩张 |

“我”不作为后端可猜测的身份。客户端若提供该快捷写法，必须明确显示其指向当前协调人，并在提交前转换成员工 ID 引用。现实用户参与使用“向用户提问”等描述，不伪装为员工成员。

## 3. 改造前的实现与缺口

当前已经具备：

- `POST /api/agent/conversations` 创建会话。
- `coordinator_employee_id` 和 `solution_instance_id`。
- `conversation_participant_session` 持久化成员及协调人角色。
- `GET /api/agent/conversations/:id/participants` 读取真实成员。
- `SessionHost.buildGroupContext` 组装成员简介、能力和方案协作说明。
- `mention_employee` 调用群内员工并返回其实际结果。
- `work_id` 关联一次员工执行的实时事件和历史记录。

当前缺少：

- 会话级群简介及自动／自定义编排配置。
- 客户端提交任意合法成员组合的创建契约。
- 根据新编排模式组装执行上下文的逻辑。

现有无方案群初始化时会从授权员工列表生成成员。新建自选成员群必须改为使用提交名单，不能继续沿用此回退逻辑。

## 4. 创建接口扩展

新增 `POST /api/agent/conversations/custom-group`，自动与自定义编排均通过此接口创建。现有 `POST /api/agent/conversations` 不接收新配置字段，保留原行为。

### 4.1 字段定义

以下上限已落实到 OpenAPI、服务端校验和客户端；标题上限保持 200 字符。

| 字段 | 类型 | 新建自选成员群的约束 |
| --- | --- | --- |
| `id` | string | 可选；客户端建议每次创建意图生成一个固定 ID，用于请求结果不确定时恢复 |
| `kind` | 不提交 | 新接口由服务端固定为 `group` |
| `title` | string | 去除首尾空白后必填，最多 200 字符 |
| `description` | string / null | 群简介，最多 4,000 字符；自动模式必填，自定义模式可空 |
| `member_employee_ids` | string[] | 必填，1–32 位员工；不允许空值和重复 ID |
| `coordinator_employee_id` | string | 必填，且必须属于 `member_employee_ids` |
| `orchestration` | object | 必填，结构见下文 |
| `permission_mode` | 原有枚举 | 沿用原契约和默认值；编排配置不改变工具权限 |

自动模式：

```json
{
  "mode": "auto"
}
```

自定义模式：

```json
{
  "mode": "custom",
  "format": "collaboration-markdown-v1",
  "prompt": "协作目标：完成课程销售方案。\n协作流程：\n1. @{emp_tech} → @{emp_sales}：输出技术亮点并转化为客户价值。\n最终交付：由协调人汇总。"
}
```

建议使用按 `mode` 区分的联合 schema，并关闭未知属性：

- `auto` 不接受自定义 `prompt` 或 `format`，防止隐藏的旧输入参与执行。
- `custom` 要求上述 `format`，`prompt` 去除首尾空白后非空，建议上限 16,000 字符。
- 不支持的格式版本返回可识别的校验错误。

### 4.2 完整请求示例

```json
{
  "id": "group-client-generated-uuid",
  "title": "AI 课程协作群",
  "description": "协同完成课程价值提炼、客户需求分析、交付评估和内容迭代。",
  "member_employee_ids": [
    "emp_sales",
    "emp_tech",
    "emp_pm",
    "emp_content"
  ],
  "coordinator_employee_id": "emp_sales",
  "orchestration": {
    "mode": "auto"
  }
}
```

本期新建自选成员群不同时提交 `solution_instance_id`。混合提交返回明确错误，避免成员来自一套配置、执行规则来自另一套配置。已有方案群走原兼容路径。

### 4.3 服务端校验

校验必须使用当前 caller 的 tenant/member 上下文，不接受客户端自行声明所有者。

1. 校验标题、简介、编排对象和模式间约束。
2. 校验成员数量、重复值以及协调人归属。
3. 逐一检查成员当前授权、撤销状态和员工快照可用性。
4. 校验自定义提示词中的员工引用全部属于提交名单。
5. 任一成员不满足条件时，整次创建失败，不静默删除成员、替换协调人或扩大名单。
6. 对新字段组合不完整的请求报错，不能因为缺少名单而回退到“全部授权员工”。

新接口强制校验成员名单、编排方式和协调人。旧接口继续拒绝这些新字段，不通过字段组合猜测创建路径。

## 5. 自定义协作提示词格式

格式标识：`collaboration-markdown-v1`。

客户端提供以下模板，后端保存其规范化文本：

```text
协作目标：
说明这份协作规则要达成的目标。

执行规则：
按编号顺序推进，后续步骤使用前面步骤的实际结果。
缺少必要信息时，由协调人向用户提问后继续。
无法完成的步骤说明原因，不将其标记为已完成。

协作流程：
1. @{emp_tech} → @{emp_sales}：
   技术专家输出课程大纲和技术亮点；销售顾问将其转化为客户价值。
   交付物：技术亮点与客户价值对照表。

2. @{emp_sales} → @{emp_pm}：
   销售顾问提供客户画像、预算和决策人；项目经理评估排期和资源。
   交付物：交付计划与资源需求。

3. @{emp_sales} → @{emp_content}：
   销售顾问提供客户关注点及竞品信息；内容团队提出课程改进建议。
   交付物：课程改进清单。

4. @{emp_pm} → @{emp_sales}：
   项目经理反馈交付约束；销售顾问调整销售承诺和定价建议。
   交付物：销售承诺边界和定价建议。

最终交付：
由协调人汇总各步骤结果，并列出待确认事项。
```

格式处理规则：

- `@{employee_id}` 为员工引用；显示名称由客户端解析展示，后端不以名称作为身份主键。
- `A → B` 表示 B 使用 A 的产出继续处理；实际结果由协调人负责传递。
- 员工改名不改变引用关系。同名员工必须通过 ID 区分。
- 后端校验引用语法、成员归属、长度和格式版本；不使用模型替客户端猜测缺失成员。
- 模板中的章节与编号用于引导模型理解，不编译成独立任务图或另一个状态机。
- 自定义模式不是严格工作流承诺。若未来需要确定性的分支、节点状态和断点续跑，应单独设计该能力。

## 6. 数据存储与读取

### 6.1 会话存储

建议在本地 SQLite `conversation` 表增加：

| 列 | 用途 |
| --- | --- |
| `description TEXT NULL` | 保存群简介 |
| `orchestration_json TEXT NULL` | 保存模式、格式版本及自定义提示词 |

同步更新 `ConversationRecord`、`ConversationMetadata`、读写映射及数据库升级逻辑。`orchestration_json` 读出后需按受控 schema 校验，不能直接信任任意 JSON。

新增列是当前本地数据库的增量升级，不迁移冻结 MVP 数据。旧会话新增列为空，继续按原有逻辑执行，不能自动将旧群解释为新自动编排群。

### 6.2 成员存储

复用 `conversation_participant_session`：

- 持久化提交的成员，每个员工一条记录。
- 协调人角色为 `coordinator`，其余为 `member`。
- 在创建时校验并记录员工版本，运行时仍重新校验当前授权与有效快照。
- 群成员与“当前授权员工全集”分离；新增授权员工不自动加入已有自选成员群。
- 恢复已有群时读取持久化成员；新配置损坏或成员索引缺失时明确报错，不扩大名单兜底。

### 6.3 读取接口

会话创建响应、详情及列表的 `ConversationMetadata` 中增加：

```json
{
  "description": "群用途说明",
  "orchestration": {
    "mode": "auto"
  }
}
```

新字段对旧会话可为空；成员继续通过现有 `/participants` 接口返回，保持单一权威来源。

本期不在普通会话 PATCH 中开放成员和编排修改；避免引入运行中变更、会话重建及规则版本切换问题。

## 7. 创建一致性与重试

建议创建顺序：

1. 完成请求、身份、成员和编排校验。
2. 在同一数据库事务中写入会话配置和成员索引。
3. 根据明确名单初始化员工 Session；不重新从授权全集推导成员。
4. 初始化全部成功后返回 `201`。
5. 初始化失败时清理本次创建的会话、成员和已创建的 Session 资源；数据库事务不跨越异步 Session 初始化。

保留现有客户端指定 `id` 的机制。后端对已存在且同所有者的 ID 返回 `409 conversation_exists`；其他所有者的 ID 继续返回 `404`，不能泄露其配置。

客户端请求超时或断网后，先查询同一 ID：

- 会话存在且返回的配置、成员与创建意图一致：恢复进入该群。
- 会话不存在：使用同一 ID 重试。
- 会话存在但配置不一致：提示冲突，不覆盖已有群。

客户端“创建中”锁定解决重复点击；固定 ID 与结果查询解决服务端已创建但客户端未收到响应的情况。不能宣称创建接口已经支持 prompt 的 `Idempotency-Key` 语义。

## 8. 编排上下文与执行

### 8.1 自动模式

协调人执行时组装以下上下文：

1. 协调人的原有角色和受控工具规则。
2. 群简介，明确标记为本群协作目标。
3. 当前群成员的稳定 ID、名称、简介、职责和有效能力。
4. 当前用户任务及已有会话上下文。
5. 自动协作要求：按能力选择成员、追踪任务进度、接收真实结果并汇总。

自动规划发生在任务执行时，不在创建阶段调用模型生成一份固定流程。任务不需要所有成员参与时，可以只调用相关成员。

### 8.2 自定义模式

协调人使用以下上下文：

1. 协调人的原有角色和受控工具规则。
2. 保存的自定义协作提示词。
3. 当前群成员的身份、简介和有效能力。
4. 当前用户任务及已有会话上下文。

群简介不作为第二份编排规则注入。旧方案的 `coordinator_instructions`、工作流技能和交付要求也不能自动覆盖新群的自定义规则。

规则要求按顺序执行时，应在前一步结果返回后再请求下一步。当前 `mention_employee` 声明支持并行执行，实施时需检查该模式下的工具调用策略：至少对顺序协作采用串行调用，并要求依赖任务使用前一步真实结果。仅把工具改为串行并不能使自然语言规则成为严格工作流。

### 8.3 复用现有执行链

继续使用：

```text
用户任务
  → 协调人的 Pi Session
  → 读取自动／自定义编排上下文
  → 调用 mention_employee
  → 群成员执行并返回结果
  → 协调人传递结果、推进任务并汇总
```

协调人自己承担的工作由其当前 Session 完成，不调用自身。`A → B` 不要求开放成员之间的递归互调；执行记录应保留实际调用来源，不能把协调人代为传递伪造为 A 直接调用 B。

派发、员工引用解析、授权检查和上下文生成都必须使用同一份持久化群成员索引。尤其需要检查无方案群路径中的授权全集回退，避免自选群成员范围被绕过。

`buildGroupContext` 应只组装本群成员信息。用户群简介和协作提示词作为业务指令，不提升为可覆盖员工授权、工具权限的系统规则。

现有上下文存在整体长度限制。新增规则不能被最后的字符串截断静默删掉：先为编排规则保留预算，再压缩可选历史摘要；必需配置仍无法完整承载时返回可识别错误，不带残缺规则启动任务。

本次不改变现有 `work_id` 含义，也不把所有员工执行合成同一个工作记录。每次员工执行继续使用自己的工作 ID，客户端沿用现有回复归并和单张任务清单展示。

## 9. 错误模型

继续使用已有 `application/problem+json` 结构。以下为建议新增或复用的错误码，需进入 OpenAPI 和客户端映射。

| HTTP | code | 场景 |
| --- | --- | --- |
| 422 | `invalid_group_members` | 成员为空、重复、超限或名单格式错误 |
| 422 | `invalid_group_coordinator` | 缺少协调人或协调人不在所选成员中 |
| 422 | `invalid_group_orchestration` | 模式未知、字段组合错误、提示词或自动模式简介为空 |
| 422 | `invalid_orchestration_reference` | 员工引用格式错误或引用群外成员 |
| 422 | `invalid_group_configuration` | 新配置与旧方案参数冲突或配置不完整 |
| 403 | `employee_not_authorized` | 所选员工未授权、已撤销或有效员工快照不可用 |
| 409 | `conversation_exists` | 当前所有者下的会话 ID 已存在，供查询恢复 |

新接口显式执行 TypeBox schema 校验；结构、长度、枚举、未知属性及重复成员等 schema 错误统一返回 `422 invalid_group_configuration`。通过 schema 后的业务校验按上表返回对应错误码。错误不回显完整群简介、自定义提示词、会话正文或密钥。运行时初始化失败沿用现有服务错误映射，不全部伪装成参数错误。

## 10. 兼容与发布

- 没有新配置字段的旧请求沿用现有创建逻辑，保证旧客户端兼容。
- 已有方案群继续使用原方案与成员规则；不得批量覆盖为新模式。
- 新客户端只在后端明确支持新 schema 后开放自选成员及编排表单；不向旧服务发送会被拒绝的新字段，也不丢弃用户填写内容后降级创建。
- 先发布数据库升级、接口和执行支持，再发布对应客户端。
- 更新 OpenAPI 示例及错误响应，说明新创建路径与旧方案路径的互斥关系。

## 11. 建议文件改动

以下路径均相对 `FredServer/server/agent_service`。

| 文件／模块 | 改动 |
| --- | --- |
| `src/http/server.ts` | 扩展请求和响应 schema；分离新旧创建路径；校验新字段组合；更新错误响应及示例 |
| `src/storage/sqlite.ts` | 新增列及升级逻辑；会话类型和映射；配置与成员事务写入 |
| 新增 `src/groups/orchestration.ts` | 编排类型、格式与成员引用校验、规范化及上下文构造，避免继续堆积到 HTTP 层 |
| `src/pi/session-host.ts` | 按提交名单初始化与恢复成员；按模式生成群上下文；统一派发和引用解析的成员边界 |

具体模块拆分遵循仓库现有分层，新增文件名可在实施时调整；不要增加新的跨端服务或复制一套任务编排内核。

## 12. 实施顺序与验收

### 实施顺序

1. 固化 OpenAPI 字段、校验规则、兼容分支和错误码。
2. 实现数据库增量升级、配置映射和明确成员名单持久化。
3. 接入创建校验、初始化失败清理及读取恢复。
4. 接入自动／自定义上下文和群成员派发边界。
5. 完成集成回归及前后端联调，再发布。

### 必须覆盖的测试

- 自动模式创建成功；群简介缺失或超限被拒绝。
- 自定义模式创建成功；空提示词、未知格式、错误成员引用被拒绝。
- 成员少选、多选、重复、已撤销，以及协调人不在群内的校验。
- 新群只包含提交成员，新增授权员工或服务重启不会扩大名单。
- 同名员工按 ID 区分，员工改名后引用仍正确。
- 群成员和协调人身份不能跨 tenant/member 使用。
- 初始化部分失败后无残留可见群、成员或本次 Session 资源。
