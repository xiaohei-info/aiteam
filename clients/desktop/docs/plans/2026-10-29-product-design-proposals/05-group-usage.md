# 5. 群聊详情增加用量展示

## 5.1 现状

| 项 | 现状 | 依据 |
|---|---|---|
| 群聊详情 | 群名称、简介、群成员、编排规则。**没有用量** | `src/components/Chat/GroupDetailPanel.tsx` |
| 统计接口 | `/api/agent/usage/statistics` **不支持按会话过滤**，只能按员工和时间窗 | `observations.ts` `WorkFilters` |
| 会话级 Token | 聊天状态栏已有：翻页读取全部工作记录，按 `conversation_id` 过滤后求和 | `src/lib/conversationUsage.ts` |
| 工作记录 | 每条有 `employee_id`、`conversation_id`、`occurred_at`、`usage`（含 Token、费用、定价状态） | `observations.types.ts` `WorkRecord` |
| 特殊情况 | 一条群消息可能触发多个员工各执行一次（`LocalUsage` 说明里也写了） | `components/Work/LocalUsage.tsx` |

结论：群聊用量**现在就能算出来**（读工作记录再过滤），但工作记录越多越慢；状态栏每 15 秒就全量翻页一次，已经是潜在的性能问题。要做好需要后端加按会话过滤。

## 5.2 展示内容

群聊详情「群成员」卡片上方新增「用量」卡片，和员工详情用同一个组件（`UsageSummaryCard`），额外加一个**按成员拆分**：

```
┌ 群聊用量 ─────────────────────────── [今日 | 全部] ┐
│  Token        费用          员工执行      参与员工      │
│  342.1K       $1.08         41 次        4 / 5         │
│                                                        │
│  按成员                                                 │
│  主持人 · 小策   ████████████░░░  148K  $0.46  43%     │
│  小李           ██████░░░░░░░░░   88K  $0.27  26%     │
│  小王           ████░░░░░░░░░░░   61K  $0.19  18%     │
│  小赵           ███░░░░░░░░░░░░   45K  $0.16  13%     │
│  ⓘ 一条群消息可能触发多位员工各执行一次                 │
│  ⓘ 仅统计你在这台设备上的使用                          │
└──────────────────────────────────────────────────────┘
```

| 指标 | 定义 |
|---|---|
| Token / 费用 | 本群会话所有员工执行的合计 |
| 员工执行 | 员工执行次数（不是消息条数）；悬停提示「你发送了 N 条消息，触发 41 次员工执行」 |
| 参与员工 | 时间范围内有执行记录的员工数 / 当前群成员数 |
| 按成员 | 每个员工的 Token、费用、占比；按 Token 从高到低排；主持人（协调员工）加标签；已被移出群的员工显示「已移出」但仍计入 |
| 解决率 | 议题 1 上线后，在按成员列表下方显示「本群已评估 9 段，解决 7 段」 |

时间范围只给「今日 / 全部」两档。群聊一般是项目型，「近 7 天」意义不大；需要时再加。

## 5.3 方案

### 方案 A（推荐）：后端加按会话过滤和分组

```
GET /api/agent/usage/statistics?conversation_id=…&window_start=…&window_end=…&group_by=employee
→ { …现有合计字段, "groups": [{ "employee_id": "…", "token_total": …, "cost_total": …, "execution_count": … }] }
```

- 改动在 FredServer `agent_service` 的用量统计查询：加 `conversation_id` 条件和一次 `GROUP BY employee_id`。
- 现有调用方不传新参数时行为不变。
- 聊天状态栏的会话 Token 也改用它，顺便消除 15 秒一次的全量翻页。

### 方案 B（过渡）：前端汇总工作记录

复用 `readConversationUsage` 的翻页逻辑，在前端按 `employee_id` 分组、按 `occurred_at` 过滤今日。

- 优点：不等后端，能马上做。
- 缺点：工作记录多时慢；`usage` 为 null 的记录无法计入，合计要标「部分数据」；和员工详情的统计口径（小时摘要 vs 工作记录）不完全一致，数字可能差几个百分点。

### 推荐

**A**。如果后端排期晚，先用 B 上线，但界面上标注「按工作记录汇总」，A 上线后无感替换。

## 5.4 交互与状态

| 状态 | 显示 |
|---|---|
| 新建群、还没对话 | 「群里还没有员工执行记录」 |
| 部分记录缺用量 | 合计后面加「（部分）」，悬停说明「N 次执行缺少用量数据」 |
| 成员很多（>6） | 默认显示前 5 名，其余折叠成「其他 N 位」，可展开 |
| 点击某个成员行 | 打开该员工的员工详情（复用 `AgentDetailPanel`） |
| 刷新 | 与员工详情一致：60 秒轮询 + 群内任一员工回复结束时刷新 |

## 5.5 视觉规范

- 合计区和员工详情一致（四列数字）。
- 成员占比条：高 6px，`--radius-full`；主持人用 `--brand-gradient`，其他成员用 `--brand` 透明度 0.45；底色 `--surface-3`。
- 成员行高 32px：头像 20px + 名字 + 条 + 数值（`font-number`，12px）。

## 5.6 验收标准

1. 合计等于各成员之和（误差只来自四舍五入）。
2. 今日窗口和员工详情使用同一个 `todayWindow()`。
3. 移出群的员工历史用量仍然计入，并标「已移出」。
4. 方案 A 上线后，聊天状态栏不再全量翻页工作记录。
