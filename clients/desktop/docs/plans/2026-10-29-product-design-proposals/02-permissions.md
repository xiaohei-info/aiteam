# 2. 「允许完全访问」与「授权目录」是否合并

## 2.1 现状：其实是三层，不是两层

| 层 | 用户看到的 | 作用范围 | 管的是什么 | 存在哪 | 依据 |
|---|---|---|---|---|---|
| ① 系统层 | 设置 → 本机文件访问权限；macOS「完全磁盘访问权限」 | 整个应用、整台设备 | AIFred 能不能读某个磁盘位置 | `local-file-access.json` + 系统 TCC | `docs/local-file-access.md` |
| ② 会话沙箱 | 聊天顶部开关「允许完全访问」 | **单个会话** | 员工能不能执行本机命令、读写工作区外的文件、访问网络 | 会话元数据 `permission_mode: read-only \| full-access` | `ConversationPermissions.tsx` |
| ③ 检索目录 | 聊天顶部按钮「授权目录」 | 目录登记对整台设备生效；开关**按员工**生效 | 员工能不能在私聊里检索某个文件夹的纯文本资料（只读，命中片段会发给模型） | 本机 Agent `local-directories` + 绑定 | `ConversationDirectories.tsx` |

②和③并排放在聊天顶部，名字都和「访问文件」有关，所以用户会觉得它们重复。但它们在**范围**（会话 vs 员工）、**能力**（执行和写入 vs 只读检索）、**风险**上都不一样：

| | ② 允许完全访问 | ③ 授权目录 |
|---|---|---|
| 关掉后影响 | 只影响当前会话 | 移除目录影响**所有员工**；关闭开关只影响当前员工 |
| 能写文件吗 | 能 | 不能 |
| 能执行命令吗 | 能 | 不能 |
| 群聊 | 支持 | 不支持（只在私聊里检索） |
| 数据会不会出本机 | 员工执行时读到的内容会进入对话 | 命中片段和文件名会随消息发给模型 |

结论：**两个设置在概念上不能合并成一个开关**，否则用户关掉「完全访问」时会意外丢掉目录检索，或者开启目录时意外放开了命令执行。能合并的是**入口和心智模型**。

## 2.2 方案

### 方案 A（推荐）：入口合并，设置分开

聊天顶部只保留一个按钮「权限」，按钮上汇总状态：

```
[🛡 只读 · 2 个目录 ▾]        [⚡ 完全访问 · 2 个目录 ▾]（金色，提醒风险）
```

点开是一个面板，分两段：

```
┌ 本会话的权限 ─────────────────────────────────────────┐
│ ○ 只读（默认）     员工只能读取工作区内的文件              │
│ ● 完全访问          执行命令、读写任意位置、访问网络         │
│                     仅对本会话生效 · 关闭后恢复只读        │
├ 员工可检索的目录（对「小李」生效）─────────────────────────┤
│ 📁 产品资料   ~/Documents/产品        [开]                │
│ 📁 周报       ~/Desktop/周报          [关]                │
│ + 添加目录                                                │
│ ⓘ 命中的片段会随消息发送给模型 · 群聊暂不支持              │
├──────────────────────────────────────────────────────────┤
│ 系统层：AIFred 未获得「完全磁盘访问权限」  [打开系统设置]   │
└──────────────────────────────────────────────────────────┘
```

- 「完全访问」仍然走现有的三项勾选确认弹窗，不降低安全门槛。
- 面板底部用一行显示系统层①的状态，把三层放在一起说明，系统拦截时不用再到处找。
- 群聊打开时，目录这一段显示为灰色并说明「群聊暂不支持目录检索」，不隐藏，避免用户以为功能丢了。

优点：解决「两个按钮看起来重复」的问题；不改后端；安全语义不变。
缺点：开关「完全访问」从一次点击变成两次（先展开面板）。

### 方案 B（远期）：目录即边界

把两个概念真正统一成「员工能碰哪些目录、能做什么」：

| 目录 | 检索 | 读写 | 执行命令 |
|---|---|---|---|
| ~/Documents/产品 | ✓ | ✓ | — |
| ~/code/项目A | ✓ | ✓ | ✓ |

「完全访问」不再是全盘放开，而是**只在授权目录内**放开读写和执行。

优点：最小权限，安全性最好；用户只需理解一个概念。
缺点：需要内嵌 Agent 的沙箱支持「允许的根目录列表」，属于 FredServer 安全模型改动；网络访问不属于目录，还得另外处理；工作量大。

### 方案 C：不合并，只改名和说明

把「允许完全访问」改成「本会话：完全访问」，「授权目录」改成「员工检索目录」，悬停时说明区别。

优点：零风险。缺点：没有解决「两个按钮重复」的感受。

### 推荐

**现在做 A**。如果后续要做 B，A 的面板结构可以直接扩展成 B 的表格，不会白做。

## 2.3 交互规则（方案 A）

| 场景 | 规则 |
|---|---|
| 按钮状态 | 只读：描边、`ShieldCheck` 图标；完全访问：金色背景、`Zap` 图标。目录数大于 0 时追加「· N 个目录」 |
| 打开完全访问 | 选中「完全访问」单选 → 弹出现有确认弹窗（三项全部勾选才能确认） |
| 关闭完全访问 | 选「只读」立即生效，无需确认 |
| 生成中 | 权限单选禁用（沿用现状）；目录开关可以改，提示「下一条消息生效」 |
| 占位会话 `emp_*` | 沿用现状：先建会话再改权限 |
| 旧版 Agent 不支持目录接口 | 目录这一段隐藏，只剩会话权限 |
| 移除目录 | 沿用两段式确认，并说明「所有员工都将无法检索」 |

## 2.4 视觉规范

- 按钮高 28px，与「问题已解决 / 未解决」分段按钮同一行，左侧放置。
- 面板宽 400px，`--surface-2-glass`、`--radius-xl`、毛玻璃；三段之间用 `--border` 分隔。
- 完全访问选中时，该行左侧 3px 金色竖条，提醒风险级别更高。
- 系统层提示用 `--warning-bg`，只有检测到未授权时才显示。

## 2.5 数据与接口

方案 A 不改接口：
- 会话权限：`PATCH /api/agent/conversations/:id { permission_mode }`
- 目录：现有 `local-directories` 一组接口
- 系统层：现有 `openFilePrivacySettings()`；如需显示「是否已获得完全磁盘访问」，需要 Tauri 侧补一个探测命令（只读探测受保护目录，失败即视为未授权）。这个可以放到第二步。

## 2.6 验收标准

1. 聊天顶部只剩一个权限按钮，状态汇总正确。
2. 开启完全访问的确认流程和现在一致。
3. 群聊里目录段显示为不可用并有说明。
4. 关闭完全访问不影响目录开关，反之亦然。
