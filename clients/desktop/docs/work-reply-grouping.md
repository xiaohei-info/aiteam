# 一次员工回复的实时 / 历史归并

目标：同一员工一次执行的思考、工具及正文在刷新前后保持同一展示分组。

## 最初实施计划（历史记录；现行契约见下）

1. FredServer Agent：复用 `work_record.id`，在 SessionHost 执行期间通过 SSE 输出可选 `work_id`；历史投影使用同 owner、conversation、employee 的 live 工作记录区间关联 assistant/toolResult，保留原始 entry 引用和排序。
2. AITeam：历史按 work + employee 聚合，工具结果只关联同员工同执行；用户输入和员工转交不参与聚合。实时订阅跟踪员工当前 work，新执行使用新气泡；恢复时接续同 work 的历史气泡。对尚未升级的服务，使用现有工作记录 API 的精确输入/输出 entry_ref 补充已成功执行的 work_id。
3. 聚合消息保留原始 entry 引用用于搜索定位；已读仍使用原始历史。统一 thinkingSteps，保留思考与工具顺序。
4. 验证同轮工具循环、交错员工、同员工多次执行、恢复流、停止重发、来源隔离、无 work 旧历史、SSE/历史契约和类型检查。

约束：不新增执行内核或正文存储，不用时间/名字猜测执行边界，不修改线上数据；不自动部署远端服务。没有可靠工作记录的历史保持分条。

后端范围：`server/agent_service/src/pi/{session-host,session-history,event-sse}.ts`、HTTP schema 和相关测试。前端范围：API types、piConverters、chat store、聊天页搜索定位和回归测试。

## 契约

`work_id?: string` 为 Agent 工作记录 ID，历史 entries 和重连 `active_runs` 可携带；普通实时 SSE **不携带**此字段。后端接入说明第 18 项是现行契约。前端保留对携带该字段事件的兼容，但不得依赖它恢复运行或分隔执行。

实时按 `source_employee_id` 与 `agent_start / agent_settled` 管理执行边界，settled 后下一次 start 使用新气泡；settled 之前的重试不拆分。`work_id` 只作为展示关联，不能代替 entry_ref、事件游标、幂等 key 或用户输入 logical_message_id。历史只关联可验证的 live 区间；未知结束位置的中断历史与推导的 pi_history 不做猜测归并。

## 历史远端服务兼容记录

2026-09-11 核对 8783 OpenAPI：entries / SSE 尚无 work_id，工作记录已有 id、input_entry_ref、output_entry_ref。

读取完整历史后，只有 assistant 缺失 work_id 才分页读取现有工作记录。仅使用同一会话、live、succeeded、输入输出锚点均存在的记录，按真实员工归属补充执行 ID。不同会话、重叠区间、缺失锚点、中间出现同员工新输入、已有 work_id 冲突均不猜测合并。工作记录读取失败仍正常展示历史。

此路径可让旧服务的已完成且边界完整的回复使用聚合展示。新服务在历史中输出 work_id，无需额外读取工作记录。多次委派同一员工的实时分组遵循现行 start/settled 契约，不要求后端在普通 SSE 中补 work_id。只有思考/工具而无正文时不显示“无回复内容”的空正文气泡。

## 历史与运行投影归并修复

- `replyProjection.ts` 统一归并同一会话、同一员工的历史行与 pending 行，保留 pending 展示 ID 和所有原始 entryRefs，移除重复行；原始 entries 仍用于已读。
- 优先采用 work ID / entry 引用。实时事件尚无 work ID 时，只允许同员工工具调用 ID 在历史中唯一对应一个已知 work 的精确关联；冲突 work、跨员工、没有可靠归属的旧历史不合并。正文、名字和时间不是关联键。
- 重连 entries 只是最近窗口，按 entry_ref 合并原始条目后再重建投影，避免覆盖较早历史。`active_runs.message` 只是当前模型轮次，不得替换整次执行的过程和正文；快照与已确认同执行的缓存做重叠合并。
- 合成快照 ID 不加入 entryRefs。已 settled 的缓存保持 delivered，不因重连再次被标记 streaming。后台会话的缓存也参与对账，切回时接续同一投影。
- 回归覆盖历史 + 活跃快照重叠、重复重连、切回会话、跨轮过程保留、普通 SSE 无 work_id、员工隔离与模糊工具 ID 拒绝关联。

## 任务清单：当前状态与执行历史

FredServer 的 `todo_update` 定义为替换当前回复的本地任务清单。因此，在已归并的同一员工同一次回复内，主区域仅显示最后一次可解析且非错误的清单；新增、删除、重排和空列表均按完整替换处理。不同员工或不同执行的清单不合并，也不使用任务名称或任务项 ID 猜测清单归属。

当前卡片使用回复 ID 作为稳定组件 key，状态更新时复用卡片；所有任务完成后显示“全部完成”。失败的调用保留在过程内，不覆盖上一版有效清单。工具参数可用于实时预览，工具返回后以有效结果为准。

思考与工具调用按原顺序保留在“执行过程”中。有任务清单时，该区域在生成中和生成后均默认折叠，用户可随时展开查看每次更新快照。历史快照标记为“任务清单更新”，进行中图标不播放动画。旧格式仅有 toolCalls 的消息也会补充过程步骤，同一调用 ID 不因同时出现在两处而重复展示。

本次清单调整仅修改前端，复用前述回复归并。无法确定执行边界的旧历史仍不强行合并。

验证：构建（含类型检查）、本次生产代码 ESLint、diff 检查通过；全量 256 项测试中 255 项通过，唯一失败仍为上述原有登录页样式检查。新增覆盖最新清单替换、失败回退、独立回复隔离、重复工具事件、实时/结算/刷新一致性，以及实际 React 组件的静态渲染和模拟状态下的展开/收起处理；未进行真实浏览器交互验收。
